# ADR-0007: コスト計測プロキシは API キー限定・非ストリーミングで、計れない呼び出しは中継しない

- **ステータス**: 採択
- **日付**: 2026-09-20

## 背景

Step2 の成果物は「LLM 呼び出しを中継するプロキシ（Anthropic/OpenAI 互換）、トークン・料金を `UsageEvent` に記録、日次集計」で、受け入れ基準は「料金計算がベンダー公表単価と誤差 0 ／ 追加遅延 p95 ≦ 50ms ／ 1 万件で集計 SQL ≦ 1 秒」（`docs/roadmap.md`）。

プロキシは Step1 までの API と性質が違う。**呼び出し元は人ではなくエージェント**で、資格情報は API キー（`aop_k_`）。中継先は外部のサービスで、本文はベンダーの仕様に従う。誤ると「請求の根拠が壊れる」「未認証の第三者に課金が乗る」「SSRF で内部へ到達される」のいずれかになる。

## 決定

1. **認証は API キーだけ**。`route()` に受け付ける資格情報の種類を渡せるようにし（既定は従来どおりユーザートークン／プラットフォーム管理者）、プロキシのルートだけ `auth: 'apiKey'` を指定する。ユーザートークンでプロキシを呼ぶと **401**（権限不足の 403 ではなく「この経路では資格情報として受け付けない」）。逆に API キーで v1 の API を呼んでも 401 のまま（`openapi.yaml` の `securitySchemes` に書いてある約束を実装でも守る）。
2. **エージェントに紐づかないキー（テナント共通キー）では中継しない（403）**。`UsageEvent.agentId` は NOT NULL なので、記録先が決まらない呼び出しを受け付けると「計測しないまま課金だけ発生する」経路になる。
3. **停止中（`stopped` / `suspended`）のエージェントのキーも 403**。Step4 の自動停止が実際に呼び出しを止める経路はここ。
4. **料金表に無いモデルは上流へ送らず 422**。0 円で記録すると請求の根拠が黙って壊れ、Step4 のコスト超過ルールも効かない。「計れない呼び出しは中継しない」を選ぶ。
5. **成功も失敗も `UsageEvent` を 1 行記録する**（失敗はトークン 0・料金 0・`statusCode` は実際の値）。Step4 のエラー率ルールが読む材料になる。**記録の失敗は中継を止めない**（サーバログに残して応答は返す）。**「失敗」を例外の種類で絞らない** — `ApiError`（時間切れ 504・接続不能 502 など、こちらが意味を与えた失敗）だけを記録する形にすると、上流を呼び終えた後に想定外の例外が出た経路（利用者へは 500）でだけ記録が 1 行も残らない。上流の課金は発生しているので「課金されたのに台帳に無い」状態になり、Step4 のコスト超過・エラー率がその呼び出しを見落とす。上流へ 1 バイトも出ていない呼び出しを記録しない方針（決定 7 の 503）とは両立する — 接続先の解決は記録の枠の外側にあるため。
6. **接続先はコードと環境変数だけから決める**。クライアントの本文・ヘッダ・パスは接続先に影響しない。許可するのは https、または**非本番の**ループバック http（ローカルのスタブ上流）だけで、資格情報付き URL・クエリ付き・その他のスキームは拒否する（fail-closed）。上流の資格情報はサーバ側の環境変数から取り、クライアントの `Authorization` は**上流へ転送しない**。転送するヘッダはコード側で組み立てるものだけ（クライアントのヘッダは 1 つも通さない）。リダイレクトは追わない（追うと接続先の判断を上流に握られる）。
7. **上流の失敗の扱い**: 2xx はそのまま返す。**許可リストに載る 4xx（400 / 413 / 422）はステータスを保ち、本文は絞って**返す（送り主自身の要求についての診断なので、握り潰すとデバッグできない）。それ以外の 4xx と 5xx は **502** に写して上流の本文を返さない（内部情報を利用者へ出さない）。時間切れは **504**、接続不能は **502**、中継の設定が無い・安全でない場合は **503**。

   **ただし 4xx の「そのまま返す」は本文には及ばない。** 上流の自由記述（`error.message`）には**プラットフォーム側の上流アカウント**の状態が載る。実測で確認した例はいずれも 4xx で、Anthropic の残高不足は **400**（「Your credit balance is too low … go to Plans & Billing」）、OpenAI の `model_not_found` は **404**（「… your organization &lt;組織名&gt; does not have access to it」）、上限超過の契約ティアや tokens/min は **400 / 413**。上流のアカウントは全テナントで共有なので、素通しすると**有効な API キーを 1 本持つ相手が他テナントぶんの課金・組織・契約の状態まで観測できる**。

   最初の版は「漏れるステータス」を表に並べて隠す形だったが、**ステータス番号では選り分けられない** — 上の 400 は「送り主の本文が悪い 400」と同じ番号で、表に足していく限り必ず抜けが残る（実測で 400 / 402 / 404 / 413 が漏れた）。そこで判断の軸を**本文のどの項目か**に変えた:

   - **項目の許可リストで絞り、値も綴りで絞る**。機械可読な `error.type` / `error.code` / `error.param` と最上位の `type` だけを通し、自由記述は自前の定型文へ差し替える（`src/lib/proxy/error-body.ts` が唯一の規則）。ベンダーの形は保つので SDK は読めるまま、「どの入力が悪いか」という診断も残る。上流の `request_id` も落とす（こちらの `UsageEvent` に記録が残るので、対応付けはプラットフォーム側で行う）。**項目名だけで絞ると足りない** — 最初の版は「文字列で 100 文字以内」しか見ておらず、実測で `code: 'quota for org-ACME exhausted; plan=Enterprise; …'` や `param: 'organization ACME Corp (tier: enterprise) has no access …'` がそのまま中継された（`*_BASE_URL` の差し替え先として想定している社内ゲートウェイや Azure OpenAI・LiteLLM は、こういう値を入れてくる）。値の綴りと長さも絞る（規則は `src/lib/proxy/error-body.ts` が唯一の定義。現行の形は下の「残る境界」に書く）。
   - **ステータス番号も許可リストで絞る**。本文を定型文へ差し替えても、番号そのものが共有している上流アカウントの状態を語ることがある（実測で `402 Payment Required` / 404 / 409 / 451 がそのまま届いた。とくに 402 は「プラットフォームの支払いが滞っている」を 1 ビットで伝える）。**隠すものを並べる拒否リストでは、ベンダーが新しい番号を使い始めた瞬間に黙って漏れる**ので、逆に「そのまま返してよい 4xx」を並べる（`RELAYABLE_CLIENT_ERROR_STATUSES` = **400 / 413 / 422**。どれも「送り主自身の要求についての診断」と言い切れる）。それ以外の 4xx・3xx・5xx はすべて **502**。
   - **401 / 403 / 429 は写像の表で個別に扱う**。401 / 403 は 502（利用者には中継の失敗としてだけ伝える）、429 は **429 のまま**（「待てば通る」情報には意味がある）。表は `src/app/api/v1/proxy/proxy-route.ts` の `UPSTREAM_STATUS_MASKING` で、**上流の `Retry-After` を中継してよいかも表が持つ**（429 だけ true）。401 / 403 でも中継していたときは「この 502 はバックオフ由来だ」というプラットフォーム側の状態が伝わっていた（実測）。中継するのは **RFC 9110 の delay-seconds（整数の秒数）の形だけ**で、それ以外（HTTP-date や非数値）は落とす。

   **上流の本文が JSON として読めないときは、ステータスに関わらず 502 にする。** 前段のゲートウェイが返す HTML のエラーページ、本文を持てない 204 / 304 の空文字、上限を超える大きさの本文がここに来る。**判定に `Content-Type` を使わない** — 前段が付け替えただけの正しい JSON を捨てる形にすると、トークン分を記録したのに応答は返さない「課金だけして捨てる」経路になった（実測で 33,000 マイクロ USD を記録して 502 を返した）。また 204 の本文をそのまま `Response` へ渡すと `TypeError` になり、上流の異常が「自分の内部エラー」= 500 とスタック付きのログに化けていた（実測）。

   **上流の応答本文にも上限を置く**（`UPSTREAM_MAX_RESPONSE_BYTES`。リクエスト側とは別の値 — LLM の応答は入力より大きいのが普通）。`Response.text()` は全量をメモリへ載せてからしか大きさが分からないので、壊れた前段ゲートウェイが巨大な本文を返すと「同時リクエスト数 × 本文サイズ」のヒープをタイムアウトまで握る（実測で 64 MiB を丸ごとバッファした）。数えながら読む処理は `src/lib/stream-bytes.ts` にまとめ、リクエスト本文（413）と上流の応答（502）で**写像先の HTTP エラーだけ**を変えている。

   **503（中継が未設定・設定が安全でない）のときは `UsageEvent` を記録しない** — 決定 5 が言う「成功も失敗も記録する」の対象は**実際に上流へ出た呼び出し**で、1 バイトも出ていない呼び出しを記録すると、上流が未設定のあいだ有効なキー 1 本で DB の行だけを無制限に増やせる（実測）。接続先と資格情報の解決を記録の枠の外側に置くことで、この区別をコードの構造で表している。

   **残る境界**:

   - **`type` / `code` / `param` の値は、形では最後まで塞げない**。(a) いずれもベンダーの分類語彙なので、`billing_hard_limit_reached` / `model_not_found` のように「共有している上流アカウントの状態」をカテゴリとして示す値は残る。(b) **区切り文字で単語を繋いだ短い文も通る**（`org_ACME_Corp.tier_enterprise.balance_zero` 等）。最初の版は 1 本の正規表現に `.` と `-` をまとめて許していたため、`credit_balance_too_low.add_funds_at_Plans_and_Billing` のような文がそのまま中継された（実測）。いまは項目ごとに綴りを分け（`type` / `code` はトークン 1 つ、`param` はトークンを `.` と `[添字]` で 6 つまで繋いだ JSON パス）、**トークンの定義は共有する**（英数字の語を `_` で 4 語まで）。**さらに総長の先読みで頭を押さえている**（`type` / `code` は 40 文字、`param` は 48 文字。**最上位 `type` は閉じた語彙 `'error'` だけを通す**ので搬送には使えず（運べるのは「その項目が出るかどうか」の 1 ビットだけ）、`error.type` 40 ＋ `error.code` 40 ＋ `error.param` 48 = **1 応答あたり 128 文字**。最上位を閉じたのは、入る値が 1 つしかない項目に綴りの自由度を与えても診断が増えないのに搬送容量だけが 40 文字増えるため — 実測で `OrgAcmeCorpTierEnterpriseBalance0` 33 文字が最上位に乗った）。**この「値は 1 つ」は公式のベンダー経路（Anthropic 直・Vertex / OpenAI / Azure OpenAI / Bedrock）についての断定で、`*_BASE_URL` が指せる社内ゲートウェイや OpenAI 互換の自ホスト実装が最上位へ別の値を置く場合、その診断は落ちる**（残る境界。搬送容量 40 文字の削減と引き換えに受け入れる）。**語数・階層の上限の効き方は項目で違う。** `type` / `code` は 1 トークンなので語数 4 がそのまま散文の上限になり、総長だけでは通ってしまう英文（`your_credit_balance_is_too_low` 30 文字）をここで止めている（実測）。一方 `param` は「6 階層 × 各 4 語」まで許すので**総語数は縛れておらず**、同じ 30 文字の散文も**区切りを 1 つ `.` にするだけで通る**（`your_credit_balance.is_too_low`。実測）。総語数に上限を置けばこの散文は落とせるが、**塞ぎきれはしない** — 5 語以内でも `ACME.tier_enterprise.balance_zero`（33 文字）のように組織名・契約ティア・残高状態は運べる（実測）。そのうえ上限は 5 にするしかなく、実在の `param` が既に 5 語に達している（`messages[0].content[0].source.media_type` / `tools[0].custom.format.grammar.definition`。実測）。**だから締めずに境界として記録する。** あわせて 2 つ: (c) **語数の上限を数字が迂回できる経路が 2 つある**（`_` で区切った語は中身が数字でも 1 語と数えるので `A_1_2_3_4` は落ちる）: **トークンの先頭語**（長さ無制限）と **`[添字]`**（4 桁 × 5 階層）。この 2 つを使うと、残高・TPM・ティアのような数値は総長の枠いっぱいまで運べる（実測: `a[1234][5678][9012][3456][7890]` 31 文字、`creditsRemainingUsdCents00000123456789` 38 文字）。(d) **PascalCase には語数の上限が効かない**ので、`param` では実質 48 文字までの英文が通る（実測: `YourCreditBalanceIsTooLow.GoToPlansAndBilling` 45 文字）。**トークンの綴りを項目ごとに別々に書くと壊れる** — `param` 側の文字クラスに `_` を入れていたときは階層の上限が `_` を 1 つも数えず、この保護が `param` にだけ効いていなかった（実測で 30〜48 文字のアンダースコア散文がそのまま中継された）。綴りだけを絞って項目別に分けた版は、語数ぶんの掛け算で**かえって運べる文字数が増え**（256 → 387 文字）、99 文字の散文がそのまま中継された（実測）。通る実在のベンダー値は `tests/proxy-error-body.test.ts` が固定する（件数はここに書かない — 写しを持つと必ず古くなる）。**「空白が無いから散文は入らない」とは言えない**。`param` はドットを許すので `org_ACME_Corp.tier_enterprise.balance_zero`（42 文字）は通り、`_` 区切りだけの `type` / `code` では同じ文字列が落ちる。完全に塞ぐには「既知の安全なコードだけの閉じた語彙」にするしかなく、ベンダーが値を増やすたびに診断が黙って消える（別の壊れ方）ので採らない。
   - **2xx の本文は素通しなので、上流が「エラーを 200 で返す」形だと絞り込みが丸ごと外れる**（実測で、200 の本文に入れた残高・組織名・キーの断片がそのまま届いた）。実際の Anthropic / OpenAI の非ストリーミング応答はこの形を取らないので、到達には上流側の異常が要る。踏み込むなら「2xx でも最上位に `error` キーがあれば絞る」だが、正常な応答に `error` を含むベンダーが出たときに壊れるので、いまは境界として記録するに留める。
   - **許可リストに残した 400 は、上流アカウントの課金状態のオラクルになる**。`error-body.ts` 冒頭が実測として記録しているとおり Anthropic の残高不足は 400 で返るので、テナントは「プロキシ自身の検証を通る最小の妥当な要求」を投げて 200 か 400 かを見るだけで、プラットフォームの残高切れを判定できる（**差し替わるのは自由記述（`message`）だけ**で、上の (a) のとおり `type` / `code` / `param` は残るため、`billing_error` / `billing_hard_limit_reached` のような課金カテゴリは番号と一緒に届く）。**それでも 400 を 502 へ写さないのは、ベンダーの SDK が 502 を再試行し 400 を再試行しないため** — 送り主の壊れたペイロードを 502 にすると 1 要求が 3 要求になり（既定 `maxRetries = 2`）、**共有している上流アカウントのレート枠（RPM / TPM）を 3 倍消費して他テナントの 429 を誘発する**（400 で拒否された要求にトークン課金は乗らないので、効くのは課金より枠のほう）。加えて `UsageEvent` の行も 3 倍になる。**そもそも 400 を 502 へ写してもオラクル自体は消えない** — 妥当な最小要求を繰り返して恒常的に 502 が返れば同種の観測はできる（502 は上流 5xx・時間切れ・接続不能とも混ざるのでノイズは増え、`billing_hard_limit_reached` のような課金カテゴリは消える）。つまり 400 と 502 の選択で変わるのは再試行の挙動と診断の質だけなので、隠す努力に見合う効果が無いと判断した。**同じ許可リストに載る 413 も同種のオラクルになりうる**（上限超過の契約ティアが 413 で返る場合）。ただしこちらは自前の本文上限（`JSON_BODY_MAX_BYTES`）が先に 413 を返すので、上流の 413 に到達できるのは上流側の上限がそれより小さいとき（社内ゲートウェイ等）に限られる。
   - **`*_BASE_URL` の許可判定はスキームしか見ない**ので、https であればプライベート IP（`10.0.0.5`）やクラウドメタデータ（`169.254.169.254`）も受理する。接続先は環境変数だけで決まりクライアントからは影響しないので古典的な SSRF ではないが、§9 の「プライベート IP・メタデータへの到達を遮断する」とはずれている。ホストの許可リストを足すと「社内ゲートウェイを指す」という明示した用途を壊すので、運用者を信頼する前提を選んでいる。

   記録する `statusCode` は**上流が返した値**なので、「上流は 200 だが本文が使えず 502 を返した」場合は 200 として残る（トークンは読めないので料金は 0）。Step4 のエラー率ルールはこの 1 件を成功として数えるが、利用者へ 502 を返した事実は台帳からは読めない。上流の事実とクライアントの体験のどちらを記録するかは Step4 でルールを書くときに決める。
8. **ストリーミング（`stream: true`）は Step2 の範囲外**で 422。黙って非ストリーミングへ落とさない。
9. **本文は `z.strictObject` にしない**。ベンダーのペイロードそのものなので、未知キーを 422 にするとベンダーが新しいパラメータを足しただけで中継が止まる。計測に必要な最小限（`model` 必須、`stream` は不可）だけを検証し、残りは保ったまま上流へ渡す。契約側も `additionalProperties: true` にし、`tests/openapi.test.ts` の「両側が未知キーを閉じる」検査には**理由付きの除外 1 件**を登録する（除外表は実在チェックと理由必須つき）。

## 理由

- 2〜4 はいずれも「記録できない呼び出しを受け付けない」という 1 つの方針の言い換えで、プロキシの存在理由（コストの可視化）を守る。
- 6 は §9 の SSRF 対策そのもの。接続先を環境変数に限れば、ユーザー入力から到達先を組み立てる経路が存在しなくなる。
- 7 の分け方は「誰の問題か」で決めている。4xx は送り主、5xx は上流。上流の 5xx をそのまま返すと、内部の詳細が利用者へ漏れるうえ、監視上も「自分の障害」と「上流の障害」が混ざる。

## 結果

- 実装は `src/lib/proxy/upstream.ts`（接続先とヘッダ）・`src/lib/proxy/usage.ts`（トークン数の読み取り）・`src/app/api/v1/proxy/proxy-route.ts`（本体）に分かれ、プロバイダごとの違いは前 2 つに閉じる。
- 追加遅延は `scripts/bench-proxy.ts` が測る。ローカルに https のスタブ上流を立てるので、**実際の Anthropic / OpenAI は呼ばず課金も発生しない**。測り方（逐次実行で 1 件あたりの増分を測る理由、p97.5 を使う理由、判定の前に捨て玉を流して初回コストを判定へ混ぜない理由）はスクリプト冒頭のコメントが正本。
- ベンチに使う `autocannon` は devDependency。推移依存の `uuid@8` に moderate の勧告（GHSA-w5hq-g745-h8pq）があるが、対象は v3/v5/v6 に `buf` を渡す使い方で、`hyperid` は Node 22 の `crypto.randomUUID` を使う（無い環境でも v4）。配布物にも入らないため受け入れる。ゲートの基準（`npm audit --audit-level=high` が 0）は満たしたまま。

## 残る宿題

- **プロキシ経路のレート制限が無い**: 有効な API キーを持つ相手は上限なく中継を要求できる。上流の 429 は中継するが、こちら側で先に絞る仕組みは持っていない（§9「公開エンドポイントを保護する」の宿題）。本文サイズとタイムアウトは効いているので、残るのは頻度だけ。Step4 のガードレール（しきい値ルール）と同じ層で扱うのが自然なので、そこで実装する。
- **`Agent.budgetMicroUsd` を中継時に見ていない**: 予算の列は Step1 で持っているが、プロキシは超過しても止めない（記録するだけ）。「しきい値ルール → 自動停止」は Step4 の成果物なので、前フェーズへ混ぜない（`docs/roadmap.md` の Step の順序）。それまでは予算は「台帳上の宣言」であって強制ではない。
- **ストリーミング中継**: SSE を中継しながら最後の usage イベントでトークン数を記録する。途中で切れた呼び出しの扱い（記録するか・料金をどう置くか）を決めてから着手する。
- **本文サイズとタイムアウトの前段での打ち切り**: ADR-0005 と同じく、アプリの手前のリバースプロキシで落とす前提。プロキシの本文上限はアプリの JSON 上限（`JSON_BODY_MAX_BYTES`）と同じ値を使っており、入口のバッファ（`ENTRY_MAX_BODY_BYTES`）の計算には波及させていない。
- **エージェントの登録プロバイダと中継先の一致**: いまは一致を求めていない（記録する `provider` は中継先のもの）。マルチプロバイダのエージェントを扱えるようにする代わり、「Anthropic として登録したエージェントが OpenAI を呼ぶ」ことが台帳からは読めない。Step5 のダッシュボードで実際の内訳を見せるときに再検討する。
