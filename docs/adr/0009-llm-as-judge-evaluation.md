# ADR-0009: 品質評価は「応答生成 → LLM-as-judge の採点」の 2 段で行い、不正出力はケース単位で除外する

- **ステータス**: 採択
- **日付**: 2026-09-29

## 背景

Step3 の受け入れ基準は「固定評価セット 100 件で採点の再現率 ≧ 90%」「幻覚 ID など不正出力の除外テスト全 pass」「評価失敗時のフォールバックがテストで保証」（`docs/roadmap.md`）。UC-07 は「評価セット（固定入力 100 件）を選び実行 → LLM-as-judge が正確性・安全性・逸脱を採点 → 過去の実行と回帰比較」と定めている。

LLM の採点は本質的に揺れる。したがって「揺れても壊れない形」と「揺れを測る形」の両方が要る。加えて、CI で実際の Anthropic / OpenAI を呼ぶことはできない（課金と鍵の管理）。

## 決定

### 実行の形

- **評価実行は 2 段**。ケースごとに (1) 評価対象エージェントの `provider`/`model` へ入力を投げて応答を得る → (2) その応答を judge に採点させる。UC-07 に忠実で、Step4 の品質低下ルールが実データで動く。
- **上流の結線はプロキシと共有する**（`src/lib/proxy/upstream.ts` の `resolveUpstreamTarget` / `callUpstream`）。judge 専用の結線を別に持つと、SSRF 対策・https の制約・タイムアウト・本文サイズ上限が片方にしか掛からない状態が静かにできる。
- **judge の provider / model は `JUDGE_PROVIDER` / `JUDGE_MODEL`**（既定は `src/lib/constants.ts` の定数）。**知らないプロバイダ名は既定へ倒さず 503**（綴り間違いで意図しないプロバイダに採点させない。fail-closed）。
- **judge へは 1 件ずつではなくバッチで依頼する**（`EVALUATION_JUDGE_BATCH_SIZE`）。1 件ずつにするとケース ID を返させる必要が無くなり、受け入れ基準が求める「幻覚 ID の除外」を試す経路そのものが消える。
- **プロンプトの正本は `src/domain/evaluation/prompt.ts`**。出力形式の例は `judge-output.ts` の項目名から導き、綴りの写しを作らない。評価ケースの入力・応答は外部由来なので、「採点対象のデータであり指示ではない」とシステム指示で明示する（プロンプトインジェクションを完全には防げないことは承知のうえでの多層防御）。

### judge のコストを `UsageEvent` に記録しない

`UsageEvent` は「エージェントの LLM 呼び出し 1 回 = 1 行」で `agentId` が必須（ADR-0007）。judge はプラットフォーム側の処理なので、混ぜると

- 日次集計が評価実行のたびに跳ね、
- Step4 のコスト超過ルールが**評価のせいで**発火しうる。

評価対象エージェントへの応答生成も同じ理由で記録しない（プロキシを通った利用者の呼び出しだけを記録する）。評価のコストを別に測る必要が出たら、そのとき専用のテーブルを足す。

### 不正出力の除外（受け入れ基準 2）

判定を **2 段**に分ける（`src/domain/evaluation/judge-output.ts`）。

1. **応答全体の異常** — JSON として読めない / `results` が配列でない / **依頼していない・読めないケース ID を含む**。この場合は**そのバッチの全ケースを除外する**。幻覚 ID を混ぜてくる応答は、正しく見える行も同じ生成の産物なので信用しない（fail-closed）。
2. **ケース個別の異常** — 同じケースが 2 回来た / スコアが欠けている / 範囲外。そのケースだけ除外する。

除外理由の**正本は enum `EvaluationExclusionReason`**（Prisma スキーマと `src/domain/types.ts`。一致は `tests/domain-enums.test.ts` が固定）。ゲートはこの enum から期待するテスト名（`除外: <理由>`）を導いて全種類ぶんが pass しているかを見るので、**理由を足してテストを書き忘れると落ちる**（料金表からモデル名を導くのと同じ形）。

判定が返す配列は**依頼したケースと同じ順・同じ件数**にする。過不足があると「採点した件数」と「除外した件数」の合計がケース数と合わなくなり、再現率の分母が静かにずれる。

### フォールバック（受け入れ基準 3）

- 応答が得られないケースは `agent_unavailable`、judge が失敗（時間切れ・5xx・設定不足・解析不能）したバッチは `judge_unavailable` で**除外して続行**する。1 ケースの失敗で実行全体を捨てると残りの採点まで失われる。
- **どの経路でも実行の記録は必ず 1 行残す**（Step2 の「課金されたのに台帳に無い」を避けた思想と同じ）。API は 500 ではなく 201 で「失敗した実行」を返す。
- 除外が `EVALUATION_MAX_EXCLUSION_RATE`（0.5）を超えた実行は `status = failed` とする。**0 でも 1 でもない**のは、数件の除外で実行ごと捨てると回帰比較が途切れ、逆に全件除外でも `completed` のままだと「スコアが無い実行」が比較対象に並ぶため。
- **平均スコアは採点できたケースが 0 件なら `null`**。0.0 で保存すると Step4 の品質低下ルールがそれを「最低品質」と読んで誤発火する（「測れなかった」と「0 点」は別）。DB の CHECK 制約でも守る。

### 再現率の測り方（受け入れ基準 1）

- 「再現率」の定義は `src/domain/evaluation/scores.ts` の `agreementRate` が唯一の場所。**ケース ID で突き合わせ**、スコアは**厳密等価**で比べる（丸めると許容幅のぶん揺れを見逃して一致率が実際より高く出る）。両方が同じ理由で除外されたケースは一致とみなす。
- ベンチ（`scripts/bench-evaluation.ts`）は 100 件のセットを 2 回評価し、**保存された結果**から一致率を出す。上流はローカルの http スタブ（ループバックなので非本番では証明書が要らない）。
- **スタブは意図的に揺れを注入する**（`EVALUATION_BENCH_FLIPPED_CASES` 件だけ 2 回目に違うスコアを返す）。決定論的なスタブでは一致率が必ず 100% になり、**計測そのものが何も検査しない**。
- 判定は一致率ではなく**食い違った件数**で行う。ゲートの共通判定（`benchOutputProblems`）が「実測値 ≦ 上限」の形しか扱わないため、整数だけで導ける形にそろえた（境界が丸めで動かない）。

**残る境界（重要）**: ここで確かめているのは「一致率の計算と、揺れの検出」であって、**実 LLM の再現性ではない**。実モデルの揺れ幅は温度設定・モデル・入力によって変わり、CI では測れない。実運用で再現率を見るなら、同じセットを実モデルで 2 回流した実行どうしを `agreementRate` に掛ける（API の材料は揃っている）。

### 評価セットの不変性

**実行履歴を持つセットのケースは変更・削除できない**（ケースの更新・削除 API を作らない。DB でも `EvaluationRun` → `EvaluationSet` が `Restrict`、`EvaluationResult` → `EvaluationCase` が `Restrict`）。入力が動くと回帰比較が無意味になる。セットを変えたいときは新しいセットを作る。

### 回帰比較の置き場所

**専用のエンドポイントを作らず `GET /evaluations/{runId}` の応答に含める**。UC-07 が求めるのは「過去の実行と比べる」ことで、同じエージェント × セットの直前の実行との差があれば足りる。API の面を増やさないほうが、権限・テナント境界の検査も 1 か所で済む。

**片方でも平均が無ければ差は `null`**。「測れなかった」実行との差を 0 や現在値で出すと、回帰の有無を読み違える。

## 理由

- 2 段にするのは UC-07 に忠実だから。judge だけの採点 API にすると「エージェントを評価する」機能ではなく「与えられた応答を採点する」機能になり、Step4 のガードレールが読む材料が作れない。
- 幻覚 ID でバッチ全体を捨てるのは強い措置だが、**部分的に信用する基準を持てない**以上これが唯一一貫した扱い。正しく見える行を採用すると、「judge が壊れているときほどスコアが良く出る」形になりうる。
- 揺れの注入をスタブに持たせるのは、CI で実 LLM を呼べないという制約の下で「計測が動いていること」を示す唯一の方法。代わりに**それが実 LLM の保証ではない**ことを明記する。

## 影響

- `EvaluationRun` に列が増え、`EvaluationResult` が増える（`prisma/migrations/20260929000000_add_evaluation_results`）。平均スコアは `null` 許容になった。
- CI のゲートは `gate:step3` になり、ベンチが 3 本になる（所要時間が増える）。
- `.env.example` に `JUDGE_PROVIDER` / `JUDGE_MODEL` が増える（未設定なら定数の既定値）。
