# ADR-0010: ガードレールは「超過した操作の直後」に判定し、監査ログは HMAC のハッシュ連鎖で追記専用にする

- **ステータス**: 採択
- **日付**: 2026-10-02

## 背景

Step4 の受け入れ基準は「ルール発火から停止まで ≦ 3 秒（統合テスト）」「監査ログの改ざん検知テスト pass」「E2E で『登録→実行→超過→停止→復帰』が通る」（`docs/roadmap.md`）。UC-08 は「しきい値ルールを設定し、超過したらエージェントを自動停止して通知する」、UC-09 は「停止したエージェントを復帰させ、操作を監査ログに残す」と定めている。

あわせて ADR-0007 が Step4 へ割り当てた宿題が 2 件ある。**プロキシ経路のレート制限**（有効な API キーがあれば無制限に中継を要求できる）と **`Agent.budgetMicroUsd` の強制**（予算は台帳上の宣言で、超過しても止まらない）。どちらも「しきい値を超えたら断る」という同じ層の話なので、この Step で閉じる。

Step4 のモデル（`GuardrailRule` / `Incident` / `AuditLog`）と enum（`RuleKind` / `RuleAction` / `IncidentStatus`）は Step0 の初期マイグレーションで既に作られている。新規に作ったのは**ハッシュ連鎖の 3 列と追記専用トリガ**だけ。

## 決定

### 判定の起点とタイミング（受け入れ基準 1）

**入口は `src/lib/guardrail/evaluate.ts` の `evaluateGuardrails` だけ**にし、3 つの起点がすべてこれを通る。別経路を書くと「cron では発火するのに中継では発火しない」食い違いが静かに生まれる。

| 起点 | 見る種別 | 理由 |
|---|---|---|
| 中継の直後（`POST /proxy/*`） | `cost` / `error_rate` | 利用イベントが増えるのはここだけ |
| 評価実行の直後（`POST /evaluations`） | `quality` | 品質が動くのはここだけ |
| 明示実行（`POST /guardrails/run`） | 全種別 | cron と「いま止まるべきか」の確認 |

**cron 間隔に依存しないのが要点。** 「超過しうるイベントの直後・同じリクエストの中」で判定するので、発火から停止までは DB の往復数回で終わる（実測 34ms / 上限 3000ms）。

**中継の直後と評価の直後で見る種別を分ける**のは費用の問題。品質を中継でも見ると、中継 1 回ごとに評価実行の表を引くことになる（しかも中継では品質は動かない）。2 つの表を足し合わせると `RuleKind` を全網羅することは `tests/guardrail-evaluate.test.ts` が enum から導いて確かめる — **種別を足して結線を忘れると、そのルールは永久に発火しない**。

**順序は固定する**: 有効ルールを引く → 窓を集計して判定 → `Incident` の記録と自動停止（アダプタが 1 トランザクション）→ 監査ログ → **通知は最後**。

- **止める側は fail-closed、記録と通知は fail-open。** 通知や監査ログの失敗で停止を取り消すと、受け手が落ちているあいだ「超過しても止まらない」状態になり、守るべきものが守れない。
- **通知を最後に回すのは、受け手の応答時間を「発火から停止まで」に入れないため。**
- **さらに中継の経路では通知の完了を待たない**（`GuardrailTrigger.detachNotifications`）。待つと受け手の応答時間が中継の応答時間に乗り、受け入れ基準「追加遅延 ≦ 50ms」を**外部の遅さで**破る（実測: 1.2 秒で応答する受け手に対して中継が 1.2 秒以上）。しかも**プロキシのベンチは「発火しないルール」で測るのでこの経路を通らない**ので、検出もできなかった。明示実行の API は待つ側のままにする（「いま判定して結果を返す」操作なので、通知まで含めて応答と対応しているほうが読みやすく、テストも決定的）。**残る境界**: 待たない側では、応答後に関数を凍結する配備先（serverless）で通知が完了しないことがある。通知は元から fail-open なのでこの取り落としは設計の範囲内。

**同じ窓の長さの集計は 1 回だけ問い合わせる。** 「50% で通知、80% で停止」のように同じ窓で複数のルールを持つのが自然な使い方なので、ルールごとに集計すると件数ぶんのクエリが中継 1 回ごとに走る（§8 の N+1 回避）。

**プロキシの遅延は測り直した。** Step2 の受け入れ基準（p97.5 ≦ 50ms）は緩めていない。ベンチの仕込みに**絶対に発火しないルール**を 1 件置いて「新しい現実」を測った結果、ルール無し 14ms → ルール 1 件 15〜17ms（Step4 の結線の cost は約 1〜3ms）。発火させないのは、発火するとエージェントが止まって以降の中継が全部 403 になるため。

### 発火の重複排除

**測れていないものは発火させない。** 呼び出し 0 件の窓・採点 0 件の評価に加えて、**エラー率は分母が `GUARDRAIL_ERROR_RATE_MIN_REQUESTS`（20 件）に届かない窓でも発火させない**。1 件だけ呼んで失敗した窓は 1/1 = 100% なので、門番が無いとしきい値をどう置いても必ず発火する — 失敗には送り主自身のペイロードの誤り（4xx）も入るので、低トラフィックのエージェントがたった 1 回のミスで自動停止し、復帰に人の操作（UC-09）が要る状態になる。コストと品質に同じ門番は要らない（合計と平均スコアは 1 件でも意味を持つ）。定数は `src/domain/guardrail/rule.ts` に置く（`src/domain/` は `src/lib/` を参照しない）。

**判定の窓は「引き金になった行」を必ず含める。** `UsageEvent.createdAt` / `EvaluationRun.createdAt` は **DB の `now()`** が入れる値で、窓はアプリの時計から組み立てるので、2 つの時計がずれていると**しきい値を越えさせた当の支出が集計から落ちる**（発火せず、以降の呼び出しが来なければ止まらない fail-open。マネージドな PostgreSQL の NTP ドリフトで現実に起こりうる）。**向きごとに別の手当てが要る**:
- DB が**進んでいる**とき（行の時刻 > いま）: 窓の終端が行より前になる → 基準時刻を「書いた行の時刻」と「いま」の遅いほうにする（`evaluationBasisTime`）。
- DB が**遅れている**とき（遅れが窓の長さを超える。窓 1 分で 90 秒の遅れ 等）: 窓の開始が行より後になる → 窓の開始を引き金の行まで広げる（`guardrailWindow` の `includeFrom`。起点は `GuardrailTrigger.triggeredBy` で渡す）。**片方だけでは塞がらない**ので両方入れる。

**連鎖の検証は区間に分けて行う。** 1 回に読む件数には上限（`AUDIT_CHAIN_VERIFY_MAX_ROWS`）があるので、`GET /audit-logs/verify` は `?fromSeq=` でその連番から検証でき、続きがあるときは `nextFromSeq` を返す。**上限だけを置いて先頭からしか読めない形にしてはいけない** — 行数が上限を超えたテナントでは毎回同じ最古の区間を検証し続け、**それ以降の行は二度と検証されない**（DB を触れる相手が新しい行を書き換えても「無傷」と答える。改ざん検知が静かに効かなくなる fail-open）。途中から辿れるのは、**1 つ前の行のハッシュを錨として渡す**ため（`AuditChainAnchor`）。錨には連番も入れて「区間の先頭が削除されている」も検知する — 錨を見ない実装にすると、区間に分けた瞬間に継ぎ目の差し込みを見逃す。

**通知の `occurredAt` はその発火の時刻**（インシデント行の作成時刻ではない）。開いている行を再利用したときに行の時刻を送ると「数日前に起きた出来事の通知がいま届いた」ように見え、しかも本文の要約はこの発火の実測値なので、1 通の中で時刻と数字が別の出来事を指すことになる。**インシデント行は最初の発火を表したまま**にし（`createdAt` と `summary` は更新しない）、各回の実測値は通知と監査ログに残す。発火回数や最終発火時刻を行に持たせるのは宿題（下記）。

**開いているインシデントが同じルール・同じエージェントにあれば、新しい行を作らない**（`RaisedIncident.created`）。超過は「しきい値を下げる・窓が過ぎる・使用量が減る」まで続くので、判定のたびに行を作ると記録と通知が溢れる。とくに **`action` が notify のルールは停止しないので条件が自己収束しない** — レート制限の上限（毎分 600 件）まで中継できるテナントなら、1 本の設定ミスで毎分 600 件のインシデントと監査行、1200 通の Webhook が出る（実測で、同じ超過のまま明示実行を 5 回呼ぶとインシデント 5 件・監査行 5 件になった）。判定はアダプタの中（エージェント行をロックした後）で行うので、同時の 2 件がどちらも「無い」を見て 2 行作ることは起きない。

**停止は重複排除の対象にしない。** ここを一緒に抑えると、開いているインシデントがあるあいだに復帰させられたエージェントを二度と止められず、**「超過しているのに動いている」状態が残る**（fail-open）。`suspended` は `created` と独立に真になりうる形にし、実際に止めたときは監査ログと通知も出す（「止めた」は記録すべき出来事）。

### しきい値の判定（ドメイン）

- **比べる向きは種別ごとに逆**なので `RULE_COMPARISON`（`Record<RuleKind, …>`）で持つ。種別を足すと typecheck が落ちる。**判定は「測る → 表の向きで比べる」の 2 段**にして、表を実際に読ませる（書き下すと表と実装が食い違っても誰も気付かない。実測で向きを逆にしても全件緑だった）。
- **測れていないものは発火させない（fail-safe）。** 呼び出し 0 件の窓にエラー率は無く、採点 0 件の評価を「品質最低」と読むのは誤判定。止めたいのは悪化したエージェントで、使われていないエージェントではない。
- 品質は 3 観点（正確性・安全性・逸脱）の**最小**を採る。平均にすると 1 観点だけが崩れた形を他の観点が埋めて隠す。**逸脱は「低いほど良い」**ので、向きを直してから（`1 - deviation`）比べる。1 観点でも欠けていれば全体を `null`（測れていない）。
- コストは **BigInt と数値を直接比べる**。`Number()` を挟むと 2^53 を超える額で「超えていないこと」になる。
- 集計窓は**半開区間**で、上限 7 日（`GUARDRAIL_WINDOW_MAX_MINUTES`）。判定は中継 1 回ごとに走るので無制限の窓を許さない。**終端は「基準時刻の 1 ミリ秒後」**にする — `now` を含まない形にすると、判定を起こしたイベント自身（同じミリ秒に記録される）が窓から外れ、**中継の直後のコストルールが永久に発火しない**。

**品質ルールの「低下」は絶対値のしきい値**とする（平均スコアがしきい値を下回ったら発火）。`GuardrailRule.threshold` が 1 列しかないので、「直前の実行からの差」で判定するには列と語彙が増える。差分での判定は宿題（下記）。

### 監査ログの改ざん検知（受け入れ基準 2）

`AuditLog` に 3 列を足した: `seq BigInt`（テナントごとの連番）/ `prevHash String?` / `hash String`、`@@unique([tenantId, seq])`。

- **連番が要る理由**: 連鎖の順序を `createdAt` で決めると同一ミリ秒の 2 行で前後が定まらず、`cuid` も単調増加しない。**順序が曖昧な連鎖は原理的に検証できない。**
- `hash = HMAC-SHA256(AUDIT_HMAC_SECRET, canonical(id, tenantId, seq, actorId, action, targetType, targetId, payload, createdAt, prevHash))`。正規化は `src/domain/audit/chain.ts` の 1 か所だけが持ち、書き込み側と検証側が同じ関数を通る。
- **正規化は JSON の配列**にする。区切り文字で連結すると、値にその文字が入ったときに境界がずれて「別の内容なのに同じハッシュ」を作れる（`action='a|b' + targetType='c'` と `action='a' + targetType='b|c'`）。
- **`payload` はキーを辞書順に並べてからハッシュに入れ、入れ子を許さない。** JSONB はキーの順序を保存しないので並べ替えないと保存して読み直しただけで検証が落ちる。入れ子は正規化がその階層を並べ替えないため**ハッシュが不定に揺れる**。形は `recordAudit` が実行時に確かめて入口で止める（追記専用なので後から直せない）。
- **鍵は環境変数から取り、未設定・32 文字未満は 503 で落とす（fail-closed）。** 鍵なしのハッシュで代用しないのは、DB への書き込み権限を得た相手が値を書き換えたうえで連鎖をまるごと作り直せて、検知の役に立たなくなるため。
- **追記専用を DB トリガで強制する**（このリポジトリ初のトリガ）。`UPDATE` は例外なく拒否、`DELETE` は `SET LOCAL agent_ops.allow_audit_delete = 'on'` を宣言したトランザクション内だけ許可する。逃げ道が要るのはテナント単位の消去要求のため（`AuditLog.tenant` は `onDelete: Cascade`）。**この GUC を設定するコードは `src/` に 1 行も無い**（設定するのは契約テストだけ）。
- 検証（`GET /audit-logs/verify`）は `seq` 順に再計算し、**最初に壊れた `seq` と壊れ方**を返す。壊れ方を 3 つ以上に区別するのは運用で原因を切り分けるため（値の書き換え / 行の削除 / 行の差し込み / 別テナントの混入 / 正規化できない payload）。比較は定数時間（`secretsEqual`）。
- **検証したいテナントを引数で渡す。** 行の `tenantId` を信じるだけだと、取り出すクエリの条件が壊れて別テナントの行が返ったとき、連鎖は整合しているので `ok` を返す（対象テナントを 1 行も見ていないのに「無傷」と報告する）。

**改ざん検知の検査は 2 系統**。(a) 契約テストが追記専用トリガの `UPDATE` / `DELETE` 拒否を実 DB で確かめ、(b) **トリガを明示的に無効化して**書き換え・削除を行い、検証が壊れた位置を返すことを確かめる。(b) が無いと「改ざんできないので検知も試せない」で終わり、検出網の中心が空洞になる。ゲートは**連鎖の壊れ方の enum から導いて**全種類ぶんのテストが pass しているかを見る。

**残る境界**: **末尾の行をまとめて消されたことはこの連鎖では分からない**（1〜N から N を消すと 1〜N-1 は完全に整合する）。区別には外部の錨（別システムへの `seq` と `hash` の定期的な書き出し）が要る。

### 人の操作は「記録できないなら状態を変えない」

状態を変える前に `assertAuditConfigured()` で「監査ログを書ける状態か」だけを確かめる。**変えてから記録に失敗すると、記録の無い変更が残り、しかも再試行は「既にその状態だ」で永久に失敗する** — 実測では、鍵が未設定のとき `POST /incidents/{id}/resolve` が 503 を返しながら incident を `resolved` にし、鍵を設定して再試行しても 409 `already_resolved` が返り続けた（**UC-09 の事後条件「監査ログに残る」がその incident については恒久的に達成不能**）。

対象は人が行う 4 経路: エージェントの停止・復帰（`POST /agents/{id}/stop` / `/resume`）、インシデントの解決、ガードレールのルールの登録・削除。**ガードレールの自動発火だけは例外**で、記録できなくても停止は行う（止める側を優先する fail-open）。

**ルールの設定変更も記録する。** ルールは「何が自動で止めるか」を決める制御そのものなので、誰が入れたか読めないと発火の記録だけでは「なぜ止まったか」を辿れない。**同じ状態への再実行も 1 行残す** — 監査ログが残すのは「誰がいつ何を要求したか」で、状態が動いたかは payload が持つ情報（「止まっているエージェントに誰が resume を打ったか」は追跡したい事実そのもの）。

**発行箇所の無い語彙を置かない。** 定義だけして使わないと「記録しているつもり」を作るだけで、実際には何も残らない（実測で `agent.budget_exceeded` が定義だけされ、予算超過の 403 は監査ログにも台帳にも 1 行も残っていなかった）。`tests/audit-coverage.test.ts` が語彙の表から導いて発行漏れを落とす。

### 通知（Webhook / メール）

- **宛先は環境変数だけが決める**（`NOTIFY_WEBHOOK_URL` / `NOTIFY_MAIL_WEBHOOK_URL`）。利用者が入れた URL へサーバが要求を出す形にすると SSRF の入口になる（上流 LLM の接続先を env 限定にした ADR-0007 と同じ流儀）。したがってここで防いでいるのは攻撃ではなく**設定ミス**で、プライベート IP の遮断は行わない（必要になるのはテナント別の宛先管理を入れるとき）。
- **スキームの規則はプロキシと共有する**（`src/lib/outbound-url.ts`）。https のみ、非本番のループバック http だけ許す、資格情報付き URL は拒否。片方にしか規則が無いと「平文の http で別ホストへ送る」設定ミスがもう片方だけ通る。**クエリ・フラグメントの可否は共有しない** — 上流の基底 URL は後ろにパスを足すので拒否が要るが、通知の宛先はそのまま POST するだけなのでクエリ付き（受け手のトークンを載せた形）が普通に要る。
- **署名できないなら送らない**（`NOTIFY_SIGNING_SECRET` が無い・32 文字未満）。署名なしの通知は受け手がなりすましと区別できない（fail-closed）。署名は `X-Agent-Ops-Signature: sha256=<hex>`。
- **リダイレクトを追わない**（`redirect: 'manual'`）。追うと受け手が接続先を書き換えられ、署名付きの本文が別ホストへ行く。3xx は「届かなかった」扱い。
- **「届かなかった」はすべてサーバログに残す**（宛先が未設定のときだけ出さない — 送るものが無いだけで異常ではない）。宛先の形が駄目なときだけ出していた頃は、(a) 宛先は正しいが署名鍵が短い、(b) 受け手が 2xx 以外を返した の 2 つが**ログに 1 行も残らず**消えていた（発火して停止したのに通知が 1 通も届かず、理由がどこにも無い状態。§6）。文言には**直すべき環境変数の名前**を書く。
- タイムアウトと応答本文のバイト上限を置き、本文は読み捨てる（上限超過では下層のストリームも打ち切る。解放しないとソケットと fd がタイムアウトまで滞留する）。
- **SMTP は持ち込まない。** メールは同じ形の署名付き POST をメール中継（`NOTIFY_MAIL_WEBHOOK_URL`）へ送る。SMTP の資格情報を持たず、送信ライブラリも増やさない。

### レート制限（ADR-0007 の宿題 1）

- **キーはテナント**（`tenant:<id>` / プラットフォーム管理者だけ `platform`）。IP だと `X-Forwarded-For` 由来で偽装できるので認証済みの値から作るが、**資格情報ごと（API キー・ユーザー）にしてはいけない** — どちらも利用者が API から好きなだけ増やせる（`POST /api-keys` ・ `POST /users` に件数の上限は無く、発行経路にレート制限も無い）ので、枠を資格情報ごとに持つと**キーを増やすだけで上限が何倍にもなる**。同じエージェント向けのキーを 100 本発行すれば中継は毎分 60,000 回通り、予算が未設定なら上流への課金に歯止めが無くなる。エージェント単位でも同じ（エージェントも増やせる）。**代償は「1 本の壊れたクライアントが同じテナントの枠を食い潰す」こと**で、費用を払う単位はテナントなので、ベンダーへの無制限な課金よりそちらを選ぶ（配備先ごとの調整は `PROXY_RATE_LIMIT_PER_MINUTE`）。
- **断った要求は数えない**（数えると断られ続けるあいだ窓が延び、永久に通れなくなる）。超過は 429 ＋ `Retry-After`（整数の秒数）。
- **掛ける対象は「外部へ費用を発生させる経路」**: プロキシの中継 2 本と `POST /evaluations`、それに `POST /guardrails/run`。評価は 1 要求でケース数ぶん（最大 400 回）の課金対象の呼び出しが走るので、掛けないと「中継の代わりに評価を回す」だけで保護を迂回できる。**掛け忘れは import の連鎖から導いて見張る**（上流を呼ぶモジュールへ到達するルートの非 GET は必ず指定を持つ）。手書きの一覧だと、上流を呼ぶルートを足した人が追記を忘れたぶんだけ検出網が静かに狭まる。
- **枠は共有の 1 つではなく、重さの理由ごとに分ける**（`RATE_LIMIT_TIER`）。回数だけを数える 1 つの枠では、**1 要求の重さが 2 桁違う経路に同じ上限を当てる**ことになり保護にならない（毎分 600 要求を許すと、評価の経路では上流呼び出し 24 万回ぶんを許すのと同じ）。
  - `standard`（中継 2 本）は共有の枠だけ。`fanOut`（`POST /evaluations`）は `FAN_OUT_ROUTE_RATE_LIMIT_PER_MINUTE` = 毎分 6 件、`outbound`（`POST /guardrails/run`）は `OUTBOUND_WAIT_ROUTE_RATE_LIMIT_PER_MINUTE` = 毎分 60 件を**追加で**消費する。
  - **「重い」をひとまとめにしない。** 守りたいものが違えば妥当な上限も違う: `fanOut` は**ベンダーへの課金**（1 要求で最大 400 回の上流呼び出し）、`outbound` は**外部の応答時間と DB 負荷**（上流 LLM は呼ばないので課金は増えない）。1 つに束ねた版は実際に `POST /guardrails/run` にとって不適切だった — この経路は**1 要求 1 エージェント**なので、エージェント 20 件のテナントの毎分の定期掃きは 20 要求になり、6 件で止まると**残りはその回は一度も判定されない**（backstop が静かに効かなくなる）。1 要求でテナントを一括判定する受け口を足すときに、この値は見直す。
  - **置き換えではなく「両方を消費する」。** 置き換えだと、重い経路と中継を交互に叩くだけで合計が共有の上限を超える（枠は「送信元ごと」で、「送信元とルートの組ごと」ではない）。
  - **数える前に全部の枠を覗き見する**（`SlidingWindowRateLimiter.inspect`）。順に `check` を呼ぶと、1 つ目が通って 2 つ目が断ったときに 1 つ目だけが呼び出しを数え、「断った要求は数えない」という約束が破れる（断られ続けるあいだ小さい枠が減り続ける）。断るときは待ち時間の長いほうを返す。覗き見は表に触らない（空の配列でも書き戻すと覗き見だけで表が膨らむ）。
  - **追加の枠は環境変数で上げ下げできない。** `fanOut` を上げたくなるのは「評価を連続で回したい」ときで、それは 1 要求のケース数を増やすか間隔を空ける側で解く（枠を広げると上の根拠がそのまま崩れる）。
  - 種類ごとの上限は**網羅的な表**（`EXTRA_FRAME_LIMIT`）が持つ。種類を足して書き忘れると型検査が落ちるので、「追加の枠を持たせるか」を必ず一度決めることになる。
  - 枠の種類はルートに載る印（`ROUTE_RATE_LIMIT_BRAND`）が**値として**持つ。真偽値だと、重い経路の指定を標準の枠へ落とす変更が検出網から見えない。
  - **追加の枠を持つルートは、枠を数える前に認可する**（`RouteOptions.requiredAction`）。レート制限は認証の後・本体の前に掛かるので、`route()` の側で認可しないと**権限の無い利用者がテナント全体の小さい枠を使い切れる** — view しか持たない利用者が `POST /evaluations` を 6 回投げると、どれも本体で 403 になるのに枠は消費され、同じテナントの operator / admin が窓のあいだ 429 になる。枠はベンダーへの課金を抑えるためのものなので、**上流へ 1 度も出ない要求で消費されるのは誤り**。宣言漏れは印（`ROUTE_REQUIRED_ACTION_BRAND`）から導いて落とす。**本体側の `requireAction` は残す**（`tenantId` と `user` を取り出すのに要るうえ、宣言を落としたときに認可が丸ごと消えないため）。残る範囲: 権限のある利用者が壊れた本文や他テナントの id で枠を減らすことは防げない（自分のテナントの枠なので許容する）。
- 掃除（期限切れの記録の回収）は**一定間隔**（窓の 1/60）で走らせる。「表が満杯のとき」だと山を越えた後に二度と走らず、「1 窓に 1 回」だと早い時点で使い切って回収が遅れる。
- **上限は環境変数（`PROXY_RATE_LIMIT_PER_MINUTE`）で上書きできる。** ベンチは 1 接続で毎秒数百件を出すので、既定（毎分 600 件）では計測トラフィックが弾かれる（実測で 3516 件のうち 3116 件が 429 になり、ベンチの門番が正しく「これは測りたいものを測っていない」と落とした）。レート制限は運用の方針で、測りたい「中継 1 件の追加遅延」の一部ではない（判定はインメモリの Map を 1 回引くだけ）。読めない値は既定へ倒す（fail-closed）。**上限そのものを上げる選択は採らなかった** — ベンチを通すには毎分 2 万件相当が必要で、それは保護として意味を持たない。

**インプロセスの Map なので水平スケールでは効きが落ちる**（インスタンスごとに別の枠になる）。共有ストアは宿題（下記）。

### 予算の強制（ADR-0007 の宿題 2）

中継の前に `Agent.budgetMicroUsd` と**当月（UTC）の累計コスト**を比べ、超過なら **403** ＋ 専用メッセージで断る。

- **中継してから断っても課金は発生する**ので、上流を呼ぶ前に確かめる。
- **予算が未設定（null）のエージェントでは問い合わせも起きない**（§8）。
- **ベンチは「予算を持つエージェント」で測る。** 未設定だと問い合わせが 1 つも起きないので、予算を入れたあとの中継を測ったことにならない（ルールを 1 件置くのと同じ理由）。実測では当月の集計を 1 回足して**追加遅延 p97.5 が 18ms**（上限 50ms）で、`windowTotals` を予算専用の `SUM` クエリに置き換える最適化は**採らなかった** — まだ余裕があり、§8 の「計測してから最適化する」に従って、必要になったときに測り直して決める。
- 比較は BigInt 同士。`>=` で断る（「上限まで使える」と「上限を超えたら止まる」の境界を上限ちょうどに置く）。
- **`Incident` は作らない。** `Incident.ruleId` が NOT NULL で、予算はルールではない。ガードレールのコストルールとは別物で、こちらは状態を変えずに要求を断るだけ（復帰の操作も要らない）。
- **確かめるのは中継だけではない。`POST /evaluations` も同じ関数を通す。** 評価の実行は同じエージェントの provider / model と同じ資格情報で上流を呼ぶので、中継だけを守ると「中継の代わりに評価を回す」だけで予算の強制を迂回できる（レート制限で迂回できたのとまったく同じ形）。
- **ただし評価そのものの支出は予算に積まれない。** 累計を数えるのは `UsageEvent` で、評価の呼び出しをそこへ書かないのは ADR-0009 の決定（利用者の呼び出しと混ぜると日次集計とコスト超過ルールが評価のたびに跳ねる）。つまり予算が効くのは「中継で使い切ったエージェントを評価に使わせない」ところまでで、評価の支出自体に上限は掛からない。**プラットフォーム側の支出台帳は宿題**（下記）。

## 理由

- 判定を「イベントの直後」に置くのは、受け入れ基準の 3 秒を cron 間隔に依存せず満たせる唯一の形だから。cron だけにすると最短でも間隔ぶん遅れ、間隔を縮めると空振りの集計が増える。
- ハッシュ連鎖に鍵を使うのは、「DB を触れる相手」を脅威モデルに入れているから。鍵なしのハッシュは内容の取り違えしか検出せず、書き換えたうえで作り直されたら気付けない。
- 重複排除をアダプタ（トランザクションの中）に置くのは、同時の判定で 2 行作られるのを型でも規約でも防げないから。
- レート制限と予算を同じ Step に入れたのは、どちらも「しきい値を超えたら断る」で、ガードレールの実装と同じ語彙・同じ層に収まるから（ADR-0007 がそう割り当てている）。

## 影響

- `AuditLog` に 3 列と一意制約、トリガ 2 つが増える（`prisma/migrations/20261002000000_add_audit_log_chain`）。**列を足す前に表が空であることを確かめて、空でなければ移行を止める** — `hash` は HMAC なので SQL では計算できず、仮の値で埋めるとその行は初日から「検証に失敗する行」になる。
- `Incident.triggeredAt` を `createdAt` に改名した（カーソルの共通規則が `(createdAt, id)` を位置として符号化する唯一の形なので、この表だけ別名にすると共有のページネーションを一般化することになる）。`prisma migrate diff` が出す DROP + ADD ではなく RENAME を手書きした（最終形は同じだが、既存行があれば発火日時を黙って捨てる形になる）。
- API が 9 本増える（`/guardrails` 4 本・`/guardrails/run`・`/incidents` 2 本・`/audit-logs` 2 本）。既存の 5 操作に 503 が宣言された（監査ログを書けないときに断るため）。
- `.env.example` に `AUDIT_HMAC_SECRET` ・ `NOTIFY_*` 3 本 ・ `PROXY_RATE_LIMIT_PER_MINUTE` が増える。**`docker-compose.yml` もこれらを素通しする** — 渡し忘れると Docker 配備でだけ監査ログが一切書けない（実測でそうなっていた）。渡し忘れは `.env.example` から導いて落とす。
- CI のゲートは `gate:step4` になり、ベンチが 4 本になる（所要時間が増える）。**ジョブ名は変えない**（branch protection の必須チェックを壊さないため）。
- `AUDIT_HMAC_SECRET` が**人の操作の前提条件**になった（未設定なら停止・復帰・解決・ルール変更が 503）。既存の配備では鍵の設定が必要。

## 残る宿題

- **テナント別の通知先**: いまは運用者が設定する 1 組だけ。テナントごとに宛先を持たせるなら、利用者由来の URL を受け取ることになるので **SSRF の防御（プライベート IP・メタデータの遮断、リダイレクト追跡先の検証）を先に足す**。Step5/6 の設定画面と一緒に入れる。
- ~~**発火済みルールの無効化 API**~~（この PR で実装した。`PATCH /guardrails/{ruleId}`）: 発火記録を持つルールは削除できない（`Incident.ruleId` の Restrict。`docs/spec.md` §3「削除の規則」が正本）ので、**しきい値を誤った `stop` ルールを止める手段が 1 つも無かった** — インシデントを解決してエージェントを復帰させても次の中継で同じルールが再び発火し、回復には DB の直接操作が必要だった。`enabled` だけを切り替える admin 限定の 1 本を足して閉じた。**しきい値や窓の変更は含めない** — 変えると「どの設定で発火したのか」が過去のインシデントから読めなくなるので、作り直し（削除 → 新規作成）で扱う。**無効化と再有効化は別の操作名で監査ログに残す**（記録を読むとき「外した」と「戻した」が区別できる必要がある）。**ルール数の上限は有効なルールだけを数える** — 無効化した行も数えると、上限ぶん発火したテナントは「消せない・止めても枠が空かない」でルールを 1 件も作れなくなる（memory と prisma の両方の契約テストが数え方を固定する）。 **代わりに行数の天井（`GUARDRAIL_RULE_ROWS_MAX_PER_TENANT` = 有効側の 4 倍）を別に掛ける** — 有効なルールだけを数えると総行数を縛るものが無くなり、「作る → 無効化する」の繰り返しで行が無制限に増える（§9 のリソース枯渇。上限を 1 つにしたままこの数え方へ変えたときに実際にそうなっていた）。**有効へ戻すときも有効側の上限を数え直す** — 数えないと「上限まで作る → 全部無効化する → また上限まで作る → 最初の分を有効へ戻す」で有効なルールが上限を超え、中継 1 回ごとの集計が行数の天井まで（＝上限の 4 倍まで）重くなる（実測。切り替えの Port に上限を渡していなかったのでアダプタ側では判定しようがなかった）。既に有効な行への再送はその数に入っているので数え直さない（冪等を壊さない）。2 つの上限は `GuardrailRuleLimits` として Port が受け取り、**省略可にしない**（既定値を持たせると新しい呼び出し側が渡し忘れたぶんだけ上限が静かに消える）。行数の天井に達したときは**別の文言**を返す（「不要なルールを削除してください」だけだと、有効なルールが 0 件なのに作れない利用者が何を消せばよいか分からない。消す対象は無効化した行の側）。
- **無効化中のインシデントの扱い**: ルールを無効化しても、そのルールが作った**開いているインシデントは開いたまま**（解決は別の操作）。ダッシュボード（Step5）で「もう無効なルールの未解決インシデント」をどう見せるかは、画面を作るときに決める。
- **時計のずれに対する広げ幅を窓の長さまでに縛った**: 遅れている DB の時計へ合わせて窓の開始を引き金の行まで広げる手当ては、縛らないと**遅れの幅がそのまま窓の長さになる**（90 秒の遅れで「1 分の窓」が 90 秒ぶんを集計し、上限を超えていないエージェントが 1.5 倍の合計で停止する。1 時間の遅れなら 60 倍）。しかも記録される文は「直近 1 分」なので、測ったものと記録が食い違う。広げるのは窓の長さまで（窓は最大 2 倍）とし、それを超える遅れでは引き金の行を取り込まない（その判定で取りこぼす代わりに、窓の長さは正しいまま）。
- **連鎖の検証にも枠を掛けた**（`heavyRead`、10/分）: 上流も外部も呼ばないが 1 回で最大 10,000 行を読んで同数の HMAC を計算し直す（一覧の上限の 50 倍）ので、枠が無いと admin のトークン 1 本で 1 万行の走査を好きなだけ並べられる。検証は「運用者が確かめる」「日次の cron が区間ごとに回す」操作なので、毎分 10 回で運用の都合には足りる（10 万行ぶんの区間を 1 分で確かめられる）。**重さの中身が違えば枠も分ける**という既存の方針（ベンダーへの課金 / 外部の応答時間 / DB の読み取りと CPU）に従った。
- **上流へ出ない拒否が重い経路の枠を消費する**: 枠を数えるのは認可の後・本体の前なので、本体が返す 403（予算超過）・404（id の打ち間違い）・503（judge の設定漏れ）でも `fanOut` / `outbound` の小さい枠（6/分）が減る。とくに 503 は 6 回で枯れて以降 429 に化けるため、**設定が誤っている理由が画面から読めなくなる**。`RouteOptions.requiredAction` と同じ形で「枠を数える前に確かめる前提条件」を一般化できるが、前提条件は経路ごとに違う（設定の有無・予算・対象の存在）ので、ルートの宣言にどう載せるかを決めてから入れる。Step5 のダッシュボードで「なぜ評価が動かないか」を見せるときに必要性が確かめられるので、そこで合わせて設計する。
- **レート制限の共有ストア**: インプロセスの Map なので、水平スケールするとインスタンス数ぶん上限が緩む。Step6（マルチテナント・課金）でデータストアを足すときに合わせて移す。
- **予算の判定が当月ぶんを毎回集計する**: `assertWithinBudget` は予算を設定したエージェントの中継ごとに「当月 (UTC) の `UsageEvent` の合計」を取る。索引 (`agentId`, `createdAt`) は効くが**走る行数は月が進むほど増える**ので、追加遅延が月末に向かって単調に伸びる（受け入れ基準は 50ms）。**ベンチでは検出できない** — `scripts/bench-proxy.ts` は `TRUNCATE` 後に約 10 秒ぶんだけ流すので、集計がほぼ空の表に対して走る。同じ形は窓の集計にもあるが、そちらは最長 7 日に縛られている。手当ては「転がり集計の表を持つ」か「当月の合計を短時間だけキャッシュする（無効化は自分の中継のみ）」で、どちらも Step6 の課金で日次・月次の集計を作るときに同じ材料が要る。**それまでは予算を設定したエージェントの中継が月末に遅くなりうることを承知で運用する**（止まるわけではない）。計測を先に足すなら、ベンチの仕込みに「当月ぶんの行を厚く積む」版を 1 本加えるのが最小。
- **プラットフォーム側の支出台帳**: 評価の呼び出し（judge とエージェント応答）は `UsageEvent` に入らない（ADR-0009）ので、**どの予算にも積まれない**。いま効いているのは「重い経路の小さい枠」と「予算を使い切ったエージェントは評価に使えない」の 2 つだけで、支出そのものの上限ではない。評価の支出を数えるには `UsageEvent` とは別の表（プラットフォームの運用費として、テナントの日次集計には出さないもの）が要る。Step6 の課金と一緒に設計する。それまでは**ベンダー側の月次利用上限（spend limit）が唯一の上限**で、`.env.example` にもそう書いてある。
- **予算超過の記録**: 403 で断るだけで、監査ログにも台帳にも残らない。超過しているあいだ中継ごとに起きるので、そのたびに追記すると発火と同じ記録の storm になる。**発火の重複排除と同じ仕組み**（「開いている超過」の概念）が要るので、Step5 のダッシュボードで「いま予算超過で止まっているエージェント」を見せる形と一緒に設計する。
- **状態変更と監査ログの原子性**: いまは「書ける状態かを先に確かめる」順序の手当てで、**追記そのものが DB 障害で落ちる窓は残る**（そのときは 503 を返し、状態だけが変わる）。1 つのトランザクションにまとめるには Port をまたぐ設計（`repos.transaction(...)` のような横断の仕組み）が要るので、別 ADR で扱う。
- **インシデントの発火回数・最終発火時刻**: 行は最初の発火を表すだけで、2 回目以降は通知と監査ログにしか残らない。`/incidents` の一覧から「いま何回目か・直近はいつか」が読めないので、列（`lastFiredAt` / `occurrences`）を足すかは Step5 のダッシュボードで必要性を確かめてから決める。
- **エラー率の最小サンプル数を設定可能にするか**: いまは定数（20 件）。窓の長さやトラフィック量によって適切な値は変わるが、ルールごとに持たせると列が増えるので、運用して「20 では早すぎる／遅すぎる」が出てから決める。
- **`notify` のルールが開いている間の中継経路**: 重複排除で何も書かないと分かっている呼び出しが、エージェント行の `FOR NO KEY UPDATE` を取って同じエージェントへの中継を直列化していた（窓のあいだ中継 1 回ごとに `raise` へ来るので、スループットが「DB の往復 1 回ぶん」に落ちる）。停止を伴わない判定に限り、開いている記録の先読みで早く返す（取り逃しはトランザクションの中の判定が吸収する）。
- **品質ルールの窓**: `windowMinutes` は種別を問わず必須で範囲検証もされるので、品質ルールも窓の中の実行だけを見る（`findLatestCompletedRun(tenantId, agentId, since)`）。全期間を見ていた版では、**ずっと前に 1 度だけ低い点だった**エージェントがその後 1 度も評価していないのに判定のたびに停止し、インシデントを解決して復帰させても次の判定で同じ古い実行を読んで再び止まった（ルールを無効にするまで抜け出せない）。窓の中に採点された実行が無ければスコアは `null` = 「測れていない」で発火しない。
- **品質ルールの差分判定**: いまは絶対値のしきい値だけ。「直前の実行から 0.1 下がったら」のような判定には列（比較の種類）と語彙が増えるので、ダッシュボードで品質の推移を見せるとき（Step5）に必要性を確かめてから決める。
- **連鎖の末尾の切り落とし**: 上記のとおりこの連鎖では検出できない。外部の錨（別システムへの定期的な書き出し）が要る。運用の要件が出たときに扱う。
- **cron からの明示実行**: `POST /guardrails/run` は用意したが、定期実行の仕組み（スケジューラ）は持っていない。中継と評価の直後に判定するので通常は不要で、必要になるのは「使われていないエージェントの窓が過ぎたこと」を検知したいときだけ。
