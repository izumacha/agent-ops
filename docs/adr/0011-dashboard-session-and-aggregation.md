# ADR-0011: ダッシュボードはセッション Cookie で認証し、画面・CSV・突合テストが同じ集計関数を通る

- **ステータス**: 採択
- **日付**: 2026-10-04

## 背景

Step5 の受け入れ基準は「Lighthouse Performance / Accessibility ≧ 90」「主要 5 画面の E2E 全 pass」「表示データと DB 集計の突合テスト一致 100%」（`docs/roadmap.md`）。UC-06「コストを日次で集計して閲覧する」の画面側がここで入る。

Step4 までで作ったのは REST API だけで、**このリポジトリに初めて UI が入る Step**。認証は Bearer トークン 2 種（ADR-0005）しかなく、`User` にパスワード列は無い。画面に必要なものは「ブラウザが毎回ヘッダを付けずに認証を保つ手段」と「画面に出す数値の出どころ」の 2 つ。

## 決定

### 1. ログインはユーザートークンの貼り付け、セッションはその値を入れた HttpOnly Cookie

画面でユーザートークン（`aop_u_…`）を貼り付け、サーバが照合できたら**その値をそのまま** `aop_session` Cookie に入れる（`HttpOnly` / `SameSite=Strict` / `Secure`（本番のみ）/ `Path=/` / 12 時間）。

- **照合は API と同じ `authenticateUserToken`**（`src/lib/api/auth.ts`）。ハッシュ照合・期限・失効・ユーザー無効化の規則を 2 つ持たない。
- スキーマ変更・パスワードのハッシュ化の自前実装・招待フローの改修が要らない。ADR-0005 が既に「Cookie はユーザートークンの上に**重ねる**（置き換えない）」と書いている方向そのもの。
- 失効は既存の `revokedAt` がそのまま効く（Cookie を消す必要がない）。

**ログインのレート制限は前段に委ねる**（ADR-0005「残る宿題」のまま）。`login` はこのアプリで唯一の未認証エンドポイントで、1 回あたり「ハッシュ化 ＋ トークン表の 1 行参照」を行う。アプリ側のレート制限（`src/lib/api/rate-limit.ts`）は**テナントをキーにする**ので、テナントが決まらないログインには掛けられず、ヘッダ由来の送信元をキーにするのは偽装できるため採らない（Step4 でその判断をしている）。共有ストアを前提にした全ルートのレート制限は Step6 の範囲。**README の「本番配備の前提」にも同じことを書いてある**ので、公開するときは前段で必ず掛ける。

**トレードオフ**: Cookie が盗まれた場合の影響はトークンが漏れた場合と同じ。`HttpOnly` なので JS からは読めず、`SameSite=Strict` で他サイトからの送信も止まるが、**不透明なセッション ID へ移す**（別テーブルでセッションを管理し、Cookie には ID だけを入れる）ほうが本来は安全。Step5 のスコープを認証基盤へ広げないため採らず、**宿題として残す**。

### 2. CSRF はセッションから導いた同期トークン ＋ Origin の照合（2 枚重ね）

§9 は「`SameSite` クッキーは CSRF トークンを置き換えるものではなく、多層防御として併用する」と明示している。そこで書き込み（停止 / 復帰 / 解決）は 2 つを要求する。

1. **同期トークン**: `HMAC-SHA256(鍵 = セッショントークン, メッセージ = 固定ラベル)` を base64url にした値をフォームの hidden 項目に置き、サーバで同じ計算をして定数時間で比べる。
2. **Origin の照合**: `Origin` ヘッダのホストが `Host` と一致すること。**`Origin` が無い要求は拒否**（fail-closed）。

**2 枚目の Cookie を発行しない**のが要点で、理由は技術的な制約: **Next.js は Server Component のレンダリング中に Cookie を書けない**ので、「ページを描くときに乱数を作って Cookie へ置く」形が成立しない。proxy で発行する手もあるが、入口の不変条件（本文のバッファ・percent-decode の扱い）に手を入れることになる。導出なら新しい環境変数も要らず、インスタンスを増やしても再起動しても同じ値になり、セッションが変わればトークンも変わる。HMAC は一方向なので CSRF トークンが漏れてもセッショントークンは復元できない。

**空のセッションを先に弾く**（`csrfTokenMatches` の 1 行目）。弾かないと「鍵が空の HMAC」という誰でも計算できる値が正解になる。

**配備の前提**: Origin の照合は `Host` ヘッダと突き合わせ、**`X-Forwarded-Host` は見ない**。前段にリバースプロキシを置く場合はブラウザが送った `Host` をそのまま転送する必要がある（nginx の `proxy_pass` は既定で上流のアドレスへ書き換えるので `proxy_set_header Host $host;` が要る）。転送しないと書き込みがすべて拒否される — fail-closed なので安全側だが、画面には「要求を受け付けられませんでした」としか出ず原因が読めないので、README の運用手順に明記した。転送ヘッダを信頼する形にしないのは、`X-Forwarded-Host` は前段が付け替えない限り要求元が自由に名乗れるため（信頼できる前段がある配備でだけ意味を持つ設定を既定にしない）。

### 3. 画面のデータ取得は Server Component から data 層を直接読む

自分の REST API を HTTP で呼ばない（認証の二重化と往復のコストを避ける）。`tenantId` は Cookie の主体から取り出して `where` に必ず差し込む（ADR-0002）。書き込みは Server Action で、冒頭で既存の `requireAction` / `requireAdminRole` を呼ぶ。

### 4. 画面・CSV・突合テストは同じ `loadDashboardSummary` を通る（受け入れ基準 3）

数値の出どころを 1 つにして、画面で足し算も割り算もしない（日ごとの稼働率も `uptimeRate` を呼ぶ）。CSV のダウンロードも同じ関数から作るので、「表の合計と CSV の合計が違う」形が生まれない。突合テストは**テストが投入した行から独立に数え直した値**と比べる（同じ関数で期待値を作らない）。

**稼働率の定義**: 期間内の `UsageEvent` のうち `statusCode < 400` の割合。**呼び出し 0 件の期間は `null`**（0% と読まない）。しきい値の床はガードレールと同じ定数（`USAGE_ERROR_STATUS_FLOOR`）を共有する。

### 5. 1 つの Server Action で複数の操作を受ける（`intent` 項目）

停止と復帰を別の Server Action にすると、押した直後にボタンが入れ替わる場面で `useActionState` の状態が捨てられ、「停止しました。」が一度も見えないまま状態だけが変わる（実測）。そこで**関数は 1 つ**にし、どちらの操作かはフォームの `intent` 項目で受け取って**表と突き合わせる**（知らない値は断る）。状態の綴り（`stopped` / `active`）を直接送らせないのは、`suspended` を人が指定できる形を作らないため。

**一覧から行が消える操作（インシデントの解決）は別の形**にする。成功すると行ごとフォームが消えるので、`useActionState` の状態に入れた文言も消える。成功時だけクエリの印を付けて同じ画面へリダイレクトし（POST → リダイレクト → GET）、サーバ側で文言を描く。

### 6. Lighthouse はデスクトップのプリセットで、1 画面あたり 3 回測って中央値を見る

- **デスクトップ**: 既定はモバイル（4G 相当の回線 + CPU 4 倍の絞り込み）。運用者が PC で開く社内の管理画面を測る条件としては実態に合わないので、Lighthouse 公式の `desktop-config` を使う。絞り込みの数値を自分で並べない（測定の前提が写しになって古くなる）。
  - 参考（実測・同じコミット）: 既定のモバイル条件では Performance が 85〜90 に落ちる。Accessibility は条件に依らず 100。
- **3 回の中央値**: 1 回の計測では同じコミット・同じ機械で Performance が 81〜98 の幅で揺れた（実測）。Lighthouse 自身も複数回の中央値を勧めている。**奇数回**にするのは、偶数だと中央値が 2 つの平均になって外れ値が半分だけ混ざるため。
- **測る相手は本番ビルド**（`.next/standalone/server.js`）。dev サーバーは毎回その場で変換するので Performance が実態より悪く出る。**静的ファイル（`.next/static`）を standalone へ配ってから測る** — 配らないと CSS も JS も 404 になり、スタイルの無い HTML を測ることになる（実測で、配る前は target-size の判定が CSS 適用後の寸法を見ていなかった）。
- 実測（この PR 時点・デスクトップ・3 回の中央値）: 5 画面すべてで Performance 100 / Accessibility 100。

### 7. 主要 5 画面の一覧は 1 か所で宣言する

`scripts/lib/step5-criteria.mjs` の `STEP5_SCREENS` が唯一の宣言で、**E2E のテスト名・Lighthouse の計測対象・スクリーンショットのファイル名**がすべてここから導かれる。別々に並べると「E2E はあるのに Lighthouse では測っていない画面」が静かに生まれる。CLAUDE.md §3 が宣言しているスクショ 5 枚と同じ 5 画面にそろえてある。

### 8. 合否の判定は測る側に持たせない

E2E と Lighthouse は「測って結果を出す」だけにして、合否は `scripts/gate-step5.mjs` が判定する（ベンチと同じ分担）。判定を測る側に置くと「測れていないのに合格」を測る側だけで作れてしまう。ゲートは終了コードだけでなく**出力の中身**も見る（スイートを空にする形・画面 1 つ分を消す形・合格点を書き換える形はいずれも終了コードに現れない）。

## 影響

- `src/lib/session.ts` / `session-server.ts` / `csrf.ts` が増える。`next/headers` に触るのは `session-server.ts` だけ。
- `DailyUsageTotal` に `errorRequests` が増える（稼働率の分子）。`GET /usage/daily` の応答にも項目が増える（追加なので後方互換）。
- 画面の Server Action は API と同じ監査ログの操作名を使う（`src/domain/agent-status.ts` の表を共有）。
- devDependency に `@playwright/test` と `lighthouse` が増える。CI の gate ジョブは chromium を入れる 1 ステップが増える。
- `npm audit` の `--omit=dev` は変えない（ADR-0004 の理由のまま）。Lighthouse の依存には修正版の無い high 勧告があり、**本番依存には入らない**。

## 却下した案

- **不透明なセッション ID（別テーブル）**: 本来はこちらが安全だが、Step5 のスコープを認証基盤へ広げることになる。宿題として残す。
- **画面から自分の REST API を HTTP で呼ぶ**: 認証を 2 回行うことになり、往復のコストも増える。data 層を直接読めば ADR-0006 の Port がそのまま使える。
- **二重送信 Cookie 方式の CSRF**: Server Component では Cookie を書けないので、発行の置き場が proxy しか無くなる（入口の不変条件に手を入れたくない）。
- **Lighthouse CI（`@lhci/cli`）**: 設定ファイルと成果物の置き場が増える。`lighthouse` を直接呼べば、合格点の判定をゲート側の既存の形（出力の JSON を読む）に寄せられる。
- **E2E を vitest で書く**: Lighthouse のためにブラウザは要るので、E2E も同じブラウザで動かすほうが道具が増えない。
