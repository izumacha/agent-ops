# ADR-0012: プラン別の上限は網羅的な表から引き、課金は SDK 無しの受信 Webhook 1 本に絞る

- **ステータス**: 採択
- **日付**: 2026-10-06

## 背景

Step6 の成果物は「Stripe 連携（Free/Pro/Enterprise）、機能ゲート、レート制限、テナント分離」で、受け入れ基準は 4 つ（`docs/roadmap.md`）: ①テナント越境アクセステスト**全パターン**で拒否 ②Webhook **冪等性**テスト pass ③契約テスト（別 DB）が CI で緑 ④**全体カバレッジ ≧ 80%**。UC-10「プランを契約し機能ゲートを解除する」がここで入る。

Step0 から `Plan` enum と `Tenant.plan` 列はあったが、**どこからも読まれていなかった**（アダプタの型だけ）。上限はすべて固定値（エージェント数・プロキシの枠・ガードレールのルール数）で、プランの違いは 1 つも無く、課金の受け口も無い。③は Step1 から CI の `migrate-and-build` ジョブで満たしているので、この Step で新しく作るのは ①②④ と「プランが実際に効く」ことの全体である。

## 決定

### 1. プラン別の上限と可否の正本は `src/domain/plan.ts` の `PLAN_LIMITS`

`Readonly<Record<Plan, PlanLimits>>` の**網羅的な表**1 つに全プランの値を置き、判定はその表を読む純粋関数（`planLimitsFor` / `planAllows` / `guardrailRuleLimitsFor`）だけが行う。`src/domain/rbac.ts` の `PERMISSIONS` / `canPerform` と同じ流儀で、**プランを足すと型がキー不足で落ちる**ので埋め忘れが起きない。

**軸は 3 つに絞った**（ユーザーと確認した範囲）: エージェント数の上限・プロキシのレート制限の枠・機能そのものの可否。**テナントの月次コスト上限は入れていない** — 予算は既に `Agent.budgetMicroUsd` がエージェント単位で持っており、テナント単位の上限はプランの軸ではなく「課金プラン × 予算」の掛け算になる（ADR-0010 の宿題「プラットフォーム側の支出台帳」と同じ材料が要る）。

**可否で分けるのは 2 つだけ**: 監査ログの改ざん検証（`GET /audit-logs/verify`。1 回で最大 1 万行を読んで同数の HMAC を計算し直す最重量の読み取り）と、ガードレールのルール数（こちらは数の上限）。**「安い側ではまるごと使わせない」もの以外は数で表す** — 可否の表に入れるたびにルートへ `requiredPlanFeature` の宣言が 1 つ要るので、数で足りるものを可否にすると宣言が増えるだけで何も守れない。

**判定は不明なら厳しい側へ倒す（fail-closed）。** ただし倒し方は 2 種類に分けた。

- `planAllows` は **false**（未知のプランは何も使えない）。
- `planLimitsFor` は **`FALLBACK_PLAN`（= free）の上限**を返してサーバログに 1 行残す。**throw にしない** — ここで落とすと「DB に enum 外の値が 1 行ある」だけで**そのテナントの全 API が 500** になる。§9 が求めるのは「クラッシュではなく機能を縮退して継続」なので、最も厳しい上限で続ける側を選んだ。

`FALLBACK_PLAN` が**どの次元でも最も厳しい**ことは `tests/plan.test.ts` が機械的に固定する（プランを足したときにこの前提が崩れたら落ちる）。表の添字は `Object.hasOwn` で確かめる — 素の添字だと `constructor` のようなプロトタイプ由来の名前が Object の値を返し、上限の比較が TypeError になる（`canPerform` で同じ手当てをしている）。

**pro の値は Step4 までの固定値をそのまま引き継いだ**（`proxyRateLimitPerMinute` = 600・`maxEnabledGuardrailRules` = 50）。プラン別にしたことで**既定が緩くなった利用者は 1 人もいない** — free は絞り、pro は据え置き、enterprise だけ広げる。あわせて重複していた定数 2 つ（`PROXY_RATE_LIMIT_PER_MINUTE` の既定値・ガードレールの 2 つの上限）を消し、根拠のコメントを表の側へ移した（§6 の一元管理。写しが残ると「どちらが効いているのか」が読めなくなる）。

**行数の天井は表に持たせず導出する**（`GUARDRAIL_RULE_ROWS_FACTOR` = 4。Step4 と同じ係数）。2 つの値が独立に動くと「有効側より小さい天井」のような成立しない組み合わせを書けてしまう。

### 2. プランは認証時に Principal へ載せる

`UserPrincipal` / `AgentPrincipal` に `plan: Plan` を持たせ、トークン・API キーを引く既存のクエリへ `tenant: { select: { plan: true } }` を足して取る。**DB の往復は増えない**（受け入れ基準「中継の追加遅延 ≦ 50ms」に影響しない）。`PlatformPrincipal` は対象外 — プラットフォーム管理者はテナント境界の外側にいるのでプランを持たない（`requirePlanFeature` はテナントのユーザーであることを先に要求する）。

**memory アダプタでも「テナント行が無ければ認証しない」に揃えた。** 以前は API キーの照合でテナントを引いていなかったので、prisma 側だけが「テナントが消えた API キーは 401」になっていた（ADR-0006 の構造的な死角そのもの）。あわせて `PrismaAgents.create` が「テナントが無い」を `too_many_agents` に写していた誤りも直した（上限の超過と存在しないテナントは別の失敗）。

### 3. 機能ゲートは `route()` の宣言で、レート制限より**前**に置く

`RouteOptions.requiredPlanFeature` を足し、パイプラインの順序は **認証 → 認可（`requiredAction` / `requiredRole`）→ 機能ゲート → レート制限 → 本文 → 本体**。

**順序には理由がある**: 使えないプランの要求で枠を消費させない。実測で、ゲートをレート制限の**後ろ**へ動かす変異は**1551 件すべて緑**のまま通った（断られた要求が枠を減らすので、free のテナントは 10 回叩くと以降 1 分間 429 になり、403 の理由が読めなくなる）。いまは `プランで断った要求はレート制限の枠を消費しない` が `sharedRateLimiter().trackedKeys === 0` まで見る。

宣言漏れは `tests/route-wrapping.test.ts` が**印**（`ROUTE_REQUIRED_PLAN_FEATURE_BRAND`）から導いて落とす。**本体側でも `requirePlanFeature` を呼ぶ**（`route()` の宣言を落としたときに静かに開かないための fail-closed。既存の `requireProxyAgent` と同じ二重化）。

### 4. 件数の上限はアダプタが挿入と同じ原子的操作の中で数える

`repos.agents.create(input, limits)` の形（既存の `GuardrailRuleLimits` と同じ）で、**上限は省略可にしない**。API 層で count → create に分けると 2 本同時の登録で上限を超える。prisma アダプタは `$transaction` の中でテナント行を `SELECT … FOR NO KEY UPDATE` して同一テナントの登録を直列化する（最後の admin の判定・トークン発行と同じ形）。**ロックの存在は契約テストが決定的に固定する** — 別トランザクションで同じテナント行を掴んだまま登録を始め、待たされることを見る（並行要求を 2 本投げるだけのテストは実際には直列に流れるので、ロック句を落としても緑のまま通る）。

**数え方は memory にも写す**（ADR-0006 の死角を閉じる唯一の形。`tests/data/memory-agents.test.ts` と契約テストに同じ期待を 2 か所）。

**超過の文言に数値を書かない。** プラン別になったので「最大 25 件」と書けない（書くと free の利用者に嘘を見せる）。代わりに `GET /billing` で現在の上限を引けるようにした。

### 5. Stripe の SDK を入れず、署名検証を自前で書く

`stripe` パッケージを依存に足さない。検証は `node:crypto` の HMAC-SHA256 と `timingSafeEqual` だけで書ける（`Stripe-Signature: t=…,v1=…` を解析し、`` `${t}.${生の本文}` `` の HMAC を比べる）。

- 依存ゼロなので `npm audit` / Dependabot / 「API バージョンを SDK から導く」といった規約が増えない（別リポジトリでは SDK の `apiVersion` の扱いだけで検出網が 8 本に育っている）。
- 送信側の署名付き Webhook（`src/lib/notify/send.ts`）と定数時間比較（`src/lib/tokens.ts` の `secretsEqual`）が既にあるので、同じ流儀で書ける。
- **リプレイを防ぐため時刻の許容幅を持つ**（`BILLING_SIGNATURE_TOLERANCE_SECONDS` = 300 秒）。鍵は `STRIPE_WEBHOOK_SECRET`（32 文字以上。未設定・短すぎは **503**。検証を飛ばして受け入れることはしない）。
- **形が違う・時刻が古い・一致しない のどれでも同じ 401**（理由を区別して返すと総当たりの手がかりになる）。

**代償を明記する**: 事業者のイベントの形（`data.object.customer` / `items.data[0].price.lookup_key`）を自前の Zod スキーマで読むので、Stripe が形を変えたときに型が教えてくれない。そこで**知らない形は「反映しない」側へ倒し、契約の変更イベント（`BILLING_EVENT_EFFECT` の表にある種別）なのにプランを決められなかったときだけサーバログに残す**（「払っているのに反映されない」状態を運用者に見せる）。

**定数時間比較は検出網で守れない境界。** `timingSafeEqual` を素の `===` に差し替える変異は**全テストが緑のまま通った**（比較の結果は同じなので、観測できるのは実行時間だけ）。二次的な網として `tests/route-wrapping.test.ts` の「秘密の生成と比較」が綴りを見張るが、**これは証明ではない**（1 段の間接化で崩れる）。本当の担保は規約とレビューで、`src/lib/tokens.ts` の `secretsEqual` を使う・比較を自分で書かない、を守る。

### 6. Webhook の冪等性は DB の一意制約で表す

`BillingEvent` に `@@unique([provider, eventId])` を置き、`repos.billingEvents.recordOnce(input)` が一意制約違反を `'duplicate'` に翻訳する（`DuplicateError` → 422 にはしない。**冪等な再送は正常系**で、2 通目は何もせず 200）。

**「処理済みか先に SELECT してから INSERT」にしない。** 同時に届いた 2 通で両方が通る。この違いは**同時性のテストでしか見えない**ので、`冪等性: ` の群に「同じイベントを並行して投げても反映は 1 回」を入れてある（逐次の再送テストだけでは SELECT 版も緑になる）。

**記録は「反映できなかった」場合も残す** — 知らない顧客 ID・知らない価格でも受信した事実を 1 行書く。残さないと、設定の取り違えで届き続ける再送を何度でも処理してしまい、しかも運用者からは何も見えない。

**順序の誤りを 1 つ直した（本物のバグ）**: 初版は受信を記録してから `assertAuditConfigured()` を呼んでいた。監査の鍵が無い配備では「1 通目を記録 → 503 → 事業者が再送 → 2 通目は `duplicate` で 200」となり、**そのイベントは永久に反映されない**（しかも事業者側は成功と見る）。いまは記録の**前**に確かめ、鍵が無ければ 1 行も書かずに 503 を返して再送でやり直させる。**残る境界**: 記録の後・反映の途中で落ちた場合は、次の `customer.subscription.updated` を受けるまで直らない（Stripe は現在の状態を周期的に送るので実運用では自然に収束するが、保証ではない）。

### 7. Webhook は `route()` を通らない唯一の API — `auth: 'none'` は採らなかった

この経路を呼ぶのは事業者であって利用者ではないので Bearer 認証が無い。`RouteOptions` に `auth: 'none'` を足す形は**採らなかった** — 既定を 1 つ緩めると、**どのルートも宣言 1 行で未認証にできる口**になる（§9 の最小公開）。代わりに CSV の画面側ルート（`SESSION_PAGE_ROUTES`）と同じく、`tests/route-wrapping.test.ts` の理由付きの表 `SIGNED_WEBHOOK_ROUTES` へ登録し、**代わりに機械で要求する**: 署名検証のモジュールへ到達していること・`no-store` を宣言していること。素の除外にすると、署名検証を忘れたルートを同じ場所へ足せる。

**レート制限は掛けられない**（テナントが決まらないので枠のキーが無い。ログインと同じ理由で前段に委ねる）。代わりに本文サイズ・深さの共通の上限（`readJsonBody` 系）と「知らない種別は 200 で捨てる」で守る。

### 8. プラン変更の経路は 2 本だけで、どちらも監査ログに残す

Stripe の Webhook と、プラットフォーム管理者の `PATCH /tenants/{tenantId}`。**テナント内の admin はプランを変えられない** — 課金の実体は事業者側にあるので、アプリ側で勝手に上げられると請求と権限が食い違う。管理者の経路は運用の手当て（移行・障害時の暫定対応・事業者を介さない契約）のために残す。

反映と記録は `src/lib/billing/apply-plan.ts` の `applyPlanChange` 1 か所に集め、`tenant.plan_changed` を監査ログへ書く（`actorId` は Webhook 由来なら `null`、payload の `source` が `billing_webhook` / `platform_admin` を示す）。**プランは上限と機能の可否を決めるので、「いつ何が変わったか」が辿れないと後から 409 / 403 の原因を説明できない。** 人の操作の側は Step4 の規則どおり**変える前に** `assertAuditConfigured()` を呼ぶ。

### 9. カバレッジは「ロジック層」で測る（基準④の解釈）

`vitest.config.mts` の `coverage.include` は `src/domain` / `src/lib` / `src/data` / `src/app/api` の 4 つで、定義の正本は `scripts/lib/step6-criteria.mjs`（ゲートと設定が同じ定義を読む）。**判定はしきい値を vitest に書かず、ゲートが `coverage-summary.json` を読んで行う**（ベンチ・Lighthouse と同じ分担。判定を測る側に持たせると「測れていないのに合格」を測る側だけで作れる）。

除外とその理由:

- **画面の `.tsx`** — 主要 5 画面の E2E と Lighthouse が担保している（Step5 の受け入れ基準）。入れると「画面の行数で全体の％が決まる」状態になり、ロジックのカバレッジが下がっても総計が動かない。
- **生成物（`src/generated/**`）・型だけのファイル（`src/types/**`）・Port の契約（`src/data/ports/**`）** — 実行されるコードが無い（Port の実装は adapters 側で測る）。
- **prisma の結線とアダプタ（`src/lib/prisma.ts` / `src/lib/prisma-client.ts` / `src/data/adapters/prisma/**`）** — この計測は `npm run test`（DB 不要）の経路で走るので原理的に 0% になる。含めると「測れないものを 0% として数える」ことになり、総計がロジック層の実態を表さない（実測で functions が 78.5%、除くと 82% 台）。**これらの正しさは受け入れ基準③（契約テストが別 DB で CI で緑）が担保する** — 同じ対象を 2 つの指標で数えない。

**契約テストをカバレッジの実行に混ぜる案は採らなかった**: 共有 DB を `TRUNCATE` するので直列実行（`--no-file-parallelism`）が要り、ユニットと同じ実行に混ぜると全テストが直列になる（CI の所要時間が数倍になる）。

**判定は 4 指標すべて**（statements / branches / functions / lines）に掛ける。1 つだけを見る形にすると、通る指標を選んで基準を満たしたように見せられる。**読めなければ落とす**（「測れていないから緑」に倒さない）。実測値は 96.5 / 92.6 / 98.5 / 97.9%（下限 80%）。

### 10. 越境アクセスの「全パターン」は OpenAPI から導く（基準①の解釈）

`tests/api/tenant-isolation.test.ts` が、契約（`openapi/openapi.yaml`）の中で**テナントの資源を指すパスパラメータを持つ全オペレーション**を列挙し、表 `CROSS_TENANT_CASES`（17 件）と**双方向**で突き合わせる（契約にあるのに表に無い／表にあるのに契約に無い、のどちらでも落ちる）。除外は理由付きの表 `CROSS_TENANT_EXEMPT` に 1 件だけ（`PATCH /tenants/{tenantId}` はプラットフォーム管理者専用で、テナント境界の中の操作ではない）。

**ゲートは群（`越境: ` の接頭辞）とは別に、この導出の照合そのものを要求する** — 群の件数だけを見ると、表から 1 件消す変異は**要求も一緒に縮む**ので素通りする（「流れたものから期待を導く」形。このリポジトリが繰り返し避けてきた）。群の件数の下限（17）は「群がまるごと消えたら気付く」ための床で、正確な網羅は導出のテストが持つ。

## 影響

- プランを読む場所が 1 つ増えた（認証）。**上限を読む場所は増えていない** — 固定値だった定数を表から引く形に置き換えただけで、呼び出し側の数は変わらない。
- 既存の配備は `pro` 相当（上限が据え置き）。`free` のテナントを作ると監査ログの改ざん検証が 403 になる。
- Webhook の受信には `STRIPE_WEBHOOK_SECRET` が要る（未設定なら 503。他の API には影響しない）。
- `GET /billing` が増えたので、409 / 403 を受けた利用者が現在の上限を参照できる。

## 代替案

- **Stripe SDK を使う** — 署名検証と型が手に入るが、依存とその更新の規約が増える（API バージョンの固定・major 更新の判断）。検証に要るのは HMAC 1 本なので、SDK の価値は Checkout を実装するときに再評価する。
- **プランの上限を DB に持つ（テナントごとに上書き可能にする）** — 柔軟だが、上限が行ごとに違うと「どの値で断られたか」が再現できず、テストも表から導けない。例外的な契約は enterprise の値を上げる形で扱う。
- **機能ゲートを本体の中だけで行う** — 宣言が無いと「掛け忘れ」を機械で落とせない（レート制限で同じ問題を既に経験している）。
- **カバレッジのしきい値を vitest の `thresholds` に書く** — 測る側が合否を決める形になり、「測れていないのに合格」を測る側だけで作れる（ベンチで実測した失敗と同じ）。

## 残る宿題

- **Checkout セッションの作成**: いまは受信と参照だけで、プランを上げる操作はアプリから出せない（事業者の画面で契約する前提）。外向きの通信が増えるので、SSRF の規約（`src/lib/outbound-url.ts`）と秘密鍵（`STRIPE_SECRET_KEY`）の扱いを決めてから足す。
- **レート制限の共有ストア（ADR-0010 の宿題の据え置き）**: インプロセスの Map のままなので、水平スケールするとインスタンス数ぶん上限が緩む。**この Step では枠の値をプラン別にしただけで、置き場所は変えていない** — 共有ストア（Redis 等）を足すと「ストアが落ちたら通すのか断るのか」という fail-open / fail-closed の判断と、依存の運用が増える。Step7 のデプロイ設定（Vercel/Supabase 向け）で「どのインスタンス構成で動かすか」が決まってから移す。それまでは**単一インスタンス前提**で、プラン別の枠は「壊れたクライアントの暴走を止める」ところまでを守る。
- **テナント単位の月次コスト上限**: プランの軸に入れていない（上記 1）。予算はエージェント単位のままで、テナント全体の上限は ADR-0010 の宿題「プラットフォーム側の支出台帳」と同じ材料が要る。
- **プラン変更時に既存の資源が上限を超える場合**: 下位プランへ落ちたとき、既にあるエージェントやルールは**そのまま残る**（新規登録だけが 409 になる）。超過分を自動で止める／読み取り専用にする、といった扱いは運用の要件が出てから決める。**いまは「落としても既存の運用は壊れないが、増やせない」**。
- **事業者側の状態との突き合わせ**: Webhook を取りこぼした場合（エンドポイントが無効化された等）に備えた照合（定期的に事業者へ現在の契約を問い合わせる）は無い。外向きの通信が要るので Checkout と同じタイミングで足す。
- **`BillingEvent` の保持期間**: 受信記録は増え続ける（冪等性の判定に使うので消せない）。古い行を落とすなら「事業者の再送が止まる期間」を調べてから決める。
