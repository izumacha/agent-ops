# ADR-0013: リリース準備の 4 基準は「2 経路で同じ上限を見る」「既知バグは文書とソースの印の 2 つで数える」で機械化する

- **ステータス**: 採択
- **日付**: 2026-10-07

## 背景

Step7（最後の Step）の成果物は「Vercel/Supabase 向けデプロイ設定、README と API docs、デモシード、負荷試験レポート」で、受け入れ基準は 4 つ（`docs/roadmap.md`）:

1. クリーン環境で `docker compose up` → **5 分以内にデモ動作**
2. **同時 100 リクエストでエラー率 < 1%**
3. `npm run build` 成功
4. **既知バグ 0（Issue 管理）**

Step0〜6 の基準はすべて「テストの名前」「ベンチの数値」「カバレッジの％」のように**リポジトリの中で測れるもの**だった。Step7 の 4 つはそこが違う:

- ① は **Docker デーモンを要求する**。この開発環境には無く（`/var/run/docker.sock` が存在しない）、ゲートは開発機でも回る必要がある（ゲート運用ルール 1〜3 の前提）。
- ② は「同時 100」という**同時性**を要求する。既存のベンチはどれも逐次か単発で、同時実行の圧力を掛ける仕掛けが無い。
- ④ は **「Issue 管理」という外部サービスの状態**を指している。ゲートはネットワークに出られないし、出られても権限が要る。
- ③ だけは既存のゲートが既に流している（`npm run build`）。

**基準をそのまま読むと機械化できない項目がある**ので、ゲート運用ルール 4（「基準を緩める変更はロードマップと ADR を同じ PR で更新する」）に従い、解釈をここと `docs/roadmap.md` に書く。

## 決定

### 1. 基準①は「同じ上限を 2 つの経路で見る」形にする

| 経路 | 時間の起点 | 含むもの | いつ走るか |
| ---- | ---------- | -------- | ---------- |
| CI の `docker-smoke` ジョブ | `docker compose up -d --build` | イメージのビルド・マイグレーション適用・起動・デモの筋 | PR / push ごと |
| `npm run bench:demo-ready` | 本番ビルド（`.next/standalone`）の起動 | 起動・デモの筋 | **ゲートが毎回** |

**上限は 1 つ**（`scripts/lib/step7-criteria.mjs` の `DEMO_READY_MAX_MS`）で、どちらの経路もそこから読む。後者は前者の**部分集合**なので必ず速く、「ゲートが緑でも CI が赤」はありうる（逆は無い）。

**なぜ分けたか**: ゲートを Docker 必須にすると、Docker の無い機械で**ゲートそのものが回らなくなる**。そうなると「ゲートが緑になってから次へ進む」という運用（ゲート運用ルール 3）が成立せず、最後には「ゲートを飛ばす」運用に倒れる。一方、CI 側だけに置くと**ゲートの一覧から基準①が消える**（ゲートの出力を読んでも基準①を見たことが分からない）。両方に置いて同じ上限を読ませるのが、どちらも失わない形。

**「デモ動作」の中身は 1 か所で宣言する** — `scripts/lib/demo-flow.mjs` の `DEMO_STEPS`（健康確認 → テナント作成 → エージェント登録 → 一覧 → 契約プランの参照 → **停止** → 監査ログの参照 の 7 段）と、それを通す `runDemoFlow`。**ベンチと CI のプローブが同じ関数を呼ぶ**ので、「ゲートが測るデモ」と「CI が測るデモ」がずれない。

**停止を筋に入れているのは監査ログの段を意味のあるものにするため。** 記録を残す操作を 1 つもしないまま `GET /audit-logs` を叩くと、空の一覧に 200 が返るだけで「運用の記録が残る配備であること」を何も示さない（記録の書き込みが完全に壊れていても通る）。そこで停止（`POST /agents/{id}/stop`。`assertAuditConfigured()` を通る数少ない経路の 1 つ）を踏み、**監査ログに 1 行以上残ったこと**まで判定する。これは「`agentsListed` を足したのと同じ理由」で、配備の鍵（`AUDIT_HMAC_SECRET`）を渡し忘れた形もここで落ちる（鍵は呼び出し側が使い捨てを作って `startDemoApp` へ渡し、**省略可にしない**）。

**段の数も判定する。** 時間だけを見ると、段を削った計測が「デモが動いた」として通る（極端には health だけを叩けば必ず合格する）。そこで *(a)* `DEMO_STEPS` の件数が受け入れ基準の `DEMO_STEP_COUNT` と一致すること、*(b)* 宣言した段を全部通ったこと、*(c)* 登録したエージェントが**一覧に出た**こと（201 が返っただけでは、別テナントへ書いていても通る）を、所要時間と同じ重みで判定する。

**(a) と (b) は別の判定に分ける** — 1 本にまとめると「基準を 1 つだけ破る」形が書けず、`tests/gate-scripts.test.ts` の表（基準ごとに 1 つだけ破って 1 件返ることを確かめる）が成立しない。(a) は宣言と基準の一致、(b) は「足りないか」だけを見る。

**仕込みは HTTP だけで行う**（DB へ直接書かない）。CI の経路ではコンテナの中へ入れないし、何より**配備した成果物で動くか**を測るのが基準の趣旨。入口はプラットフォーム管理者トークンでの `POST /tenants` で、応答に最初の admin のトークンが入るので以後はそれで進める（事業者もユーザーも居ない状態からの唯一の入口）。

### 2. 基準②は「レート制限の無い読み取り」を同時 100 で叩く

`npm run bench:concurrency` が、デモの筋で用意したテナントに対して `GET /api/v1/agents` を autocannon で同時 100 接続・10 秒叩く。

**経路の選び方が判断の中心。** レート制限のあるルート（中継 2 本・評価の実行・ガードレールの明示実行・連鎖の検証）を選ぶと、同時 100 で 429 が返るのが**正しい挙動**なので「エラー率 < 1%」を測れない。枠を環境変数で広げれば測れるが、それは**本番と違う設定を測る**ことになる。上流 LLM を呼ぶ経路も選ばない（実キーと課金が要る）。残るのは「認証とテナント境界つきのクエリを通る、枠の無い読み取り」で、`GET /api/v1/agents` がその代表。

**失敗は 2xx 以外 ＋ 応答が返らなかった要求の合計で数える。** `non2xx` だけを見ると「接続を切られた分」が無かったことになる。**ただし `timeouts` を足し合わせない** — autocannon の `errors` は**タイムアウトを含む**（`lib/run.js` の `onTimeout()` が `errors++; timeouts++` の両方を数え、README も「including timeouts」と書いている）。足すと二重に数え、**基準を満たしている計測を赤にする**（2 万件中 100 件のタイムアウトは本当は 0.5% だが 1.0% として出る）。`timeouts` は内訳として別に出すだけにする。

**分母の門番を置く。** エラー率は割合なので、分母が小さいほど緩くなる（3 件流して 0 件失敗なら 0%）。接続数の 10 倍（`CONCURRENCY_MIN_REQUESTS`）を下回る計測は成立していないものとして落とす。**同時接続の数そのものも判定する**（1 接続に下げるとエラー率は 0% になる）。

**境界（ちょうど 1%）はベンチ側の判定が落とす。** ゲートがベンチの結果に独立に掛ける共通の比較は「実測値 ≦ 上限」の形しか扱わない（`benchOutputProblems`）。基準の文は「< 1%」なので、等号を含めない判定は `concurrencyErrorRateProblem` が持ち、その実効性は `tests/gate-scripts.test.ts` の negative control（境界ちょうどの値を実際に通して非 0 で終わることを見る）が固定する。**ゲート側の比較は「桁で外れていないか」の二重化**として読む。

**遅延は判定に使わない。** 同時 100 では待ち行列が伸びるので、出るのは「1 件あたりの処理時間」ではなく飽和した状態の待ち時間。1 件あたりの増分は Step2 の基準（追加遅延 ≦ 50ms、逐次 1 接続）が別に測っている。実測値は結果の JSON に載せるだけにする。

### 3. 基準④は「文書の表」と「ソースの印」の 2 つの手がかりで数える

GitHub の Issue はゲートから読めないので、**未解決のバグの正本は `docs/known-issues.md` の「未解決のバグ」の表**に置き、ゲートは「表が空であること」を見る。

**文書だけを手がかりにしない。** 編集 1 行で黙らせられる（表の行を消せば緑になる）。そこで**ソースのコメントに残った「未解決の欠陥」の印**（`KNOWN_BUG_MARKERS`。一覧の正本は `scripts/lib/step7-criteria.mjs`）も同時に探し、1 件でもあれば落とす。**印だけを手がかりにする形も採らない** — 印を書かずに文書へ書いたバグが素通りする。どちらも片方だけでは fail-open。

**走査が空振りしていたら落とす（fail-closed）。** 1 ファイルも読めていないのに「印ゼロ＝緑」になる形は、走査の対象を縮める変更を黙って通す。走査したファイル数を判定へ渡し、0 件なら落とす。

**表の枠そのものを要求する。** 節を空にして表ごと消すと「0 件」と区別できないので、見出し行と区切り行が無い節は「読めない」として落とす。

**`TODO` は印に含めない。** このリポジトリは「後の Step でやる設計上の宿題」を ADR とコメントに書く流儀で、それらは欠陥ではない。含めると実行不能な要求（宿題を全部消すか検出網を緩めるかの二択）になり、**検出網が緩められる側に倒れる**。宿題は `docs/known-issues.md` の「既知の制限」の節と各 ADR に書く。

**印を探すのはコメントの中だけ。** 印の一覧そのもの（`['…', …]` の配列リテラル）や、その挙動を固定するテストの中の値を拾ってしまうと、**検出網が自分自身を報告する**。そこで `commentPositions` が 1 文字ずつ状態を持って「どの位置がコメントの中か」を求める。

**「印より手前にコメントの開きがあるか」だけを見る形では足りなかった**（どちらも実測）: SQL の `--` を見ていなかったのでマイグレーション（`.sql`）のコメントに書いた印が素通りし、囲みコメントの 2 行目以降は「行頭に `*` を書く」整形の慣習に頼っていたので `*` の無い行が素通りした。状態を持って追えば、行末までのコメント（`//` / `#` / `--`）と行をまたぐ囲みコメントが同じ 1 つの規則で閉じる。**文字列リテラルの中は区別しない**（余計に拾うほうが安全側）。

**走査から外すのは生成物のディレクトリ 1 件だけ**（`KNOWN_BUG_MARKER_EXCLUDED_DIRS` に理由付きで登録した `src/generated`）。gitignore 対象で**人が直せる場所ではない**ので、依存を上げたときに生成物のコメントへ印が入ると「直す手段が無い指摘」でゲートが赤くなり、残る道は検出網を緩めることだけになる。あわせて走査件数が「生成前か生成後か」で変わらなくなる（ゲートが出す数が再現する）。**`git ls-files` から対象を導く案は採らなかった** — negative control の行列は `npm` をシムへ差し替えるために PATH を置き換えるので、ゲートが PATH 上の `git` に依存すると**何も壊していないのに赤になる**（実測）。理由付きの 1 件の表のほうが、依存を増やすより安い。

**代償**: 説明の文章に印の綴りを書けない（書くと自分で引っかかる）。そのため `scripts/lib/known-issues.mjs` と `docs/known-issues.md` は印を「印」と呼び、綴りは `step7-criteria.mjs` の配列だけが持つ。

### 4. 基準③は既存のゲートがそのまま満たす

`npm run build` は Step2 から各ゲートのステップにあり、CI の `migrate-and-build` ジョブでも二重化している（`tests/deployment-invariants.test.ts` がその二重化が黙って外れないことを見張る）。**Step7 で足すものは無い。**

### 5. API リファレンスは「生成」ではなく「契約から導いた検査」で鮮度を保つ

`docs/api.md` は手書きだが、**`tests/api-docs.test.ts` が `openapi/openapi.yaml` から導いて両向きに突き合わせる**（契約にあるのに文書に無い／文書にあるのに契約に無い／`operationId` の不一致）。

**生成器にしなかった理由**: 生成器は `scripts/` に置くことになるが、そこは静的検査（import の許可リスト・`process` の使い方）が掛かる領域で、YAML パーサを許可リストへ足す差分になる。そして生成した文書には**散文を書けない**（運用者が読むのは認証の系統やステータスの使い分けのような散文）。検査にすれば散文を自由に書けて、鮮度は機械が保つ。

### 6. Vercel + Supabase の設定は `vercel.json` と `docs/deploy.md` に分ける

`vercel.json` は**ビルドの結線だけ**を持つ（`npm run gen` と `npm run db:generate` をビルド前に流す。生成物はコミットしないので、忘れると型が無くて落ちる）。環境変数の一覧・接続の 2 本立て（実行時はプーラ・マイグレーションは直結）・サーバーレスでの制限は `docs/deploy.md` に書く。

**`DIRECT_URL` のような 2 本目の環境変数は作らない。** アプリも `prisma.config.ts` も `DATABASE_URL` だけを読む形を保ち、マイグレーションのときだけ値を差し替えて流す（環境変数を増やすと「どちらが実行時か」を取り違える経路が増える）。

## 代替案と却下理由

- **ゲートで `docker compose up` を実際に回す** — Docker の無い機械でゲートが回らなくなる（上記 1）。CI 側に置いて同じ上限を読ませる形を採った。
- **基準②をレート制限のある経路で測り、枠を広げて計測する** — 本番と違う設定を測ることになる。枠の無い読み取りを選んだ（上記 2）。
- **基準④を GitHub の Issue API で数える** — ゲートがネットワークと権限に依存する。リポジトリの中の文書を正本にした（上記 3）。
- **印の走査から所有モジュール（印の一覧・判定・そのテスト）を理由付きで除外する** — 除外表は静かに緩む口。「コメントの中だけを見る」で構造的に解いた（上記 3）。生成物の 1 件だけは表に残したが、そちらは「人が直せない場所」という別の理由で、gitignore 対象であることを機械で照合している。
- **`docs/api.md` を生成物にする** — 散文が書けず、生成器が静的検査の許可リストを広げる（上記 5）。

## 影響

- ベンチが 2 本増える（`bench:demo-ready` / `bench:concurrency`）。ゲートのベンチは 4 本 → 6 本。
- 共有モジュールが 2 本増える（`demo-flow.mjs` / `known-issues.mjs`）。前者はアプリを子プロセスとして起こすので、`tests/gate-scripts.test.ts` の許可リストへ `node:net` と `process.execPath` を足した（どちらも副作用も終了経路も持たない）。
- CI の `docker-smoke` ジョブが「起動の確認」から「**5 分以内にデモの筋が通ることの確認**」になった（`scripts/demo-probe.mjs`）。デモの筋が停止を踏むので、このジョブは `PLATFORM_ADMIN_TOKEN` と `AUDIT_HMAC_SECRET`（どちらも CI の使い捨て）を compose へ渡す。
- `scripts/bench-proxy.ts` から `freePort` の写しを消し、共有モジュールの 1 本へ寄せた（同じ失敗の数え方も `errors` にタイムアウトが含まれる前提へ揃えた。あちらの門番は「0 件か」なので判定は変わらない）。
- `tests/lib/script-files.ts` の `reachableScopes` が**関数を実引数として渡す形も辿る**ようになった。`runBench('demo-ready', main)` のように他の関数へ渡して実行させるスコープが「到達不能」と判定され、その中の呼び出しがどの検査からも見えなかった（実測）。**検出網が広がる方向の修正**で、既存のベンチにも同じ検査が効くようになる。

## 宿題（この Step で閉じないこと）

- **レート制限の共有ストア**（ADR-0010 から継続）。サーバーレスで配備すると枠がインスタンスごとになる。`docs/deploy.md` と `docs/known-issues.md` に制限として明記した。
- **書き込みの同時実行の負荷**は測っていない（基準の文は「同時 100 リクエスト」で、読み取りの経路を選んだ理由は上記 2）。行ロックの存在は契約テストが固定しているので、正しさの側では担保されている。
- **長時間の安定性**（メモリの増え方・接続の滞留）は 10 秒の窓では見えない。
- **公開デモ URL** は出していない（`docs/deploy.md` の手順まで。§15 の「DB/常駐サーバーが必要な Web」はデモ動画必須・URL は任意）。
