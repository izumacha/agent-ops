# ADR-0014: 観測性の出口は「閉じた語彙の構造化ログ」と「プロセス内カウンタ」の 2 本にする

- **ステータス**: 採択
- **日付**: 2026-10-09

## 背景

Step0〜7 を終えた時点で、このアプリが外へ出す運用情報は **`console.error` の 37 か所だけ**だった。
文言は人間向けの散文（`'[proxy] 上流の呼び出しに失敗しました:'` のような形）で、構造を持たない。

実測した問題は 3 つある。

1. **出来事の種類で集計・警報を作れない。** ログ収集に載せても、条件は文言の部分一致にしかならない。
   文言は推敲で変わる（このリポジトリは実際に何度も推敲している）ので、警報が静かに空振りする。
2. **1 行が機械で読めない。** 時刻・深刻度・出来事の識別子が行の中に無く、あるのは散文と
   `describeError` の戻り値を Node が整形した結果だけ。収集側が構文解析できない。
3. **数が分からない。** 「上流の失敗が直近 5 分で何件あったか」を知る方法が無い。
   DB に残る事実（利用量・インシデント・監査ログ）は `GET /usage/daily` と画面で読めるが、
   **DB に残らない失敗**（上流の時間切れ・通知の不達・レート制限で断った数）はどこにも出ていない。

一方で、既存の検出網（`tests/error-logging.test.ts`）は「`console` のログの実引数は
リテラル / 置換の無いテンプレート / `describeError(...)` だけ」を構文で固定している。
**ここを緩めずに構造を足せるか**が設計上の制約だった（例外の `message` には ORM の検証エラー経由で
PII が、pg のプールエラー経由で接続文字列が載る）。

## 決定

### 1. ログの出口を `src/lib/log.ts` の 1 本に閉じ、出来事は閉じた語彙で名乗る

`console` を呼べるのは `src/lib/log.ts` **だけ**にし、他のすべては
`logEvent('<語彙のキー>', describeError(error)?)` を呼ぶ。語彙 `LOG_EVENTS` は
`<サブシステム>.<何が起きたか>` のキー（以前の `[tag]` の接頭辞をそのまま引き継いだ）と、
深刻度（`error` / `warn`）・人間向けの説明を持つ網羅表。

出力は**常に 1 行 1 JSON**（`ts` / `level` / `event` / `message` と、診断があれば `error`）。
**`console` のメソッドは深刻度で選ぶ**（`warn` は `console.warn`、それ以外は `console.error`。
どちらも stderr で行の形は変わらない）— 配備側のログ基盤はメソッドで深刻度を付けるので、
全部 `error` で出すと「縮退して続けた」が運用者の警報を鳴らす（実際、利用者がログイン用
トークンを 1 回打ち間違えただけで ERROR のレコードが立つ）。**環境では分けない**という決定は
そのままで、分けているのは深刻度だけ。

- **環境で形式を分けない。** 分けると本番だけを通る経路ができ、手元では一度も確かめられない
  （このリポジトリが「CI の緑が判断材料にならない fail-open」として繰り返し記録している形）。
  読みにくさの代償は承知の上で 1 つの経路に寄せる。
- **警報の条件に使うのは `event`。** 文言（`message`）は推敲してよい、識別子は変えたら気付く、
  という分担にする（`tests/error-logging.test.ts` が語彙のキーを構文で照合する）。

### 2. 検出網は「狭まらない」どころか強くなる

以前の規則（実引数の許可リスト）は出口のモジュールの中でそのまま効き、**そこへ 3 つ増える**:

| 増えた規則 | 何を止めるか |
| ---------- | ------------ |
| `console` を呼べるのは出口のモジュールだけ | 散文のログが別の場所から生えること |
| `logEvent` の第 1 引数は**語彙に実在するキーのリテラル**、第 2 引数は `describeError(...)` だけ | 語彙の外の出来事、例外の素渡し、引数を増やす署名変更 |
| 語彙に宣言した出来事は**どれも実際に出している** | 宣言だけの値（「監視できる」という誤解を生み、警報が永久に空振りする） |

`console` へ渡してよい形に `formatLogLine(...)` を足した。許せる理由は `describeError` と同じで、
**受け取れる値が構造で縛られている**から（第 1 引数は閉じた語彙のキー、第 2 引数は診断だけ）。

変異で確かめた（5 件すべて落ちる）: 出口の外で `console` を呼ぶ / 語彙に無いキーを渡す /
第 2 引数に `error.message` を渡す / 語彙を 1 件増やして出さない / 出口の名前を同名の `const` で覆う。

### 3. 数えるのは「DB に残らないもの」だけ

`src/lib/metrics.ts` がプロセス内のカウンタを持ち、`GET /api/v1/metrics`
（監視専用トークン・Prometheus のテキスト形式）が書き出す。数えるのは 3 つ:

| カウンタ | ラベル | 何に使うか |
| -------- | ------ | ---------- |
| `agentops_http_responses_total` | `method` / `status` | 要求数とエラー率（インスタンスごと） |
| `agentops_log_events_total` | `event` / `level` | 出来事ごとの発生数（警報の条件） |
| `agentops_metrics_series_dropped_total` | なし | 系列数の上限を超えて捨てた数（0 でなければラベル設計の誤り） |

- **DB を引かない。** 耐久する事実を返す経路は既にある（`GET /usage/daily`・画面・`GET /audit-logs`）。
  スクレイプのたびに DB を触らないので、監視そのものが本番の負荷にならない。
- **値はインスタンスごと。** 足し合わせるのはスクレイプ側（Prometheus の通常の形）。
  サーバーレスではインスタンスが短命なので、`agentops_process_start_time_seconds` /
  `..._uptime_seconds` を添えて「カウンタが 0 へ戻ったこと」が分かるようにする。
- **ラベルの値は閉じた集合へ写してから渡す**（`methodLabel` / `statusLabel`）。
  可変の値を入れると 1 プロセスの Map が無制限に伸びる。さらに系列数そのものに上限
  （`MAX_METRIC_SERIES`）を置き、超えた増加は捨てて**捨てたことを数える**（黙って落とさない）。
- **テナントの利用者には見せない。** 値はインスタンス全体の合計でテナントごとに分かれていない。
  ラベルにテナント id を入れると系列がテナント数だけ増え、しかも他テナントの活動量が読める。
- **カウンタとゲージの名前はどちらも表に置く**（`COUNTERS` / `GAUGES`）。ゲージ 2 本を
  `renderMetrics` の中へ直書きしていた版では、「名前の宣言は表だけ」という約束が実際には
  守られておらず、`Object.keys(COUNTERS)` から導いていた照合がその 2 本だけ素通りしていた
  （名前を書き換えても全件緑）。
- **「捨てた数」のカウンタは系列の表（`COUNTS`）の外に持つ。** 中に入れていた版では、上限に
  達してから**最初に**捨てるときにその系列を作るので `COUNTS.size` が上限を 1 本超えていた
  （上限そのものが破れる）。しかも分岐のコメントは「捨てた数そのものは既存の系列なので、
  この分岐へ再び入ることはない」と書いており、それが真になるのは 2 件目以降だけだった。

### 3-a. 応答を数える入口は 1 つだけにする

`countHttpResponse(method, status)` が唯一の入口で、`route()` を通らない経路も同じ関数を呼ぶ。

**最初の版は `route()` の中だけで数えていた。** そのため `route()` を通らない 4 本
（`GET /health`・受信 Webhook・画面側の CSV・`/metrics` 自身）が**メトリクスにもログにも
1 件も現れなかった**。とくに受信 Webhook は未認証で誰でも叩ける経路なので、
`STRIPE_WEBHOOK_SECRET` の設定ミスで全件 401 になっても、401 の山がどの出口にも出ない。

**包むのも 1 本に寄せる。** 最初の版は数える 3 行を 4 本のルートへ書き写していたので、
包む側が毎回 2 つの判断を自分でしており、**どちらも実際に間違えた**:
(a) 本体を `try` で包むか — 包み忘れた画面側の CSV は例外のとき何も数えず、その経路の 5xx が
系列に一度も現れなかった。(b) メソッドを何で渡すか — 文字列を書いた 3 本は `HEAD` を `GET` として
数え、`route()` 側は `other` として数えた（同じ要求が経路で違うラベルになる）。
`withResponseCount(handler)`（**`src/lib/api/response-count.ts`**）が両方を決めるので、次に
`route()` を通らない経路を足す人は同じ判断をしない。`route()` 自身もこのラッパーを通る。
**`handler.ts` に置かない**のは、あちらから取り込むと `@/data`（Composition Root）が
`GET /api/v1/health` の推移依存へ入るため（実測で到達モジュールが 20 → 44 に増えた）。
health は compose の healthcheck が 10 秒ごとに、`npm run bench:demo-ready` も叩く経路なので、
この分割はこのファイルが存在する理由そのもの（`src/lib/api/response-count.ts` 冒頭が正本）。

- 検出網は `tests/route-wrapping.test.ts` が **`src/app` 配下の全ルートの HTTP メソッドの export**
  を実体から導き、**どれも例外なく**共通のラッパーの印を持つことを要求する（`route()` で包んだ
  export も対象。`route()` 自身がこのラッパーを通るので、そこを免除する条件は 1 つも無い）。
  手書きの一覧にすると、`route()` を通らない経路を足した人が追記を忘れたぶんだけ網が狭まる。
- 判定は**印**（`RESPONSE_COUNT_BRAND`）を実体から読む。綴りで照合していた版は
  **コメントに関数名が出ているだけで条件を満たした**（実測で、画面側の CSV を自前で数える形へ
  戻しても全件緑で通った）。実際に数えていることは経路ごとの API テストが固定する
  （`tests/api/metrics.test.ts` / `tests/api/health.test.ts` / `tests/api/billing.test.ts`）。
- **キャッシュ制御もこのラッパーが付ける。** 例外の経路にだけ付けていた版では、本体が
  **返した**早期の 401 / 404 に付かなかった（画面側の CSV がそれで、認証付きの経路の
  401 / 404 が共有キャッシュへ載りうる状態だった）。
- **数えない種類の一覧の正本はコード側**（`src/lib/uncounted-response-sources.ts` の
  `UNCOUNTED_RESPONSE_SOURCES`。**件数は書かない** — 種類を足すたびに数字だけが古くなる。
  実際この PR の中で 3 → 4 へ増え、散文の「3 つ」が 5 か所残った）。文書は鍵を目印（`<!--uncounted:<鍵>-->`）として持ち、
  `tests/docs-gate.test.ts` が表から導いて突き合わせる。**散文だけに置いていた版は実際に
  古くなった** — 入口の 404 だけを「1 つある」と書き、画面の描画と Server Action が 1 件も
  数えられていないのに言及が無かった（運用者が「他の HTTP 通信はすべてこの系列に乗る」と
  読め、ログインの総当たりを条件に書いても一度も発火しない）。種類が増えていないことは
  `tests/route-wrapping.test.ts` が `src/app` 配下の分類（`route.ts` / `.tsx` /
  `'use server'` / そこから取り込まれる部品）から確かめる。
  - 入口（`src/proxy.ts`）の短絡。<!--uncounted:entryProxy-->
    入口は Route Handler とは**別のモジュール実体**で評価されるので、そこで
    `countHttpResponse` を呼んでも `/metrics` が読むカウンタには入らない（本番ビルドで
    実測: health の 200 は現れるのに入口の 404 は 2 件とも現れなかった）。**数えたように
    見えて見えない形は作らず**、ログだけで非可視を解いた（`entry.undecodable_path`。
    未認証で叩ける経路なのでプロセスに 1 度だけ出す。続いているかは前段のアクセスログで
    見る）。**同じ分離なので `agentops_log_events_total` にもあの行は現れない** —
    `logEvent` の「ログに出たのにメトリクスに出ない食い違いは起きない」は**同じモジュール
    実体の中での話**で、docstring をそう書き直した。
  - 画面の描画（`src/app` 配下の `.tsx`）。<!--uncounted:pageRender-->
    Next.js は描画の応答を Route Handler として扱わないので、包める入口が無い。
  - Next.js がルートの代わりに組み立てる応答。<!--uncounted:frameworkSynthesized-->
    export の無いメソッドへの 405 と、自動実装される `OPTIONS` の 204
    （`auto-implement-methods` が応答を作るのでラッパーを通らない。本番ビルドで実測:
    `PUT /api/v1/health` → 405・`DELETE /api/v1/metrics` → 405・`OPTIONS /api/v1/metrics`
    → 204 を叩いた後、3 件とも系列に 1 つも現れなかった）。同じ理由で `no-store` も `Vary` も
    付かないが、405 は本文が無く `OPTIONS` は `allow` だけなのでテナント固有の内容は漏れない。
    **この種類は検出網では見つけられない** — `src/app` 配下の分類ガードは「ファイル」しか
    見ないので、フレームワークの継ぎ目は**実測で見つけて表へ足す**しかない。
  - Route Handler から投げた Next.js の制御フローの例外。<!--uncounted:nextControlFlow-->
    **数えられないだけでなくヘッダも付かない** — 押印もラッパーの中なので、投げ直した時点で
    `no-store` も `Vary` も通らない（`frameworkSynthesized` と同じ）。遷移先は共通のログイン
    画面でテナント固有の内容を持たないが、認証付きの経路から投げるようになったら前段の
    キャッシュ設定を見直す。
    包むラッパーは `redirect()` / `notFound()` / `forbidden()` / `unauthorized()` を**応答へ
    写さず投げ直す**（写すと遷移も 404 も起きず 500 の JSON になり、`api.unexpected_error` の
    警報まで鳴る＝実測）。応答を作るのは Next.js なので数える場所が無い。**いま投げている
    経路は 1 本も無い**が、画面側の CSV を `currentSession()` から `requireSession()` へ
    寄せる 1 行の整理で生まれる。
  - Server Action（`'use server'` のモジュール）。<!--uncounted:serverAction-->
    同じく包める入口が無い。**代わりにログで見えるようにした** —
    `session.login_rejected`（ログインの拒否。理由は区別しない）と
    `session.cross_origin_action`（別オリジンからの送信を断った）。後者は
    `checkSameOriginAction` の中で出す（呼び出し側に書くと、Server Action を足した人が
    出し忘れたぶんだけ黙る）。
- **出来事の名前の接頭辞は 1 サブシステムに 1 つ。** 入口の出来事を `proxy.undecodable_path`
  と名付けていたが、`proxy.*` は LLM の中継（`src/app/api/v1/proxy`）が既に使っており、
  `proxy.*` の警報が 2 つの無関係な出来事を混ぜていた（上流の健康を見たいのに、壊れた URL の
  走査で鳴る）。`entry.undecodable_path` へ改名した。
- **プロセスの起動時刻は `Date.now()` ではなく `process.uptime()` から導く。** モジュールが
  評価されるのは最初の要求が届いたときなので、`Date.now()` だとサーバーレスのコールドスタート
  1 回分ずれる（実測: プロセスは 35 秒生きているのに稼働秒数が 29.774 を返した）。
  検査も `process.uptime()` と突き合わせ、**モジュールを 1.2 秒遅らせて読み直す**
  （遅らせない版では素の `Date.now()` へ戻す変異が全件緑で通った）。
- **`HEAD` と `OPTIONS` はラベルの閉じた集合に入れるが、理由は別。** Next.js の App Router は
  `HEAD` を `GET` のハンドラで応えるので**ラッパーに届く**。外していた版では死活監視の `HEAD` が
  「未知・敵対的なメソッド」のまとめ先 `other` に積まれていた（警報に使える信号ではなくなる）。
  **`OPTIONS` は逆で、Next.js が自分で実装するものはラッパーを通らない**（上の
  `frameworkSynthesized`）。集合に入れてあるのは**ルートが自分で `OPTIONS` を export した
  とき**のためで、いま export しているルートは 1 本も無い。「Next が自分で実装するから入れる」
  という以前の説明は向きが逆で、「自動の `OPTIONS` も数えられている」と誤読させていた。

### 3-b. `/metrics` は専用の読み取りトークンで守る

認証は環境変数 `METRICS_TOKEN`（32 文字以上）で、`src/lib/api/metrics-auth.ts` が照合する。

**最初の版はプラットフォーム管理者トークンで守っていた。** だが `docs/deploy.md` は
「監視の収集エージェントにそのトークンを渡す」と案内する一方、同じ文書の §15 は
「`PLATFORM_ADMIN_TOKEN` は配らない」と書いており、手順が自分の方針と矛盾していた。
あのトークンは `POST /tenants`（**応答に新しいテナントの admin トークンの平文が載る**）と
`PATCH /tenants/{tenantId}`（プラン・課金の紐付けの変更）も通るので、収集側の設定ファイルや
収集サーバの侵害がそのままテナント作成・プラン変更の権限になる（§9 最小権限）。

- **`Principal` の種類を増やす形は採らなかった。** 増やすと RBAC の許可表・プランのゲート・
  テナント境界の検査がすべてその種類を扱わねばならず、「どこでも通る主体」を足すことになる。
  代わりにこのルートは `route()` を通らず、`tests/route-wrapping.test.ts` の理由付きの表へ
  登録して**監視用トークンの入口への到達**を機械で要求する（署名 Webhook・画面側ルートと
  同じ扱い）。キャッシュ制御と応答の数え上げはこの表では要求しない — 包むラッパーが
  全応答へ付けるので、全ルート共通の 2 本の検査（印の付いた export であること・合成した
  応答に実際にヘッダが付くこと）が固定する。
- **未設定・短すぎは 503（fail-closed）。** 数字そのものは秘密ではないが、応答数とログの
  出来事数から「どの経路が叩かれているか」「どの失敗が起きているか」が外から読める。
- **合わなければ 401（403 ではない）。** 役割を持たない資格情報なので「権限が足りない」ではなく
  「この経路では受け付けない」。契約側の 403 の要求も、方式が役割を持つかで分けた
  （`tests/openapi.test.ts` の `SCHEMES_WITHOUT_ROLES`。載せない方式は 403 を要求される）。

### 3-c. 未認証経路の記録は 2 つの間引き方に分ける

`src/lib/log.ts` は出口を 3 つ持つ。**毎回 1 行**（`logEvent`）のほかに、未認証で誰でも叩ける
経路のための 2 つがある。1 要求 1 行で出すと、匿名の相手が**ログの量＝保存の費用**を好きなだけ
増やせるので、そこは必ずどちらかを通す。

| 出口 | 出し方 | 使うところ |
| --- | --- | --- |
| `logEventThrottled` | 窓（1 分）の中の通算件数が **2 の冪**の回だけ行にし、その件数を行の `occurrence` に載せる | 「断った」記録と「設定が使えない」記録（既定。一覧の正本は呼んでいる箇所） |
| `logEventOnce` | **1 プロセスに 1 度だけ** | **率を別の出口から読める**出来事だけ（いまは入口の読めないパスの 404。率は前段のアクセスログが持つ） |

**分ける軸は「率を別の場所から読めるか」の 1 つだけ。**

最初は「設定の通知か、断った記録か」で分け、設定ミスは 1 度きりにしていた。**それは誤り
だった** — 設定ミスのほうがむしろ「直すまで続き、続いていることが知りたい」側で、しかも
1 度きりだとその 1 行を取りこぼした配備では以降どの出口にも何も現れず、
`agentops_log_events_total` も 1 で止まる（行を出した回しか数えないため）。具体的には
`STRIPE_WEBHOOK_SECRET` の設定漏れが受信 Webhook を全滅させ、事業者がバックオフののち
エンドポイントを無効化するので、**解約が反映されないまま有料の権限が残る**。間引く側なら量は
窓あたり対数に収まるので、匿名の相手にログの量を決めさせる心配もない。

**「窓あたり 1 本＋次の行に抑えた件数を載せる」形は採らなかった。** 1 本目は定義上「その前に
抑えた件数」を持てないので必ず 0 で、**burst が止まると**抑えた件数を載せる 2 本目が永久に
来ない。1 万件叩いて去る総当たりが「1 人の打ち間違い 1 件」とまったく同じ 1 行になり、
画面側（Server Action）の出来事は系列も `/metrics` から読めないので規模がどこにも残らない。
2 の冪なら行数は件数の対数（1 万件で 14 本）に収まり、**最後に出た行がそのまま桁を言う**。
**タイマーで後から流し込む形も採らない** — サーバーレスでは実体が凍結されて発火しないことが
あるので、出した時点で意味が完結している形を選んだ。

**未認証で誰でも引ける出来事の `level` は `warn` にする。** 配備側のログ基盤は `console` の
メソッドで深刻度を付けるので、`error` だと**外からの走査がプラットフォームのエラー率の警報を
鳴らせる**。任意の設定（`METRICS_TOKEN` / `STRIPE_WEBHOOK_SECRET` は「繋ぐなら必須」）の
未設定はまさにこれに当たり、繋いでいない配備では未設定が正常なので `warn`。値を入れたのに
短すぎる側は設定ミスが確定するので `error` のままにしてある。**警報の条件は深刻度ではなく
`event` の等値で組む**という分担（§1）があるので、これで情報は落ちない。

**だから警報は「行が出たこと」で組み、規模は最後の行の `occurrence` で読む**（行数は件数の
対数なのでしきい値に使えない）。数える側（`agentops_log_events_total`）は**行にしなかった回も
毎回**積むが、その系列が読めるかは呼び出し元の束による（§3 の実測）。

**壁時計なので負の経過は「窓を越えた」として扱う。** `elapsed < 窓` だけを見ていると、NTP の
巻き戻しで**巻き戻した時間ぶん行が 1 本も出なくなる**（しかもサーバーレスではその行が唯一の
読める信号なので、運用者が原因を調べたいまさにその時間が沈黙する）。

### 4. 出口の import は最小に保つ

`src/lib/log.ts` が取り込むのは `metrics.ts` だけにする。ここは `src/domain` からも呼ばれるので、
`constants.ts` のような大きなモジュールを取り込むと純粋ロジック側の推移依存がそこへ一気に広がる
（実測: 取り込んだ版では seed の import グラフが 9 ファイル増え、`tests/docker-seed-files.test.ts` が落ちた）。

設定値の下限のような数値は文言に埋め込まず**定数の名前**で指す（運用者はその名前で引ける。
通知の既存の文言が既にこの形）。

## 影響

- `console.error` の 37 か所が `logEvent(...)` になった。文言は語彙の表に移り、**行の形が変わった**ので、
  ログを文言で検索している手順書があれば `event` の識別子へ移す必要がある（この時点では無い）。
- ログ 1 行を読むテスト側のヘルパーを `tests/lib/log-lines.ts` に集約した（文言ではなく識別子で照合する）。
- `HTTP_STATUS` に `OK: 200` を足した（テキストを返す経路が自分で status を書くため。
  ラベルの照合もここから導く）。
- 環境変数が 1 つ増えた（`METRICS_TOKEN`）。`.env.example` と `docker-compose.yml`・
  `docs/deploy.md` の表に載せてある（素通し漏れは `tests/deployment-invariants.test.ts` が
  `.env.example` から導いて落とす）。
- `src/lib/api/auth.ts` の `extractBearerToken` と `invalidTokenError` を export した。
  監視用トークンの入口が同じ関数を使うので、Bearer の解析と `WWW-Authenticate` の綴りが
  2 か所に分かれない（§6 DRY）。**`unauthorizedError` は export していない** — 資格情報が
  無いときの 401 は `extractBearerToken` が自分で投げるので、呼び出し側から使う必要がない
  （最初は 3 つとも export していたが、1 つはどこからも使われない公開面になっていた）。
- `formatLogLine` の「例外を投げない」を実際にそうした。`now.toISOString()` と語彙の引きが
  `try` の外にあったため、無効な `Date` や語彙に無いキーでは縮退の経路に入らず投げていた
  （docstring だけが守備範囲を広く名乗っていた）。**`logEvent` 側も同じく防御的に引く** —
  あちらが先に落ちると固めた縮退へ一度も届かず、しかも `pg` のプール障害ハンドラ
  （要求の外）から呼ばれるので、投げると誰も捕まえられない例外になる。
- `src/domain/plan.ts` が `@/lib/log` を取り込む。**これは `src/domain` から `src/lib` への最初の依存**で、
  層の向きとしては逆行している。許容したのは (a) 取り込む先が純粋な TS で Prisma / Next に依存しない
  （`src/domain` の「`npm run db:generate` 無しでもユニットテストが動く」という条件は保たれる）、
  (b) 代わりの形（`planLimitsFor` が記録をやめ、呼び出し側それぞれが出す）はフォールバックの
  観測性を呼び出し側へ散らす、の 2 つ。**この向きの依存をこれ以上増やさない。**

## 宿題

- **トレース（分散トレーシング）は入れていない。** 1 要求の中で上流・DB・通知のどこに時間が
  掛かったかは、いまのカウンタでは分からない。入れるなら `route()` の 1 か所に span を張る形になる。
- **メトリクスの保持はスクレイプ側に委ねている。** スクレイプが来ない配備では値がどこにも残らない。
- **引きに行く形（pull）はサーバーレスでは成り立たない。** 要求ごとにどのインスタンスへ届くかが
  決まるので、`GET /api/v1/metrics` へのスクレイプが読むのは**その 1 回を処理したインスタンスの
  表だけ**で、他のインスタンスが処理した応答は 1 件も見えない（コールドスタートごとに 0 へ戻る）。
  つまりこの文書が主に案内する配備先では、**`agentops_http_responses_total` を使った率の警報は
  全要求が 500 でも鳴らない** — `src/proxy.ts` の応答が系列に現れないのと同じ非可視が、
  1 段上（インスタンスの単位）で起きている。**警報は構造化ログの `event` で組む**のが
  この配備での答えで、手順は `docs/deploy.md` の監視の節が持つ。塞ぐなら押す形
  （スクレイプを待たずに送る）が要るが、外へ送る経路は SSRF の制約と宛先の検証を別途伴う
  （下のログの宿題と同じ理由で入れていない）。
- **ログの出力先は `console` のまま。** 収集は配備側（Vercel / コンテナのログドライバ）が行う前提で、
  アプリから外へ送る経路（OTLP 等）は持たない（送るなら SSRF の制約と宛先の検証が別途要る）。
