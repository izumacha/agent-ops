# ADR-0015: レート制限の記録は DB の共有ストアに置く

- **ステータス**: 採択
- **日付**: 2026-10-09
- **関連**: ADR-0007（プロキシと API キー）／ADR-0010（ガードレールと監査の連鎖。この宿題の出所）／ADR-0006（Ports & Adapters）

## 背景

Step2 から Step7 まで、レート制限の記録は**インプロセスの `Map`**（`SlidingWindowRateLimiter`）が
持っていた。1 インスタンスで動かすあいだは正しく効くが、**水平スケールすると枠が台数分だけ
緩くなる**（同じテナントの要求が別のインスタンスへ振られると、それぞれが別の `Map` を数える）。

守っているのは「テナントが毎分どれだけ上流へ費用を発生させられるか」なので、**枠は配備全体で
1 つでなければ意味を持たない**。`.env.example` にも「レート制限はインプロセスの Map なので
複数インスタンスでは台数分だけ緩くなる」と書いて、ベンダー側の月次利用上限を必ず設定するよう
案内していた — つまり**アプリ側の歯止めは実質 1 台構成でしか働いていなかった**。

サーバーレス（Vercel）ではさらに悪い。インスタンスは短命で、要求ごとに別のインスタンスへ
振られうるので、`Map` は「ほぼ毎回空」になる。`agentops_process_uptime_seconds` を足したのは
まさにこの短命さを観測するためで（ADR-0014）、同じ事実がレート制限を無力化していた。

## 決定

### 1. 記録は `repos.rateLimit`（data 層）が持つ

Port は `src/data/ports/rate-limit.ts`、実装は `adapters/memory` と `adapters/prisma`（ADR-0006）。
表は `RateLimitHit`（`key` / `tier` / `at`）で、**業務データではない**（窓から外れた行は捨ててよい）。

- **`key` は認証済みの主体から作る**（`tenant:<id>` か `platform`）。偽装できるヘッダ
  （`X-Forwarded-For`）には頼らない（ADR-0007 からの方針を引き継ぐ）。
- **`tenantId` の外部キーを張らない。** `platform` の行はテナントに属さないので、FK を張ると
  その枠が表現できない。解約したテナントの行は窓から外れた時点で掃かれる（下記の `sweep`）。
- **主キーは `BIGSERIAL`**（他の表の `cuid()` と違う）。アプリから id で引く経路が無く、
  毎分の追記が主な負荷なので、採番を DB へ任せて挿入を 1 文で書けるようにする。

### 2. 「数えて、上限未満なら 1 行足す」を 1 回の操作で行う

読んでから書く形に分けると、同時に届いた 2 本がどちらも「上限未満」を読んで両方が通る
（`agents.create` の件数上限と同じ理由）。prisma アダプタは CTE を鎖にして
**1 文**で「そのキーの期限切れを掃く → 窓の中を数える → 条件を満たせば 1 行入れる → 結果を返す」を行う。

**ただし 1 文に収めるだけでは足りなかった（実測）。** PostgreSQL の READ COMMITTED では
文のスナップショットが**文の開始時点**で固まるので、同時に走った別の文の挿入は見えない。
専用 DB で上限 3 に対して 10 本を同時に投げると **6 本が通った**。
当初の設計では「超過は最大で同時実行数 − 1。毎分の回数を絞る目的には十分」として受け入れる
つもりだったが、**守っているのは「高くつく処理の回数」なので、攻撃者の同時実行数に比例して
緩む上限は上限として機能しない**（`heavyRead` は毎分 10 回なのに、100 本同時なら 100 回通りうる）。

そこで**キーごとの助言ロック**（`pg_advisory_xact_lock(hashtext(key))`）を取ってから数える。
`agents.create` / `guardrailRules.create` が「挿入と同じ原子的操作の中で数える」のと同じ立場。

- **ロックは別の文で取る。** 同じ文の中（CTE）で取っても意味が無い — スナップショットは
  ロックを取る前に固まっている。トランザクションを開いてロックを 1 文で取り、**次の文**で
  数えると、その文は「ロックが下りた時点までにコミット済みの行」を見る。
- **助言ロックはトランザクションの終わりで必ず解放される**ので、取りこぼしの心配が無い
  （`pg_advisory_lock` のセッション版は使わない）。
- **直列化するのは同じキーの「数える文」だけ**で、上流への呼び出しは外側。別のキーは独立
  （契約テストが「別のキーなら待たされない」を固定する）。
- **`hashtext` の衝突**は無関係なキーが時々直列化するだけで、答えは変わらない。

**同時性の検査は「N 本投げて通ったのは上限ぶんか」では書けない**（実測）。同時に*実際に*
走る本数は接続プールの大きさで決まるので、本数を増やすほど待ち行列ができて直列に近づく —
10 本では超過が出たのに 30 本ではロック無しの実装でもちょうど上限ぶんになった。
代わりに**ロックそのものの存在を決定的に確かめる**（別の接続で同じキーのロックを掴み、
`consume` が待たされることを見る）。エージェント数の上限で既に使っている手口。

### 3. ストアが落ちたら**断る**（fail-closed）

記録に失敗した例外はそのまま伝播し、`route()` が 500 へ写す。**上流の呼び出しは起こらない。**

**専用の出来事を残してから投げる**（`rate_limit.store_unavailable`。ADR-0014 の語彙）。
汎用の 500（`api.unexpected_error`）に埋もれさせない — 運用者が知りたいのは
「断っているのが上限超過なのか、枠を数えられていないのか」。**行は間引く**
（DB が落ちている間は全要求で起きる＝直るまで続く条件。`health.db_unreachable` と同じ判断）。

「落ちたら通す」（fail-open）を採らなかったのは、ここで守っているのが**費用**だからで、
素通しにすると DB 障害の最中に上流への課金が無制限になる。なお PostgreSQL は**アプリが
そもそも動けない相手**（認証もテナントの解決も DB を引く）なので、「レート制限のためだけに
可用性が下がる」ことは無い。

### 4. `src/lib/api/rate-limit.ts` は**方針だけ**を持つ

残るのは「キーの作り方・上限の決め方（プラン別・環境変数の上書き）・待ち時間の計算・
枠の組み合わせ」で、「窓の中で何件あったか」は Port の実装が持つ。待ち時間の計算は
純粋関数（`retryAfterSecondsFor`）へ出し、合成入力で固定する。

**テスト用の逃げ道の名前を変えた**（`resetSharedRateLimiterForTesting` →
`setRateLimitOverridesForTesting`）。作り直す「制限器」が無くなったので、名前が実体を
指さなくなっていた。記録そのものは memory アダプタをテストごとに作り直すことで空になる。

## 影響

- `enforceRateLimit` が**非同期**になり、`repos` を受け取る（`route()` は既に `repos` を
  持っているので、渡すのは 1 引数）。
- **プロキシの追加遅延が DB のトランザクション 1 つぶん増える**（ロックを取る文＋数える文）。
  Step2 の基準（p95 ≦ 50ms）に対する実測はベンチ（`npm run bench:proxy`）が見張る。
  既定の毎分 600 回（＝毎秒 10 回）に対してロックを握るのは数ミリ秒なので、同じテナントの
  要求が入口で詰まる水準ではない。
- 表が増えるので、契約テストの `TRUNCATE` の対象も増える（`tests/data/*.contract.prisma.test.ts`
  の `beforeEach` は全テーブルを対象にしているので自動で入る）。
- `.env.example` の「台数分だけ緩くなる」の記述と `docs/known-issues.md` の既知の制限①、
  ADR-0010 の宿題欄を書き直した。

## 宿題

- **定期掃き。** `consume` はそのキーの期限切れを同じ操作で片付けるので通常は表が膨らまないが、
  **二度と来ないキー**（解約したテナント）の行は残る。`sweep(before)` は用意したが、
  **定期的に呼ぶ仕組みは同梱していない**（次のタスク）。
- **上限の単位は「毎分」のまま。** バーストを許す形（トークンバケット）には変えていない。
