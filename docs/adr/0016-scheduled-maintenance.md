# ADR-0016: 保守の定期実行は 1 本の受け口に集め、スケジューラは持たない

- **ステータス**: 採択
- **日付**: 2026-10-09
- **関連**: ADR-0010（ガードレールと監査の連鎖。定期掃きの宿題の出所）／ADR-0015（レート制限の共有ストア。記録の回収の宿題の出所）／ADR-0004（Step ゲート）

## 背景

**宿題が 2 件、同じ形で残っていた**: どちらも「誰も呼ばない後片付け」で、呼ぶ仕組みが無い。

1. **ガードレールの定期掃き**（ADR-0010）。判定の起点は 3 つ（中継の直後・評価実行の直後・
   明示実行 `POST /guardrails/run`）だが、**定期的に明示実行を呼ぶ仕組みを持っていなかった**。
   通常はイベントの直後に判定するので足りる、という理由で据え置いていた。
2. **レート制限の記録の回収**（ADR-0015）。`sweep(before, limit)` は用意したが**呼び出し元が
   1 つも無い**。インプロセスの `Map` だった頃は全キーを一定間隔で自動回収していたので、
   これは共有ストアへ移したときに**失った分**だった。

### 1 が「通常は不要」では済まない理由（この ADR で考えを変えた点）

集計窓は**半開区間**で、終端は基準時刻。つまり**窓から古い行が抜けるだけでしきい値を越える**
ルールがある:

- **エラー率**: 1 時間の窓で見るルールは、成功した古い呼び出しが窓から外れると、新しい要求が
  1 件も無くても率が上がる（分母が減って分子だけが残る）。
- **品質**: 良い実行が窓から抜けると平均が下がる。

**どちらも「使われなくなったエージェント」で起きる**。そのときイベントは発生しないので、起点が
「イベントの直後」だけでは**判定そのものが走らない＝永久に発火しない**（fail-open）。
ADR-0010 が「必要になるのは『使われていないエージェントの窓が過ぎたこと』を検知したいときだけ」と
書いていたのはこの形で、**それは例外的な要望ではなく、エラー率と品質のルールでは常に起きうる**。

## 決定

### 受け口は 1 本（`POST /maintenance/run`、プラットフォーム限定）

**2 つの後片付けを 1 つの受け口に集める。** 別々のエンドポイントにすると、スケジューラ側の設定も
2 本になり、片方だけが設定されていない配備が生まれる（しかも「設定されていない」ことは
どこにも現れない）。

- **プラットフォーム管理者トークンのみ**。テナントをまたいで読むので RBAC の 3 役割では表せない
  （テナント内の admin に配備全体の掃きを許すとクロステナントの読み出しになる）。
- **レート制限は掛けない**（他のプラットフォーム経路と同じ）。枠はプランから引くのでプランを
  持たない主体には倒れ先が無く、しかも**一巡はカーソルで何十回も呼ぶ**形なので小さい枠を掛けると
  掃きが途中で止まる（`OUTBOUND_WAIT_ROUTE_RATE_LIMIT_PER_MINUTE` のコメントが記録している
  失敗の形と同じ）。叩けるのは運用者のトークンだけ。
- **GET ではなく POST**。発火すればインシデントを作りエージェントを止め、記録を消すので副作用が
  ある（§9「副作用のある操作を GET で行わない」）。

### 1 要求でやる仕事には必ず上限を置き、続きはカーソルで返す

テナント数もエージェント数も運用で増える一方なので、「全件を 1 要求で」にすると配備が育つほど
1 回が長くなり、いずれ配備先の実行時間上限（serverless）に当たって**最後まで届かなくなる** —
しかも**途中で切れたことは応答に現れない**ので、掃きが静かに効かなくなる。

- 1 要求で判定するエージェント数は `agentBudget`（既定 `MAINTENANCE_AGENT_BUDGET_DEFAULT`、
  上限 `MAINTENANCE_AGENT_BUDGET_MAX`）。
- 記録の回収は 1 回の `DELETE` を `MAINTENANCE_RATE_LIMIT_SWEEP_BATCH` 件に区切り、
  1 要求で `MAINTENANCE_RATE_LIMIT_SWEEP_MAX_BATCHES` 回まで。
- 続きの位置は**テナントとエージェントの 2 本のカーソル**。1 本に畳むと符号化の規則を自分で
  作ることになり、既存のカーソルの復号（`decodeCursor`）と 2 つの形が並ぶ。

**やることが残っているかは `passComplete` の旗が表し、カーソルの `null` では表さない。**
**根拠は当初書いたものとは違う（実測で書き直した）** — 最初は「続きの位置が『先頭のテナント』に
なることがある（1 件目のテナントのエージェントが予算に収まらなかったとき）」を理由にしていたが、
その場合は `nextAgentCursor` が非 `null` になるので `null` からの導出でも区別できる。
**旗をカーソルの `null` から導く変異は、テスト 19 件すべて緑のまま通った**（＝当時の旗は
何も守っていなかった）。

旗が実際に要るのは**記録の回収を打ち切ったとき**で、下の順序の決定と対になっている。

**同じテナントにエージェントが残っているあいだはテナントのカーソルを進めない。** 進めると
残りのエージェントがその一巡では二度と判定されず、取りこぼしが静かに起きる。

### 記録の回収は「一巡の開始」で、しかも**終わるまでテナントを歩かない**

毎ページで回収すると、テナント数の多い配備では同じ掃きを何十回も繰り返す（消す行はもう無いので
空振りだが、そのぶん `DELETE` が走る）。境目は**窓の長さから導く**（`rateLimitWindowMs`）—
新しくしすぎると**生きている記録を消して枠をリセットしてしまう**。

**打ち切ったときは、テナントを 1 件も歩かずに「カーソルは両方 `null`・`passComplete` は偽」で
戻る。** 歩いてしまうと、残りの回収は「次の一巡の開始」まで待つことになり、**その一巡の最後の
応答は `passComplete: true` を返す**（回収の残りが応答のどこにも現れないまま消える）。
先に回収を片付ける形にすると、「やることが残っている」が**カーソルを 1 つも進めない状態**で
必ず呼び出し側へ伝わり、ここで初めて `null` と「終わった」を区別する必要が生まれる
（＝旗が実際に効く）。呼び出し側は「旗が真になるまで、返ったカーソルを送り返す」だけでよく、
回収と判定で分岐を書き分けない。

### 判定が失敗しても 200 を返す（`POST /guardrails/run` とは逆）

明示実行は「人がいま判定しろと言った操作」なので、判定できなかったことを隠さず 500 にする。
こちらは**一巡を回し切ること自体が仕事**で、500 にすると呼び出し側のループが続きのカーソルを
受け取れず**そのテナント以降が丸ごと判定されない**。件数（`failed`）を応答に載せることで
運用者には見え、サーバログにも `guardrail.evaluation_failed` が 1 行ずつ残る。

**取りこぼしをスケジューラの失敗として見せるのは呼び出し側の責務**にした
（`scripts/maintenance-tick.mjs` は `failed > 0` で非 0 終了する）。

### 停止しているエージェントは判定しない

止まっているあいだは中継も評価も走らないので窓の集計は動かないうえ、発火しても「もう止まって
いる」だけ（`suspended` は偽になる）。判定の費用だけが掛かるので、絞って予算を生きている
エージェントへ回す。

### スケジューラはこのリポジトリに持たない

同梱するのは「1 回のティックで何をするか」だけ（`scripts/maintenance-tick.mjs`。
`npm run maintenance:tick`）。配備先ごとに手段が違い（host の cron・systemd timer・
GitHub Actions の `schedule`・クラウドのジョブ）、どれを選ぶかは運用の判断なので、
繋ぎ方は `docs/deploy.md` に書く。

**Vercel Cron からは直接呼べない** — あちらは GET しか発行せず、この経路は上記の理由で POST
にしてある。Vercel で配備する場合も外部のスケジューラからこのスクリプトを回す。
**これは代償であって、回避のために GET を用意しない**（副作用のある GET を 1 本作ると、
その経路だけ §9 の規則の外に出る）。

## 影響

- `POST /maintenance/run` が増える（契約・ルート・入力検証・応答の型）。
- `rateLimitWindowMs()` を `export` した（境目を同じ値から導くため。`RATE_LIMIT_WINDOW_MS` を
  直接読む形にすると、テストの上書きが効かないうえ fail-closed の検証を通らない値で境目が決まる）。
- カーソルの復号（`cursorSchema`）を一覧のクエリと本文で共有した（§6 DRY）。
- ADR-0010 と ADR-0015 の宿題を 1 件ずつ閉じた。

## 残る宿題

- **スケジューラの死活は見えない**。ティックが 1 度も走らなくなっても、アプリ側には「呼ばれて
  いない」ことを知る術が無い（最後に掃いた時刻を持っていない）。見えるようにするには
  `agentops_*` のメトリクス（ADR-0014）へ「最後の一巡の完了時刻」を足し、収集側で古さを
  見張るのが最小。**運用に入れてから必要性を確かめる**（いまは `maintenance:tick` の終了コードを
  スケジューラ側で見張る前提）。
- **一巡の間隔は決めていない**。適切な値は窓の長さ（ルールごとに違う）と配備の規模で決まる。
  短くすると判定の費用が増え、長くすると「窓が過ぎてから発火するまで」の遅れが伸びる。
  `docs/deploy.md` に出発点（毎時）を書き、運用して調整する。
- **判定の重複は避けていない**。イベントの直後の判定と定期掃きが同じ窓を二度集計することはある
  （発火の重複排除が働くので記録は増えないが、集計のクエリは走る）。費用が問題になったら
  「最後に判定した時刻」を持って間引く形が要るが、列が増えるので必要性を確かめてから。
