## `src/proxy.ts`

全リクエストの入口（Next.js 16 の `proxy` ファイル規約。旧 `middleware.ts` の後継で**エクスポート名は `proxy` 固定**）。パスの percent-decode に失敗する要求（`/api/v1/agents/%ff` 等）を 404 で落とす — Next.js が `params` を組み立てる `decodeURIComponent` は `route()` の try/catch より手前なので、素通しすると**認証ヘッダ無し**で動的セグメントを持つ全ルートが素の 500 を返す（実測）。`TRACE` などの未対応メソッドはこの proxy にも到達しないので、前段のリバースプロキシで落とす前提（ADR-0005 の宿題）。**proxy を置くと Next.js は非 GET の本文を入口でバッファし、`experimental.proxyClientMaxBodySize` を超えた分を黙って切り詰める（エラーにしない）。** このバッファは**認証より前**に走るので、既定（10 MiB）のままだと未認証の相手が 1 接続あたりその分のヒープを握れる。そこで `next.config.ts` は値を `src/lib/body-limits.ts` の `ENTRY_MAX_BODY_BYTES`（= `JSON_BODY_MAX_BYTES` ＋ 余白）から**導出**する（数値を書き写さない）。**余白は「1 回のソケット読み取り以上、その 2 倍以内」に保つ**（`MAX_SOCKET_READ_BYTES`。いまの値は下端ちょうど）— Next.js は上限を跨いだかたまりを**丸ごと捨てて**閉じるので、余白が小さすぎると切り詰め後の長さがアプリの上限ちょうどに着地して 413 をすり抜け、**先頭が完結した別の妥当な JSON** だと 201 が返って送信者の書いた項目を落とした資源が黙って作られる（実測）。大きすぎると未認証に握らせるヒープが戻る。両方向を `tests/proxy.test.ts` が固定し、**基準は `node:stream` から実測した読み取り単位**から取る（定数どうしで比べると恒真式になり、写しを縮める変異が素通りする）。実測値の記録は `src/lib/body-limits.ts` に置く（数値の写しを増やさない）。`body-limits.ts` は `next.config.ts` が import するので**定数だけを持ち import を持たない**（Next の config transpile は `next.config.ts` 自身の import しか `paths` を書き換えず、連鎖に `@/...` が残ると `npm run build` だけが落ちる）。**サイズだけでは資源の消費を縛れないので、入れ子の深さにも上限を置く**（`JSON_BODY_MAX_DEPTH`。超過は 422 で、判定は本文を読む共通の入口 `readJsonBody` にあるので**本文を取る全ルートに等しく効く**）。`JSON.parse` は深さ 10 万でも通るのに `JSON.stringify` は約 4,164 で RangeError になり、しかも落ちなくても深い構造の stringify 自体が重い — 上限が無かった頃は 8.4 KiB の本文 1 通で 6.4ms を焼いたうえ RangeError が 500 になっていた（いまは 0.33ms の 422）。**しきい値を上げる変異は「本文の上限まで詰めたフィクスチャ」で気付く**（位置の打ち切り・キーの打ち切り・訪問回数の予算・**同時に積む枝の数の予算**）。フィラーは**攻撃者と同じ密度**まで詰める — 疎なフィラーだとその比のぶん窓が開いたままで、実測で訪問予算 26,000 とキー数 7,000 の変異が全件緑を通った。**フィラーは攻撃者と同じ文字集合・同じ詰め方にする** — JSON のキーは任意の文字列なので、攻撃者は `"` と `\` を除く 0x20〜0x7F の **94 文字**（DEL も使える）を**全単射の N 進**で使い、同じ 64 KiB に 9,303 キーを詰められる。英数字 36 文字の版は 8,341 キー、印字 ASCII 93 文字＋素の N 進の版でも 9,268 キーで、それぞれ `slice(0, 8_500)` と `slice(0, 9_290)` が全件緑を通った（素の N 進は「先頭が字母の 0 番目」になる 2 文字キーを 1 つも作らないので、同じ字母でも密度が落ちる）。**番兵はフィラーの文字集合の外から採る** — キーが衝突すると `JSON.parse` の重複キーは「値だけ後勝ち・位置は初出のまま」なので深い値が意図より手前へ落ち、実測では「最後のキー」のつもりが 8 倍手前（1,015 番目）で、`Object.keys(...).slice(0, 8_000)` が全件緑を通った。**フィクスチャの意図と実体の乖離は判定側の変異が無いと永久に見えない**ので、位置そのものも別に固定する。**同時に積む枝の数**は `[],` を並べる形が最密（3 バイト/節点＝21,800 本）で、数値や 1 本の鎖で埋めた版では 575 件しか積まれず、`if (stack.length > 2_000) return false;` が全件緑を通った。**ただしこれは証明ではない** — 位置の偶奇・部分集合・間引き（`index += 2` 等）はしきい値ですらないので原理的に列挙できず、実測でも深い値の位置がすべて偶数添字だった時点で 1 文字の変異が全件緑を通った。**「この族は閉じた」と書かない**。**値そのものは `tests/body-depth.test.ts` が上下から縛る** — RangeError の余裕（`< 3,000`）だけを見ていた版では、上限を 2,999 に上げても全件緑・件数も不変のまま「上限ちょうどの本文」が 33.4ms に戻せた（実測）。いまはコスト側の上限（`<= 128`）で押さえ、上げる差分は実測を取り直してレビューで確認する。**残る境界は 2 つ**: 深さを数えるのは `JSON.parse` の後なので 422 に倒す本文でも解釈の費用は払う。また**幅では同じことができる**（64 KiB に短いキーを詰めた本文は、上流も記録も無しで 1 通 3.3ms＝典型的な本文の約 31 倍。実測値と Step4 への申し送りは ADR-0007）。**残る境界: 保持時間は設定では直らない** — `Content-Length` を大きく宣言して 1 バイトずつ送ると Node 既定の `requestTimeout`（300 秒）まで 1 接続を占有できる（実測 305 秒）。本文のサイズとタイムアウトは前段のリバースプロキシでも落とす前提（ADR-0005 の宿題）。

## `src/app/*`

App Router。API は OpenAPI の `servers.url`（`/api/v1`）に合わせて `src/app/api/v1/*` に Route Handler として実装する。`api/v1/health/route.ts` は DB 到達性を返す（compose の healthcheck が使う）。**それ以外の Route Handler はすべて `src/lib/api/handler.ts` の `route()` で包む**（認証 → 本体 → 例外の HTTP 化を 1 か所に集める。`NextResponse` ではなく素の `Response.json` を返すので、テストは HTTP を介さずハンドラを直接呼べる）。本体の定型: `requireAction(principal, 'view'|'execute'|'stop')` / `requireAdminRole` / `requirePlatformAdmin` で認可 → `readJsonBody(request, schema)` で本文 → `repos.<port>` をテナント id 付きで呼ぶ → `serializers.ts` で DTO に写す。他テナントの id は `notFoundError()`（404）。**`route()` は本体へ渡す前に URL の動的セグメントを資源 id の形（`src/domain/resource-id.ts` の `isResourceId`）で検証し、形が違えば 404 にする** — Next.js はパスセグメントを percent-decode して渡すので、`/agents/%00` は NUL を含む文字列として届き、素通しすると PostgreSQL が拒否して 500 になる（実測。viewer のトークンだけで無制限に 500 とスタックのログを積める）。**この壊れ方は API テストからは見えない** — memory アダプタでは「表に無い」だけなので同じ入力が 404 に見える（ADR-0006 の構造的な死角）。判定はルートごとではなく `route()` に置くので、新しい `[id]` を足すときに書き足す場所は無い。

## `src/data/`

**Ports & Adapters**（ADR-0006）。契約は `ports/`（レコード型も Prisma 非依存）、本番は `adapters/prisma/`（`src/` の中で Prisma を直接 import してよい唯一の場所。`tests/` は上の ESLint の対象外）、テストは `adapters/memory/`。Composition Root は `index.ts` の `getRepos()`（async。prisma アダプタと singleton は動的 import で初回だけ読み、静的 import で生成物 `src/generated/prisma` を API テストの経路に引き込まない）で、テストは `setReposForTesting()` で差し替える（`NODE_ENV=production` では throw）。新しいエンティティ操作は「Port → memory → prisma → API テスト → 契約テスト」の順で足す。**削除の規則（Cascade / Restrict）は memory にも必ず写す** — API テストは memory で走るので、memory が prisma より緩いと「API テストも契約テストも緑、本番だけ違う挙動」になる（実測で、エージェント削除がガードレールのルールを Cascade せず、インシデントを Restrict と数えていなかった。前者は消えたエージェントを指すルールが一覧に残り続け、後者は memory だけが 204 を返していた）。prisma 側の挙動は契約テストで、memory 側は `tests/data/memory-*.test.ts` で**同じ期待を 2 か所に書く**（ここは意図的に対にする。ADR-0006 の死角を閉じる唯一の形）。一意制約違反は `DuplicateError` に翻訳（→ 422）、削除の可否は `'deleted' | 'not_found' | 'restricted'` の戻り値（→ 204 / 404 / 409）、役割変更・無効化は `UserMutationResult`（`ok` / `not_found` / `last_admin` / `disabled` → 200 / 404 / 409 / 409。`disabled` は無効化済みユーザーの役割変更の拒否で、無効化そのものは冪等なので返さない）。トークン発行は `UserTokenCreateResult`（`ok` / `not_found` / `disabled` → 201 / 404 / 409。発行先の存在と有効/無効の判定もアダプタが挿入と同じトランザクションで行い、prisma は発行先ユーザー行の `FOR NO KEY UPDATE` で無効化と直列化する）。**「最後の有効な admin を降格・無効化しない」判定は API 層ではなくアダプタが更新と同じ原子的操作の中で行う**（prisma はテナント行の `FOR NO KEY UPDATE` で同一テナントの要求を直列化。子テーブル INSERT の FK 検査（`FOR KEY SHARE`）とは衝突させない。API 層で count → update と分けると 2 人の admin が互いを同時に降格して 0 人になる。**ロックの存在は契約テストが決定的に固定する** — 別トランザクションで同じテナント行を掴んだまま降格を始め、待たされることを確かめる。並行要求を 2 本投げるだけのテストは実際には直列に流れるので、ロック句を落としても緑のまま通る）。一覧は `createdAt → id` 順。**カーソルは最終行の `(createdAt, id)` を符号化したキーセット**（`src/data/page.ts` が唯一の定義。API 層は `decodeCursor` で 1 回だけ復号して `PageQuery.cursor`（`CursorKey`）に渡し、形が違えば 422。アダプタは位置の比較 `(createdAt, id) > key` を where に AND する）。行 id をカーソルにしない（Prisma の `cursor` 引数は where と AND しないため他テナントの id で先頭行が飛び・存在が漏れ、行が削除されると続きが取れない）。更新は `findById` → `update` の 2 往復にせず、複合一意 `(tenantId, id)` の `update` 1 回で P2025 を null に翻訳する（`updateOrNull`）。失効の冪等性は `updateMany({ where: { ..., revokedAt: null } })` の条件付き更新で表す（無効化の冪等性は上の最後の admin 判定と同じトランザクションの中で「既に無効なら書き換えない」として表す）。

## プロキシ（Step2）

`src/app/api/v1/proxy/*` は `route()` に `auth: 'apiKey'` を渡して**API キー（`aop_k_`）だけ**を受け付ける（ユーザートークンでは 401。ADR-0007）。本体は `proxy-route.ts` のファクトリ 1 つで、プロバイダごとの違いは `src/lib/proxy/upstream.ts`（接続先・ヘッダ・タイムアウト）と `src/lib/proxy/usage.ts`（トークン数の項目名）に閉じる。**接続先はコードと環境変数だけから決まり**、クライアントの本文・ヘッダ・パスは影響しない（§9 SSRF）。許可は https か**非本番の**ループバック http だけで、資格情報付き URL・クエリ付き・リダイレクト追従は拒否する。上流の資格情報はサーバ側の環境変数から取り、クライアントの `Authorization` は転送しない。**料金表に無いモデルは中継しない（422）** — 0 円の行を作ると請求の根拠が壊れる。成功も失敗も `UsageEvent` を 1 行記録し（失敗はトークン 0・料金 0・実際の `statusCode`）、**記録の失敗は中継を止めない**。上流の 2xx はそのまま返す。**ステータスを保って中継する 4xx は許可リストの 400 / 413 / 422 だけ**で、それ以外（402 / 404 / 409 …）は 502 に写す — 本文を定型文にしても**番号そのもの**が共有している上流アカウントの状態を語る（402 は支払いの滞り）。拒否リストだとベンダーが新しい番号を使った瞬間に漏れるので許可リストにしてある（§9 fail-closed）。中継する 4xx も**本文は機械可読な項目（`error.type` / `code` / `param` と最上位 `type`）に絞る** — 自由記述には残高・組織名・契約ティアが載る。絞り込みの規則は `src/lib/proxy/error-body.ts` で、**項目ごとに綴りを分ける**（1 本にまとめると `param` 用のドットが `type`/`code` にも効き、区切り文字で書いた文が素通りする）。**許す文字の negative control は「禁止文字を 1 つだけ混ぜた値」を文字ごとに総当たりし、ASCII の全域（制御文字を含む）＋非 ASCII の代表点まで掃く** — 既存のケースは `'quota for org-ACME exhausted; plan=Enterprise'` のように禁止文字を複数含んでいたため、どれか 1 つが漏れても他の文字が落としてしまい、実測で `[A-Za-z0-9]` に空白を 1 文字足すだけで 116 件すべて緑になり `'Your credit balance is too low'` が 3 項目すべてに載った（`:` `=` `,` `/` `$` も同じ。ハイフンだけは既存のケースが単独で落としていた）。いまは許可文字の表から「許していない符号位置」を導いて **BMP を全点**当てる。**代表点のリストでは足りない** — 印字できる ASCII だけに絞った版は非 ASCII の BMP を足す 1 行の変異が全件緑を通り、代表点 26 点へ広げた版も **U+3164 HANGUL FILLER**（多くのフォントで空白として描画される）を足す変異が全件緑を通った。「空白に見えるが分類は Zs でない文字」は U+115F / U+1160 / U+FFA0 / U+2800 …と続き、代表点を足す限り追いかけっこが終わらない。**BMP の外も 1 点ずつ掃く** — 面ごとの端と代表点だけに間引いていた版は、数学用英数字（`U+1D400`〜、人間に読める字形）を足して `u` フラグを付ける変異が全件緑を通った。**3 項目を 1 つの本文に同時に載せて掃く**ので、費用は 1 項目ぶんのまま実装（`SAFE_CODE_PATTERN` / `SAFE_PARAM_PATTERN`）を直接確かめられる。`param` だけを掃いて「`type` / `code` の許可集合は `param` の部分集合だから導ける」としていた版は、**確かめているのがテストファイル側の手書きの表どうし**で 実装については何も言っておらず、`SAFE_CODE_PATTERN` にだけ数学用英数字を足す 1 行の変異が全件緑を通った。**当てる値は 2 形**（`abc<文字>def` と `<文字><文字><文字>`）— 挟んだ形だけでは「許した文字と混ざれるか」しか見ておらず、**同質な並びを丸ごと許す代替パターン**（`|[\u{1D400}-\u{1D7FF}]{1,40}`）は既存の綴りにも代替にも一致しないため出口に現れず、実測で全件緑を通った（`𝐘𝐨𝐮𝐫𝐂𝐫𝐞𝐝𝐢𝐭𝐁𝐚𝐥𝐚𝐧𝐜𝐞𝐈𝐬𝐓𝐨𝐨𝐋𝐨𝐰` が `error.code` に載った）。**残る境界**: 全 1,114,112 符号位置を 1 点ずつ当てるので「掃いていない符号位置を1 つだけ通す」族は閉じるが、**代替パターンの族は開いたまま**（4 文字以上の並びや特定の並び方を要求する形はこの 2 形では踏めない）。**「この族は閉じた」と書かない**。費用は約 26 秒で、vitest の既定のタイムアウト（5 秒）を超えるので明示的に延ばしてある。401 / 403（→ 502）と 429（そのまま）は写像の表 `UPSTREAM_STATUS_MASKING` が扱い、**`Retry-After` を中継してよいかも表が持つ**（429 だけ。値は整数の秒数の形だけ通す）。5xx は 502、時間切れは 504、設定不足は 503。**上流の失敗はサーバログに残す**（利用者へ返すのは定型文なので、残さないと接続不能も時間切れも証明書エラーも運用者には見えない）。**応答本文の読み取りに失敗した 502 も同じ**で、この経路は `ApiError` を投げて catch を素通りするため記録が別に要る（理由は閉じた語彙なので定型文で分岐して出し、上流由来の文字列は 1 バイトも混ぜない）。**上流の本文が JSON として読めなければステータスに関わらず 502**（HTML のエラーページ・本文を持てない 204/304・上限超過。`Content-Type` では判定しない — 前段が付け替えただけの正しい JSON を捨てると「課金だけして捨てる」経路になる）。上流の応答本文にも上限を置く（`UPSTREAM_MAX_RESPONSE_BYTES`）。数えながら読む処理は `src/lib/stream-bytes.ts` がリクエスト本文と共有するが、**写像先の HTTP エラーと「上限超過で下層を解放するか」は呼び出し側が選ぶ**（リクエスト本文側で解放すると 413 が届く前に接続が切れ、上流側で解放しないと ソケットと fd がタイムアウトまで滞留する — 事情が正反対）。**503 のときは記録しない**（上流へ 1 バイトも出ていない呼び出しを記録すると、未設定のあいだ有効なキー 1 本で DB の行だけを無制限に増やせる）。**残る境界は ADR-0007 決定 7** に記載。ストリーミングは Step2 の範囲外で 422。**本文だけは `z.strictObject` にしない**（ベンダーのペイロードなので未知キーを通す。`tests/openapi.test.ts` の除外表に理由付きで 1 件だけ登録してある）。

## 品質評価（Step3）

評価実行は**2 段**（対象エージェントへ入力を投げて応答を得る → その応答を judge が採点する。ADR-0009）。**上流の結線はプロキシと共有する**（`src/lib/proxy/upstream.ts`）— judge 専用の結線を別に持つと SSRF 対策・https の制約・タイムアウト・本文サイズ上限が片方にしか掛からない。プロバイダ差（本文の組み立て・応答テキストの取り出し）は `src/lib/llm/messages.ts` だけに閉じる（トークン数で同じことをしている `src/lib/proxy/usage.ts` と同じ役割分担）。judge の provider / model は `JUDGE_PROVIDER` / `JUDGE_MODEL`（既定は定数）で、**知らないプロバイダ名は既定へ倒さず 503**（fail-closed）。**judge も評価時のエージェント呼び出しも `UsageEvent` に記録しない** — 利用者の呼び出しと混ぜると日次集計が評価のたびに跳ね、Step4 のコスト超過ルールが評価のせいで発火する。**不正出力の判定は 2 段**（`src/domain/evaluation/judge-output.ts`）: 応答全体の異常（JSON として読めない・`results` が配列でない・**依頼していない/読めないケース ID を含む**）は**そのバッチを全件除外**し、ケース個別の異常（重複・欠け・範囲外）はそのケースだけ除外する。幻覚 ID を混ぜる応答は正しく見える行も同じ生成の産物なので信用しない。**判定が返す配列は依頼したケースと同じ順・同じ件数**（過不足があると再現率の分母が静かにずれる）。**どの段が失敗してもケース単位の除外に落として続行し、実行の記録は必ず 1 行残す**（API は 500 ではなく 201 で「失敗した実行」を返す。Step2 の「課金されたのに台帳に無い」と同じ思想）。**平均スコアは採点 0 件なら `null`**（0.0 だと Step4 の品質低下ルールが「最低品質」と読んで誤発火する。DB の CHECK 制約でも守る）。**除外理由の正本は enum `EvaluationExclusionReason`**で、ゲートはそこから期待するテスト名（`除外: <理由>`）を導いて全種類ぶんが pass しているかを見る（料金表からモデル名を導くのと同じ形。理由を足してテストを書き忘れたら落ちる）。**再現率の定義は `src/domain/evaluation/scores.ts` の `agreementRate` が唯一の場所**で、ケース ID で突き合わせ、スコアは**厳密等価**で比べる（丸めると許容幅のぶん揺れを見逃して一致率が実際より高く出る）。**ベンチのスタブ上流は意図的に揺れを注入する** — 決定論的なスタブでは一致率が必ず 100% になり、計測そのものが何も検査しない。**残る境界**: 確かめているのは「一致率の計算と揺れの検出」で、**実 LLM の再現性ではない**（ADR-0009）。**実行履歴を持つ評価セットのケースは変更・削除できない**（更新・削除 API を作らない。入力が動くと回帰比較が無意味になる）。**回帰比較は専用エンドポイントを作らず `GET /evaluations/{runId}` の応答に含める**（片方でも平均が無ければ差は `null`）。

## ガードレール・監査ログ（Step4）

判定の入口は `src/lib/guardrail/evaluate.ts` の `evaluateGuardrails` **だけ**で、3 つの起点（中継の直後 = cost / error_rate、評価実行の直後 = quality、明示実行 `POST /guardrails/run` = 全種別）がすべてここを通る（ADR-0010）。**別経路を書かない** — 「cron では発火するのに中継では発火しない」食い違いが静かに生まれる。**2 つの種別の表（`USAGE_RULE_KINDS` / `QUALITY_RULE_KINDS`）を足し合わせると `RuleKind` を全網羅する**ことを `tests/guardrail-evaluate.test.ts` が enum から導いて確かめる（種別を足して結線を忘れると、そのルールは永久に発火しない）。**順序は固定**: ルールを引く → 窓を集計して判定 → `Incident` の記録と自動停止（アダプタが 1 トランザクション）→ 監査ログ → **通知は最後**。 **1 本のルールの失敗で判定全体を止めない**（ループの中で受け止めてログに残し、次のルールへ進む。**受け止めた件数は `GuardrailEvaluation.failed` で呼び出し側へ返し、`POST /guardrails/run` は 1 本でも失敗していれば 500**。**数えるのは例外だけではない** — 「集計窓が範囲外で測れなかった」（`measureFor` が `null`）と「発火したのに記録できなかった」（`repos.incidents.raise()` が `null`＝エージェントかルールが並行して消えた）も同じく失敗。どれも数え損なうとそのルールが `evaluated` の側に入り、**超過して記録も停止もされていないのに `{ evaluated: N, fired: [] }` の 200** が返るので、運用者と cron は「何も超過していない」と見分けが付かず上限内だと読む。失敗したルールは `evaluated` に数えない）— 例外が外へ出ると後ろのルール（`stop` を含む）が 1 本も判定されないまま終わり、中継の経路は `evaluateGuardrailsSafely` が 1 行のログに畳むのでエージェントは超過したまま動き続ける（同じ並び順である限り次の中継でも同じ所で止まる）。**停止するかは `RULE_ACTION_SUSPENDS` の網羅的な表が決める**（`action === 'stop'` と書き下すと、`action` を足したときに新しい値が黙って「通知だけ」へ落ちる）。**止める側は fail-closed、記録と通知は fail-open**（通知や監査の失敗で停止を取り消すと「超過しても止まらない」状態になる）。**中継の経路だけ通知の完了を待たない**（`GuardrailTrigger.detachNotifications`）— 待つと受け手の応答時間が中継の応答時間に乗り、受け入れ基準「追加遅延 ≦ 50ms」を外部の遅さで破る（実測 1.2 秒。しかもプロキシのベンチは発火しないルールで測るので検出できない）。**同じ窓の長さの集計は 1 回だけ**問い合わせる（§8 の N+1 回避）。**開いているインシデントが同じルール・同じエージェントにあれば新しい行を作らず、監査ログも通知も出さない**（`RaisedIncident.created`。超過は解消するまで続くので、判定のたびに記録すると notify のルールでは毎分 600 件規模まで溢れる）。**ただし停止は重複排除しない** — 開いている間に復帰させられたエージェントは再び止める（抑えると「超過しているのに動いている」状態が残る）。 **停止を伴わない判定で既に開いている記録があるときは、エージェント行を押さえずに先読みだけで返す**（`notify` のルールは超過が解消するまで自分では止まらないので窓のあいだ中継 1 回ごとに `raise` へ来る。毎回ロックを取ると同じエージェントへの中継が 1 件ずつ直列化し、しかも結果は毎回 `created: false` で捨てられる）。先読みの取り逃しはトランザクションの中の判定が吸収する。ロックの有無は結果に現れないので、**別のトランザクションで同じ行を掴んだまま呼んで「待たされないこと」**を契約テストが固定する（ロックの存在を見る検査と逆向きの手口）。しきい値判定のドメインは `src/domain/guardrail/rule.ts` で、**比べる向きは `RULE_COMPARISON` の表が決め、判定はその表を読む**（書き下すと表と実装が食い違っても気付かない。実測で向きを逆にしても全件緑だった）。**測れていないものは発火させない**（呼び出し 0 件の窓・採点 0 件の評価・**分母が `GUARDRAIL_ERROR_RATE_MIN_REQUESTS` に届かないエラー率**。1 件だけ呼んで失敗した窓は 1/1 = 100% なので、門番が無いと 1 回のミスで自動停止する）。 **品質ルールも `windowMinutes` を見る**（`findLatestCompletedRun` に窓の開始を渡す）— 全期間を見ていると「ずっと前に 1 度だけ低い点だった」エージェントが、その後 1 度も評価していないのに判定のたびに停止し、インシデントを解決して復帰させても次の判定で同じ古い実行を読んで再び止まる（ルールを無効にするまで抜け出せない）。**窓の長さごとに引き直す**（1 回で済ませると、窓の違う 2 本のうち片方では見えない実行で判定してしまう）。**判定の窓は引き金になった行を必ず含める** — `createdAt` は DB の時計が入れる値なので、時計がずれると引き金の行が窓から落ちて発火しない（fail-open）。**向きごとに手当てが別**で、DB が進んでいる側は基準時刻を遅いほうに合わせ（`evaluationBasisTime`）、遅れている側は窓の開始を引き金の行まで広げる（`guardrailWindow` の `includeFrom` ← `GuardrailTrigger.triggeredBy`）。片方だけでは塞がらない。**広げ幅は窓の長さまでに縛る（＝窓は最大で 2 倍）** — 縛らないと遅れの幅がそのまま窓の長さになり、90 秒の遅れが続くと「1 分の窓」が毎回 90 秒ぶんを集計して、上限を超えていないエージェントが 1.5 倍（1 時間の遅れなら 60 倍）の合計で停止する。しかもインシデントと通知の文は「直近 1 分」と書くので記録が測ったものを偽る。遅れが窓の長さを超えるほど大きいときは引き金の行を取り込めず、その判定では発火しないことがある（「測った範囲と記録した範囲が食い違う」より「その 1 回は取りこぼす」を選ぶ取り決め）。**通知の `occurredAt` はその発火の時刻**で、インシデント行は最初の発火を表したまま（行の時刻を送ると「数日前の出来事の通知がいま届いた」ように見える）。品質は 3 観点の**最小**で、**逸脱は「低いほど良い」ので `1 - deviation` に直してから**比べる。コストは **BigInt 同士**で比べる（`Number()` を挟むと 2^53 超で「超えていない」になる）。**集計窓の終端は「基準時刻の 1 ミリ秒後」**（`now` を含まない形だと、判定を起こしたイベント自身が窓から外れてコストルールが永久に発火しない）。 **発火記録を持つルールは削除できない（409）ので、止める手段は `PATCH /guardrails/{ruleId}` の無効化だけ** — `enabled` 以外は切り替えさせない（しきい値や窓を変えると過去のインシデントが「どの設定で発火したのか」を示さなくなる。変えたいときは作り直す）。**無効化と再有効化は別の操作名で監査ログに残し**（記録を読むとき「外した」と「戻した」が区別できる必要がある）、**ルール数の上限は有効なルールだけを数え、別に行数の天井を掛ける**（`GuardrailRuleLimits` の `maxEnabled` / `maxRows`。無効化した行も有効側で数えると、上限ぶん発火したテナントは「消せない・止めても枠が空かない」でルールを 1 件も作れなくなる。一方で有効側だけを数えると総行数を縛るものが無くなり「作る → 無効化する」で行が無制限に増える — どちらも実測。上限は**省略可にしない**：既定値を持たせると渡し忘れたぶんだけ静かに消える。数え方は memory と prisma の両方の契約テストが固定する）。**有効へ戻すときも有効側の上限を数え直す**（渡していなかったときは「上限まで作る → 全部無効化 → また上限まで作る → 戻す」で有効なルールが上限の 4 倍まで増やせた。既に有効な行への再送は数に入っているので数え直さない）。**しきい値の単位は網羅的な表 `RULE_THRESHOLD_UNIT` が決める**（`kind === cost ? 金額 : 割合` と書くと、種別を足したときに黙って比率扱いになり lint も typecheck もテストも何も言わない）。

## 監査ログ（Step4）

書き込みは `src/lib/audit/record.ts` の `recordAudit` **1 か所経由**（`repos.auditLogs` を直接呼ばない）。鍵は `AUDIT_HMAC_SECRET` から読み、未設定・32 文字未満は **503**（fail-closed。鍵なしのハッシュで代用すると、DB を触れる相手が連鎖を作り直せて検知にならない）。**`createdAt` はアプリが決めて保存とハッシュの両方へ同じ値を渡す**（DB の既定値に任せると別の瞬間になり、全行が初日から `hash_mismatch`）。正規化・HMAC・連鎖検証は `src/domain/audit/chain.ts` が唯一の源で、**正規化は JSON の配列**（区切り文字の連結だと「別の内容なのに同じハッシュ」を作れる）、**`payload` はキーを辞書順に並べ入れ子を許さない**（JSONB はキー順を保存せず、入れ子は正規化が並べ替えないのでハッシュが不定に揺れる。形は `recordAudit` が実行時に確かめる）。**人が行う操作は状態を変える前に `assertAuditConfigured()` を呼ぶ** — 変えてから記録に失敗すると記録の無い変更が残り、しかも再試行は「既にその状態だ」で永久に失敗する（実測で resolve がそうなっていた）。対象は停止・復帰・インシデントの解決・ルールの登録と無効化と削除の 5 経路で、**ガードレールの自動発火だけが例外**（止める側を優先する）。**操作名の語彙は `src/domain/audit/action.ts`** で、**発行箇所の無い値を置かない**（`tests/audit-coverage.test.ts` が表から導いて落とす。実測で `agent.budget_exceeded` が定義だけされ予算超過の 403 が 1 行も残っていなかった）。`AuditLog` は DB トリガで**追記専用**（`UPDATE` は例外なく拒否、`DELETE` は `SET LOCAL agent_ops.allow_audit_delete = 'on'` を宣言したトランザクション内だけ。**アプリはこの設定を 1 か所も行わない**）。**検証は区間に分けて行う** — `GET /audit-logs/verify` は `?fromSeq=` でその連番から検証でき、続きがあれば `nextFromSeq` を返す（**先頭からしか読めない形にしない**。行数が 1 回の上限を超えたテナントでは最古の区間だけを検証し続け、それ以降の行は二度と検証されない＝書き換えても「無傷」と答える fail-open）。途中から辿れるのは**1 つ前の行のハッシュを錨として渡す**ため（`AuditChainAnchor`。錨には連番も入れて「区間の先頭が削除されている」も検知する）。**`fromSeq` は桁数と値の両側で範囲を見る**（正本は定数だけのモジュール `src/domain/audit/seq.ts`。`FIRST_AUDIT_SEQ` は `chain.ts` が再公開し、文言は `src/lib/constants.ts` が上下限から組み立てる） — 上限（int8 の最大値）を見ないと、範囲外の連番が `where: { seq: { gte: … } }` へ届いて PostgreSQL が拒否し、**利用者の入力が原因なのに 500 とスタックのログ**になる（実測 `P2020`）。**API テストからは見えない**（memory アダプタは空を返すだけなので「末尾を越えた」の 422 に見える＝ADR-0006 の死角）。桁数の門（`BigInt` へ直す前に落とす）は外しても同じ 422・同じ文言になるので、`tests/validations.test.ts` が Zod の issue の `code` でどちらの段で落ちたかを見分ける。OpenAPI にある写し（`pattern` と説明文の上限）は `tests/openapi.test.ts` が、README の写しは `tests/docs-gate.test.ts` が定数と突き合わせる。**範囲は `src/domain/pg-bigint.ts` の `parsePgBigint` が判定する**（金額と共有。同じ int8 の上限を 2 か所に literal で書かない）。**Prisma の `P2020`（範囲外）はアダプタで翻訳しない** — 利用者の入力が原因のときだけでなく「自前の計算が桁あふれした」ときにも出る code なので（`UsageEvent` のトークン数がその例）、一律に 422 へ写すと後者が「あなたの入力が不正」に化けて自分のバグを隠す。**利用者由来の BigInt を where に入れる経路は入口で範囲を見る**のが規則で、Step6 で新しい BigInt の絞り込みを足すときも同じようにする。**残る境界**: 末尾の行をまとめて消されたことはこの連鎖では分からない（外部の錨が要る）。

## レート制限と予算（Step4 / ADR-0007 の宿題）

`src/lib/api/rate-limit.ts` のスライディングウィンドウ。**キーはテナント**（`tenant:<id>`。プラットフォーム管理者だけ `platform`）で、偽装できるヘッダ（`X-Forwarded-For`）に頼らない。**資格情報ごと（API キー・ユーザー）にしない** — どちらも API から好きなだけ増やせるので、キーを増やすだけで上限が何倍にもなる（代償は「1 本の壊れたクライアントが同じテナントの枠を食い潰す」こと。費用を払う単位はテナントなのでそちらを選ぶ）。**断った要求は数えない**（数えると窓が延びて永久に通れない）。**記録は DB の共有ストア**（`repos.rateLimit` / 表 `RateLimitHit`。ADR-0015）で、枠は配備全体で 1 つ。配線は `RouteOptions.rateLimit` で、**掛ける対象は「上流へ費用を発生させる経路」と「1 要求が極端に重い経路」**（中継 2 本 ・ `POST /evaluations` ・ `POST /guardrails/run` ・ `GET /audit-logs/verify`）。**枠は重さの理由ごとに分ける**（`RATE_LIMIT_TIER`。上限は網羅的な表 `EXTRA_FRAME_LIMIT` が持つ）: `fanOut`（評価の実行。守るのはベンダーへの課金）・`outbound`（明示実行。守るのは外部の応答時間と DB 負荷で、上流 LLM は呼ばない）・`heavyRead`（連鎖の検証。1 回で最大 `AUDIT_CHAIN_VERIFY_MAX_ROWS` 行を読んで同数の HMAC を計算し直す＝一覧の上限の 50 倍で、守るのは DB の読み取りと CPU）が共有の枠に**加えて**それぞれの小さい枠を消費する（置き換えだと重い経路と中継を交互に叩くだけで合計が共有の上限を超える）。**「重い」をひとまとめにしない** — 1 つに束ねた版は、1 要求 1 エージェントの明示実行にとって小さすぎて定期掃きが成り立たなかった（**いまの定期掃きは明示実行ではなく `POST /maintenance/run` が行う**ので、この経路に枠を掛け直す判断は ADR-0016 が持つ）。**判定と記録は data 層の 1 回の操作**（共有の枠と追加の枠の両方が上限未満のときだけ 1 行足す）— 2 つの表を順に数える形だと、片方だけが数えてしまい「断った要求は数えない」が破れる。**追加の枠を持つルートは枠を数える前に認可する**（`RouteOptions.requiredAction` / **admin 限定のルートは `requiredRole: 'admin'`**。レート制限は認証の後・本体の前に掛かるので、`route()` で認可しないと view しか持たない利用者がテナント全体の小さい枠を使い切れる — 本体で 403 になる要求でも枠は減る。**`requiredAction: 'view'` では admin 限定のルートを守れない** — RBAC の許可表に「admin だけが持つ操作」が無く `view` は 3 役割すべてが持つので、実測で viewer が 10 回投げると `heavyRead` の枠が尽き admin の改ざん確認が 1 分間 429 になった。**本体の `requireAction` / `requireAdminRole` は残す**）。**掛け忘れは import の連鎖から導いて見張る** — `tests/route-wrapping.test.ts` が「`src/lib/proxy/upstream.ts` へ到達するルートの非 GET は必ず指定を持つ」「`src/lib/evaluation/runner.ts` へ到達するルートの非 GET は `fanOut`」「追加の枠を持つルートは `requiredAction` を宣言している」を要求する（手書きの一覧だと、上流を呼ぶルートを足した人が追記を忘れたぶんだけ網が狭まる）。**429 の宣言漏れも結線から導く** — `tests/openapi.test.ts` が「印の付いたオペレーションは 429 を宣言している」ことを要求する（宣言が無いと生成した型にその応答が現れず、型から使うクライアントが 429 と `Retry-After` を知らないまま書かれる）。判定は印（`ROUTE_RATE_LIMIT_BRAND`）を実体から読み、**印は枠の種類を値として持つ**（真偽値だと `fanOut` を標準へ落とす変更が見えない）。**印そのものの挙動も `tests/rate-limit.test.ts` が固定する**（常に値を返す変異は本番の挙動を変えないのでそこでしか落ちない）。**共有の上限は `PROXY_RATE_LIMIT_PER_MINUTE` で上書きできる**（ベンチは毎秒数百件を出すので既定では計測トラフィックが弾かれる。読めない値は既定へ倒す）。**追加の枠は環境変数で動かせない**（広げると上の根拠が崩れる）。**同じキーの「数える文」は助言ロック（`pg_advisory_xact_lock(hashtext(key))`）で直列化する** — 1 文の CTE に収めるだけでは足りない（READ COMMITTED のスナップショットは文の開始時点で固まるので、同時に走った別の文の挿入が見えない。実測で上限 3 に対して 10 本同時なら 6 本が通った）。**ロックは別の文で取る**（同じ文の CTE では意味が無い）。**同時性の検査は「N 本投げて通ったのは上限ぶんか」では書けない**（同時に実際に走る本数は接続プールの大きさで決まるので、本数を増やすほど直列に近づく＝実測で 30 本ならロック無しでも上限ぶんになった）— 別の接続で同じキーのロックを掴み、`consume` が待たされることを決定的に見る。**ストアが落ちたら断る**（fail-closed。`rate_limit.store_unavailable` を間引く出口で残してから投げるので、汎用の 500 に埋もれない）。**二度と来ないキーの行は `sweep(windowMs, limit)` で掃く**（呼ぶのは保守の定期実行＝`POST /maintenance/run`。ADR-0016）。予算は `src/lib/guardrail/budget.ts` が中継の**前**に当月（UTC）の累計と比べ、超過なら 403（中継してから断っても課金は発生する）。**`POST /evaluations` も同じ関数を通す** — 中継だけを守ると「中継の代わりに評価を回す」だけで迂回できる。**ただし評価の支出は `UsageEvent` に入らない（ADR-0009）ので予算には積まれない**（プラットフォーム側の支出台帳は ADR-0010 の宿題）。**予算が未設定なら問い合わせも起きない**。**`Incident` は作らない**（`Incident.ruleId` が NOT NULL で、予算はルールではない）。

## 保守の定期実行（ADR-0016）

受け口は `POST /maintenance/run` の 1 本（プラットフォーム管理者のみ）で、中身は `src/lib/maintenance/run.ts` の `runMaintenance`。**2 つの「誰も呼ばない後片付け」を同じ受け口に集める**: ガードレールの定期掃き（ADR-0010 の宿題）とレート制限の記録の回収（ADR-0015 の宿題）。**定期掃きが要るのは「通常は不要」ではない** — 集計窓は半開区間なので**窓から古い行が抜けるだけでしきい値を越える**ルールがあり（エラー率は分母が減って率が上がり、品質は良い実行が抜けて平均が下がる）、どちらも**使われなくなったエージェント**で起きるので判定を起こす要求が無く、繋がないと永久に発火しない（fail-open）。**1 要求でやる仕事には上限を置き、続きはカーソルで返す**（上限は `MAINTENANCE_*` の定数。全件を 1 要求でやると配備が育つほど 1 回が長くなり、実行時間上限に当たって途中で切れたことが応答に現れない）。**予算はエージェント数とテナント数の 2 本**（`MAINTENANCE_TENANT_SCAN_MAX`）— エージェント数だけだと**稼働中のエージェントを 1 件も持たないテナント**（解約済み・作ったばかり・全部停止）が予算を消費しないので、そういうテナントが並ぶあいだループが止まらない。**予算は、それを使い切らないまま進む経路があるなら上限として機能しない。** **テナントはページでまとめて読む**（§8。1 件ずつ読むと往復が直列に積み上がる）が、**エージェントの読み出しはテナントごとに 1 本**なので（一覧はテナント単位＝ADR-0002）往復の本数はテナント側の上限で決まる — だからその上限は 1 ページぶんに置く。**ティックが足し合わせる `tenantVisits` は「テナントの件数」ではない**（同じテナントにエージェントが残るあいだカーソルを進めないので、続きの要求でもう一度数えられる）。**カーソルは 2 本**（テナントとエージェント）で、**呼び直す必要があるかは `passComplete` の旗が表す** — カーソルの `null` から導いてはいけない（旗の意味は「全部終わった」ではなく「この一巡を続けるために呼び直す必要があるか」。打ち切りも真になる）。**回収の旗は `null` を取る**（続きの要求では掃きを 1 度も試していないので、`true`＝「確かめて残っていなかった」と区別する）— そのぶん**判定は `=== false` で書く**（`!swept.complete` だと続きの要求すべてが戻ってテナントを 1 件も歩かなくなる＝実測で既存のテストが落ちた）。**掃きの打ち切りは「0 件」で判断する**（`FOR UPDATE SKIP LOCKED` を入れたので、上限未満は「もう無い」と「いま触れない行があった」の両方を意味する）。記録の回収は**一巡の開始でだけ**行い（境目は `rateLimitWindowMs()` の長さを**記録側の時計**から引いて決める。**呼び出し側が時刻を渡せる形にしない** — `at` を入れるのは DB の `statement_timestamp()` なので、アプリの壁時計から組み立てた境目を渡すと、アプリが進んでいる配備で窓の中の生きた記録が消えて枠がリセットされる＝ADR-0015 が `consume` について直した食い違いが掃きだけに残る。契約テストは同じホストで走るので捕まらない）、**バッチ数の上限で打ち切ったときはテナントを 1 件も歩かずに「カーソルは両方 `null`・旗は偽」で戻る** — 歩くと残りの回収が次の一巡の開始まで待ち、**その一巡の最後の応答は `passComplete: true` になって回収の残りが応答から消える**。この順序のおかげで旗が実際に効いている（**旗をカーソルの `null` から導く変異は、順序を入れる前はテスト 19 件すべて緑のまま通った** — ADR-0016 に当初の誤った根拠と実測を残してある）。**同じテナントにエージェントが残っているあいだはテナントのカーソルを進めない**（進めると残りがその一巡で二度と判定されない）。**回収と一覧の読み出しも投げさせない** — 回収（`sweep`）は一巡の開始でだけ走るので、投げると毎回のティックが同じ所で落ちてテナントを 1 件も歩かない（軽い仕事の失敗が本題を恒久的に止める）。 `agents.list` が落ちたらそのテナントを飛ばし（カーソルは進める）、`tenants.list` が落ちたら進めた分を返して **`passComplete: true` でこの一巡を打ち切る**（偽で返すと、一巡の最初の要求では「回収が途中」の応答と 1 ビットも違わないので、ティックが同じ要求を上限まで送り直し `failed` も繰り返しのぶん積み上がる）。どちらも `failed` に数える（投げると 500 になって続きのカーソルが応答に載らず、その要求で進めた分がまるごと捨てられる＝1 テナントの不調が配備全体の backstop を止める）。**経路は `maxDuration` を宣言する**（1 要求が数十秒かかるので、サーバーレスの既定では毎回 504 になり一巡が一度も終わらない）。**判定が失敗しても 200 を返す**（`POST /guardrails/run` とは逆。500 にすると呼び出し側が続きのカーソルを受け取れず、そのテナント以降が丸ごと判定されない。取りこぼしは `failed` と `scripts/maintenance-tick.mjs` の終了コードで見せる）。**停止しているエージェントは判定しない**（窓の集計は動かず、発火しても「もう止まっている」だけ）。**レート制限は掛けない**（他のプラットフォーム経路と同じ。枠はプランから引くのでプランを持たない主体には倒れ先が無く、一巡はカーソルで何十回も呼ぶので小さい枠では掃きが途中で止まる）。**GET にしない**（副作用があるので §9。その代償として **Vercel Cron からは呼べない** — あちらは GET しか発行しない）。**スケジューラは同梱しない**（`npm run maintenance:tick` が一巡を回し切る形だけを持ち、起こすのは配備側。繋ぎ方は `docs/deploy.md`）。

## 通知（Step4）

`src/lib/notify/send.ts`。**宛先は環境変数だけが決める**（`NOTIFY_WEBHOOK_URL` / `NOTIFY_MAIL_WEBHOOK_URL`）。利用者由来の URL を受け取らないので SSRF の入口を作らない（防いでいるのは攻撃ではなく設定ミス）。スキームの規則は `src/lib/outbound-url.ts` でプロキシと共有する（https のみ・非本番のループバック http は可・資格情報付き URL は不可）。**クエリとフラグメントの可否は共有しない**（上流の基底 URL は後ろにパスを足すので拒否が要るが、通知の宛先はクエリ付きが普通に要る）。**署名できないなら送らない**（`NOTIFY_SIGNING_SECRET` が無い・32 文字未満。署名なしの通知は受け手がなりすましと区別できない）。**リダイレクトを追わない**（追うと署名付きの本文が別ホストへ行く）。タイムアウトと応答本文のバイト上限を置き、上限超過では下層のストリームも打ち切る（しないとソケットと fd がタイムアウトまで滞留する）。**SMTP は持ち込まない**（メールも同じ署名付き POST を中継へ送る）。**例外を外へ出さない**（通知だけ fail-open）。**ただし「届かなかった」は必ずログに残す** — 宛先が未設定のときだけ出さない（送るものが無いだけ）。宛先の形が駄目なときだけ出していた頃は、署名鍵が短い・受け手が 2xx 以外を返した の 2 つがログに 1 行も残らず消えていた（発火して停止したのに通知が 1 通も届かず、理由がどこにも無い）。文言には**直すべき環境変数の名前**を書く（`describeError` 以外の値をログの実引数に混ぜられないので、URL も理由の値も出さない）。

## 画面（Step5）

`src/app/login/` と Route Group `src/app/(dashboard)/`（ダッシュボード・エージェント一覧・詳細・インシデント一覧の 4 画面）。**ログインはユーザートークンの貼り付けで、セッション Cookie の値はそのトークンそのもの**（ADR-0011）。照合は `src/lib/api/auth.ts` の `authenticateUserToken` を再利用し、**新しい照合ロジックを書かない**（期限・失効・ユーザー無効化の扱いが 2 か所に分かれると片方だけ古くなる）。Cookie は `HttpOnly` / `SameSite=Strict` / `Path=/` と、**本番では `Secure`**（属性の組み立ては `src/lib/session.ts` の 1 か所）。

- **画面のデータは `repos`（data 層）を Server Component から直接読む**（自分の REST API を HTTP で呼ばない。認証の二重化と往復のコストを避ける）。`tenantId` はセッションの主体から取り出して `where` に必ず差し込む（ADR-0002・§9）。
- **集計は `src/lib/dashboard/summary.ts` の 1 か所だけ**で、画面・CSV ダウンロード（`(dashboard)/reports/daily/route.ts`）・突合テストがすべてここを通る。**受け入れ基準 3（突合）が機械で確かめられるのはこの形だから**で、CSV が別の集計を持つと「表示は合っているのにダウンロードが違う」を検査できない。稼働率の定義（`statusCode < 400` の割合・呼び出し 0 件は `null`）は `src/domain/uptime.ts` の純粋関数で、`docs/spec.md` の UC-06 が散文の正本。**0 件を 0% に倒さない**（Step4 の「測れていないものは発火させない」と同じ流儀で、0% は品質低下ルールの誤発火に直結する）。
- **書き込み（停止・復帰・インシデントの解決）は Server Action で、順序が決まっている**: Origin の一致 → セッション → CSRF トークン → 入力の形 → **RBAC（`requireAction` / `requireAdminRole` を API と同じ許可表で）** → 監査の鍵の確認（`assertAuditConfigured`）→ 更新 → `recordAudit` → `revalidatePath`。**`SameSite` は CSRF トークンの代わりにならないので併用する**（§9）。トークンは `HMAC-SHA256(鍵 = セッションのトークン, メッセージ = 固定文字列)` の同期トークンで、**サーバ側に状態を持たない**（`src/lib/csrf.ts`）。**Origin ヘッダが無い要求は拒否する**（fail-closed）。
- **1 つの画面に複数の操作を置くときは Server Action を 1 本にして `intent` を検証する** — `useActionState` の状態は**渡したアクション関数の同一性が変わると初期値へ戻る**ので、操作ごとに別のアクションを渡す形では成功メッセージが一度も表示されない（実測）。`intent` の値は網羅的な表（`src/domain/agent-status.ts` の `AGENT_STATUS_BY_INTENT`）で解釈し、知らない値は拒否する。
- **一覧から行が消える操作の結果は redirect ＋ クエリで伝える**（インシデントの解決。`RESULT_QUERY_NAME`）— 解決した行は「未解決だけ」の一覧から消えるため、その行に紐づくメッセージを返しても描画される場所が無い（実測で一度も見えなかった）。
- **`'use server'` のファイルは async 関数しか export できない**ので、フォームの項目名・初期状態・結果の語彙は `src/lib/dashboard/form.ts` に置く（ビルドだけが落ちる形なので typecheck では気付けない）。
- **CSV の経路は `route()` で包まず OpenAPI にも載せない**（セッションで認証して `text/csv` を返すので、Bearer 認証・JSON 応答を前提にした契約に乗らない）。**例外は理由付きの表 `SESSION_PAGE_ROUTES`（`tests/route-wrapping.test.ts`）に登録し、代わりに「`api/v1` の外にあること」と「セッションを自分で確かめていること」を機械で要求する**（素の除外にすると、認証を忘れたルートを同じ場所へ足せる）。**キャッシュ制御はこの表では要求しない** — 応答を数えるラッパー（`withResponseCount` ＋ `withPrivateCacheHeaders`）が**全ルート共通で**付けるようになったので（ADR-0014）、固定しているのはそちらの 2 本（「export はすべてラッパーを通っている」と「返した応答にも付く」）。表ごとに同じことを要求すると、片方だけが古くなる。
- **画面の文言は `src/lib/constants.ts` の `UI_TEXT`**（`API_MESSAGES` と同じ流儀。画面に直書きしない）。配色は `src/app/globals.css` の `:root` のトークン 1 か所で、WCAG AA を満たす値を持つ（§7）。日時の表示は `src/lib/dashboard/datetime.ts`（UTC・分まで。列見出しに `(UTC)` を付ける）。
- **受け入れ基準の正本は `scripts/lib/step5-criteria.mjs`** で、**`STEP5_SCREENS` が「主要 5 画面」の唯一の宣言**。E2E のテスト名（`画面: <title>`）・Lighthouse の測定対象・スクショのファイル名がすべてここから導かれる（撮影対象と E2E の対象を二重管理しない）。
- **Lighthouse は公式の `desktop-config` で測り、1 画面を 3 回測って中央値を取る** — 既定はモバイル（4G 相当＋CPU 4 倍の絞り込み）で、運用者が PC で開く管理画面を測る条件に合わない。1 回だけの計測は同じコミット・同じ機械で 81〜98 まで揺れた（実測）ので判定に使えない。**測る側は点数を JSON で出すだけで、合否は `scripts/gate-step5.mjs` が判定する**（ベンチと同じ分担。判定を測る側に持たせると「測れていないのに合格」を測る側だけで作れる）。

## プランと課金（Step6）

契約プラン（`free` / `pro` / `enterprise`）ごとの上限と可否の**正本は `src/domain/plan.ts` の `PLAN_LIMITS`**（網羅的な表。`PERMISSIONS` と同じ流儀で、判定は `planLimitsFor` / `planAllows` / `guardrailRuleLimitsFor` だけが行う。ADR-0012）。**軸は 3 つ**（エージェント数・プロキシの枠・機能の可否）で、テナント月次コスト上限は入れていない。**未知のプランは最も厳しい側（`FALLBACK_PLAN` = free）へ倒す** — `planAllows` は false、`planLimitsFor` は free の上限を返してログに 1 行残す（throw にすると「DB に enum 外の値が 1 行ある」だけでそのテナントの全 API が 500 になる）。表の添字は `Object.hasOwn` で確かめる（素の添字だと `constructor` が Object 由来の値を返し、上限の比較が TypeError になる）。`FALLBACK_PLAN` がどの次元でも最も厳しいことは `tests/plan.test.ts` が固定する。**pro は Step4 までの固定値と同じ**（プラン別にして緩くなった利用者はいない）。**行数の天井は有効側の 4 倍を導出する**（表に 2 つ持たせると「有効側より小さい天井」を書ける）。

- **プランは認証時に Principal へ載せる**（`UserPrincipal` / `AgentPrincipal` の `plan`）。トークン・キーを引く既存のクエリに `tenant: { select: { plan: true } }` を足すので**DB の往復は増えない**（中継の追加遅延 ≦ 50ms に影響しない）。`PlatformPrincipal` は対象外（テナント境界の外側なのでプランを持たない）。
- **機能ゲートは `route()` の宣言**（`RouteOptions.requiredPlanFeature`）で、**レート制限より前**に置く。順序を入れ替える変異は実測で**全件緑**のまま通り、使えないプランの 403 が枠を消費して以降 429 になった（いまは `プランで断った要求はレート制限の枠を消費しない` が**記録の件数が 0 であること**まで見る＝`rateLimitHitCount(seed.store)`）。宣言漏れは `tests/route-wrapping.test.ts` が印から導いて落とし、**本体側でも `requirePlanFeature` を呼ぶ**（宣言を落としたときに静かに開かない fail-closed）。
- **件数の上限はアダプタが挿入と同じ原子的操作の中で数える**（`repos.agents.create(input, limits)`。上限は**省略可にしない**）。prisma はテナント行の `FOR NO KEY UPDATE` で直列化し、**ロックの存在は契約テストが決定的に固定する**（別トランザクションで同じ行を掴んだまま始めて待たされることを見る）。**数え方は memory にも写す**（ADR-0006 の死角）。**超過の文言に数値を書かない**（プラン別なので書けない。現在の上限は `GET /billing` で引く）。
- **課金は受信と参照だけ**（`POST /billing/webhook` と `GET /billing`）。**Stripe の SDK は入れない** — 署名検証は `node:crypto` の HMAC と `timingSafeEqual` で足りる（`src/lib/billing/signature.ts`。鍵は `STRIPE_WEBHOOK_SECRET`、32 文字以上。未設定・短すぎは 503）。**定数時間比較は検出網で守れない境界** — 素の `===` へ差し替える変異は全件緑のまま通る（二次的な綴りの網はあるが証明ではない。`secretsEqual` を使う規約とレビューで守る）。イベント種別 → プランの写像は網羅的な表（`src/lib/billing/events.ts`）で、**知らない種別・知らない価格は反映せず 200**（勝手に free へ落とすと有料テナントが機能を失う。契約の変更イベントなのに決められなかったときだけログに残す）。**価格だけでプランを決めない** — 契約の状態（`status`）も網羅的な表 `BILLING_SUBSCRIPTION_STATUS_EFFECT` で見る（`active`/`trialing`/`past_due` は価格から、`canceled`/`unpaid`/`paused` は free へ、`incomplete`/`incomplete_expired` と**知らない状態・状態が無い本文は何もしない**）。見ないと「払っていない契約で有料プランが付く」「解約の 2 通目（`updated` の `canceled`・価格は有料のまま）が有料へ戻す」が通る（**配信順は保証されない**ので後者は実際に起きる）。**いまの契約とは別のサブスクリプションの解約も反映しない**（`isStaleCancellation`。解約の再送が遅れているあいだに結び直した契約を古い解約が打ち消すため。判定は両方の ID が分かるときだけで、契約の開始・変更は対象にしない＝新しい契約が勝つ）。**反映できなかったことは表にある全種別でログに残す**（`fromPrice` だけを見ていた版では解約の取り違えが無言で消えた）。**残る境界**: 同じ契約の中で価格だけが前後する入れ替わりは閉じていない（`event.created` の高水位が要る。ADR-0012 の宿題）。
- **冪等性は DB の一意制約で表し、受信の記録とプランの反映を同じ原子的操作に入れる**（`BillingEvent` の `@@unique([provider, eventId])`。`recordOnce(input, apply)` が違反を `'duplicate'` へ翻訳し、2 通目は何もせず 200）。**「処理済みか先に SELECT」にしない** — 同時に届いた 2 通で両方が通る。この違いは**同時性のテストでしか見えない**ので、`冪等性: ` の群に並行の 1 本を必ず置く。**受信は反映できなかった場合も記録する**（知らない顧客・知らない価格でも「受け取った事実」を残す）。**反映を「記録の後の別の操作」にしない** — 記録だけが先に確定すると、反映が落ちた（DB の一時障害・連携 ID の一意制約違反）イベントが `duplicate` として無視され続け、**そのイベントは永久に反映されない**（解約が落ちれば解約済みのテナントが有料の権限を保つ。実際そうなっていた）。**反映は省略可にしない**（`null` を明示する。既定で「反映しない」にすると渡し忘れが静かに穴を戻す）。アダプタの約束は 4 つ（反映なしなら記録だけ / 対象が居なければ記録だけ残す / **反映が失敗したら記録も残らない** / 2 通目は何も書かない）で、prisma は 1 つの `$transaction`・memory は同じ順序。**prisma は「記録 → 反映」の順**にし、**どちらの文で一意制約に当たったかを変数で持つ**（違反は `$transaction` の外で受けるので中断済みトランザクションには触れない）。受信の記録を先に置けば、そこで落ちた違反は必ず `(provider, eventId)` のものなので、`meta` から列名を当てる推測が要らない — 推測に頼ると、ドライバが形を変えた瞬間に**ただの再送が 422** になり冪等性が反転する。**反映は条件付き更新 1 文**（`updateMany` の `where` に `id` と、必要なら `billingSubscriptionId`。0 件なら記録だけ残す）で、**解約のときだけ `expectSubscriptionId` を付ける** — 呼び出し側が読んだ行で `isStaleCancellation` を判断すると、解約と結び直しが並行して届いたときに古い解約が新しい契約を打ち消す（課金が続いているテナントが free へ落ちる）。**反映しなかった理由のログは冪等性の判定より後**に出す（前に出すと再送のたびに同じ行が鳴る）。**残る境界**: 反映は確定したが監査ログの書き込みだけが落ちた場合は記録の無い変更が残る（連鎖のハッシュをアプリ側で計算するので同じトランザクションへ入れられない。`assertAuditConfigured()` を反映の前に通して大半の原因を先に落とすところまで。ADR-0012 決定 6）。
- **`POST /billing/webhook` は `route()` を通らない唯一の API。** `auth: 'none'` を足す形は**採らない**（既定を 1 つ緩めると、どのルートも宣言 1 行で未認証にできる）。`tests/route-wrapping.test.ts` の理由付きの表 `SIGNED_WEBHOOK_ROUTES` へ登録し、代わりに**署名検証への到達**を機械で要求する（CSV の画面側ルートと同じ扱い。キャッシュ制御は上と同じ理由で、全ルート共通のラッパーの側が固定する）。**レート制限は掛けられない**（テナントが決まらない。前段の責務）。
- **プラン変更の経路は 2 本だけ**（Webhook と、プラットフォーム管理者の `PATCH /tenants/{tenantId}`）。**テナント内の admin は変えられない**（請求と権限が食い違う）。**課金連携の 2 列（`billingCustomerId` / `billingSubscriptionId`）も同じ PATCH で行う** — Webhook は顧客 ID で引くだけで書かないので、前者が無いと事業者のイベントが永久に `applied: false` になる（実際そうなっていた）。**後者は修復の経路**で、顧客を付け替えたとき新しい契約が既に有効だと `created` / `updated` が届かず古い契約 ID が残り、`isStaleCancellation` が以後の解約を**すべて捨てる**（受信は記録済みなので再送も来ない）。項目の省略は据え置き・`null` は連携を外すので、**省略を `null` として渡さない**。**既存の配備の行はマイグレーション `20261006000100_promote_existing_tenants_to_pro` が pro へ上げる**（`plan` 列は Step0 からあったが読まれていなかったので、放置すると配備した瞬間に全テナントが free の上限になる。新規テナントは free のまま。`tests/billing-migration.test.ts` が両方を固定）。**デモシード（`DEMO_TENANT_PLAN`）も pro** — README の quickstart が `GET /audit-logs/verify` まで通して書いてあり、free だとその手順が 403 になる（README 自身が「free では 403」と書くので文書の中で矛盾する）。整合は `tests/demo-quickstart.test.ts` が**ルートの印**（どのパスがプランで閉じているか）と **README の本文**（quickstart が何を叩くか）という独立な 2 つの手がかりから照合する。記録の形は `src/lib/billing/apply-plan.ts` に集め（`applyPlanChange` = 反映＋記録。Webhook は反映をアダプタが済ませているので `recordPlanChangeAudit` だけを呼ぶ）、`tenant.plan_changed` を監査ログへ書く（`actorId` は Webhook 由来なら `null`、payload の `source` が経路を示す）。**記録できる状態かの確認は「反映より前」**（順序を誤ると、鍵が無い配備で 1 通目を記録 → 503 → 再送は `duplicate` で 200 となり**そのイベントが永久に反映されない**。初版が実際にそうなっていた）。**`applyPlanChange` は反映後の行をそのまま返す** — プランだけを返して呼び出し側が「読んだ行＋プラン」で応答を組み立てる形は、`TenantDto` に可変の項目が増えた瞬間に更新前の値を返す（テストは 1 件も落ちない）。

## リリース準備（Step7）

成果物はデプロイ設定（`vercel.json` ・ `docs/deploy.md`）・API リファレンス（`docs/api.md`）・デモシード（既存の `prisma/seed-data.ts`）・負荷試験レポート（`docs/load-test.md`）。受け入れ基準は 4 つで、**うち 2 つは「基準の文のままでは機械化できない」ので解釈を決めてある**（ゲート運用ルール 4 に従い `docs/roadmap.md` と ADR-0013 に書く）。

- **基準①（`docker compose up` → 5 分以内にデモ動作）は同じ上限を 2 経路で見る。** CI の `docker-smoke` ジョブが `up -d --build` から数えて（イメージのビルドとマイグレーション適用を含む＝**基準そのもの**）、`npm run bench:demo-ready` が本番ビルドの起動から数える（**部分集合**。ゲートが毎回確かめるのはこちら）。上限は `scripts/lib/step7-criteria.mjs` の `DEMO_READY_MAX_MS` の 1 つで、どちらもそこから読む。**ゲートを Docker 必須にしない**のは、Docker の無い機械でゲートが回らなくなると「ゲートが緑になってから次へ進む」運用が成立しないため（部分集合のほうが必ず速いので「ゲートが緑でも CI が赤」はありうる。逆は無い）。
- **「デモ動作」の中身の正本は `scripts/lib/demo-flow.mjs` の `DEMO_STEPS`**（7 段: 健康確認 → テナント作成 → エージェント登録 → 一覧 → 契約プランの参照 → **停止** → 監査ログの参照。**停止を入れているのは監査ログの段を意味のあるものにするため** — 記録を残す操作を 1 つもしないまま `GET /audit-logs` を叩くと、空の一覧に 200 が返るだけで記録の書き込みが壊れていても通る）で、**ベンチと CI のプローブ（`scripts/demo-probe.mjs`）が同じ `runDemoFlow` を呼び、判定も同じ `demo*Problem` を呼ぶ**（別に書くと「ゲートが測るデモ」と「CI が測るデモ」が静かにずれる。初版はプローブが 5 本の比較を書き写していて、しかも `demoStepDefinitionProblem` が抜けていたので `DEMO_STEPS` から 2 段消すと CI 側は「5/5 段・並び一致」で緑のままだった）。**仕込みは HTTP だけで行う**（DB へ直接書くと「配備した成果物で動くか」を測らない。入口はプラットフォーム管理者トークンでの `POST /tenants` で、応答の `adminToken.secret` 以後はそれで進む）。**時間だけでなく段の数・「一覧に出た件数」・「監査ログに残った件数」も判定する** — 段を削った計測は「デモが動いた」の証拠にならず、201 だけでは別テナントへ書いていても通り、`GET /audit-logs` が 200 を返すだけでは記録が残る配備だと言えない。**宣言の正しさ（`demoStepDefinitionProblem`）・「全部通ったか」（`demoStepsCompletedProblem`）・**「正本と同じ名前が同じ順序か」（`demoStepOrderProblem`）**は別の判定に分ける**（1 本にまとめると「基準を 1 つだけ破る」形が書けず、`tests/gate-scripts.test.ts` の表が成立しない）。**件数だけでは足りない** — `runDemoFlow` は段の名前を返すのに呼び出し側も判定も長さしか見ていなかったので、`GET /billing` の要求を消してラベルだけ積む形や同じラベルを 2 回積む形が「7 段通った」として素通りした。突き合わせは `countStepsInOrder`（正本の隣＝`demo-flow.mjs`）が行い、**判定へは一致した位置の数（数値）を渡す** — `judgeBenchPayload` の「項目が数値でなければ例外」という fail-closed を配列 1 つのために緩めると、「項目名を打ち間違えたときに基準を黙って飛ばす」穴が全基準に戻る。**デモの筋の `fetch` には 1 要求ごとの上限を掛ける**（`fetchWithTimeout`。Node の global fetch は既定でタイムアウトしないので、配備が応答を返さなくなると判定は所要時間の比較より後ろにあるため一度も実行されず、ジョブは「基準違反で赤」ではなく無言でハングする）。あわせて **CI の 3 ジョブすべてに `timeout-minutes` を置く**（置かないと既定の 6 時間まで待たされ、必須チェックなのでマージも止まる）。
- **基準②（同時 100 でエラー率 < 1%）は「レート制限の無い読み取り」で測る**（`GET /api/v1/agents`）。枠のあるルートは同時 100 で 429 を返すのが**正しい挙動**なので基準を測れず、枠を環境変数で広げると本番と違う設定を測ることになる。**失敗は 2xx 以外 ＋ 応答が返らなかった要求の合計**（`non2xx` だけでは「切られた分」が消える）。**`timeouts` を足し合わせない** — autocannon の `errors` はタイムアウトを含む（`lib/run.js` の `onTimeout()` が両方を数える）ので、足すと二重に数えて**基準を満たしている計測を赤にする**。**分母は「決着した要求」＝ `requests.total + errors`** にして、分子（`non2xx + errors`）と母集団をそろえる。autocannon の 3 つの数は意味が違う: `requests.total` は応答を受け取った件数（接続エラーとタイムアウトを含まない）、`requests.sent` は送った件数（打ち切り時に飛行中だった分も含む）、`errors` は応答が返らなかった件数。`total` を分母にすると分子だけが決着しなかった分を含んで**100% を超えうる**（2,000 件送って 1,200 件タイムアウト・800 件 200 なら本当は 60% なのに 150%）、`sent` を分母にすると逆に**飛行中の分で薄まる**（同時 100 なら最大 100 件が分母にだけ入り、基準ちょうどの配備が合格側へ寄る）。**丸めは切り捨て**（`Math.round` だと [0.99995%, 1%) が `1` になり、基準「< 1%」を満たす計測が誤って赤になる）。**分母の門番（接続数の 10 倍）と同時接続数そのものも判定する**（3 件流して 0 件失敗なら 0%、1 接続ならそもそも 0%）。**ちょうど 1% の境界を落とすのはベンチ側の判定**（`concurrencyErrorRateProblem`）— ゲートの独立な比較は「実測値 ≦ 上限」の形しか扱えないので、そこは桁違いの悪化を見る二重化として読む。**遅延は判定に使わない**（同時 100 では待ち行列が伸びるので「1 件あたりの増分」は Step2 のベンチが逐次で測る）。
- **基準④（既知バグ 0）は手がかりを 2 つ要求する**: `docs/known-issues.md` の「未解決のバグ」の表が空であること（**未解決のバグの正本**）と、**ソースのコメントに残った「未解決の欠陥」の印**（一覧の正本は `scripts/lib/step7-criteria.mjs` の `KNOWN_BUG_MARKERS`）が 0 件であること。片方だけでは fail-open（文書だけなら編集 1 行で黙らせられ、印だけなら文書に書いたバグが素通りする）。材料を集めるのは `scripts/lib/known-issues.mjs`、判定は `gate-report.mjs` の `knownBugProblems`（ベンチ・Lighthouse と同じ分担）。**走査が 1 ファイルも読めていなければ落とす**（「印ゼロ＝緑」にしない）。**表の枠（見出し行と区切り行）そのものを要求する**（節を空にして枠ごと消すと「0 件」と区別できない）。**印はコメントの中だけを探し、行末までのコメントと行をまたぐ囲みコメントの両方を状態を持って追う**（`commentPositions`。整形の慣習で行頭に `*` が付く前提を置くと、`*` の無い行が素通りする。実測）。**行末コメントの綴りは拡張子ごとに決める**（`lineCommentOpenersFor`。`//` は全拡張子、`--` は `.sql` だけ。`#` は走査するどの拡張子でもコメントではないので持たない）— 一律に `--` を当てていた版は TS の `i--` を「ここからコメント」と誤読して続く `/*` を見落とし、**その囲みコメントの中の印がまるごと素通りした**（実測。取り落ち＝fail-open。文字列リテラルを区別しないほうは「余計に拾う」向きなので誤った赤で済み、向きが逆）。**1 行の中の出現は全部見る** — 最初の 1 回だけを見ると、同じ行でコードの側に先に綴りが現れたときコメント中の本物の印を取り落とす（実測。印を値として書いた変数宣言の後ろに同じ印のコメントを続けた 1 行が 0 件になった）。**走査対象として宣言したディレクトリ（`KNOWN_BUG_MARKER_DIRS`）が実在して中身を持つことも固定する** — `filesUnder` は読み取りの失敗を `[]` に畳むので、1 つ改名・移動するだけでその配下の印が黙って外れ、他にファイルがあるかぎり「1 ファイルも読めていません」も鳴らない（痕跡が差分にもテスト件数にも出ない）。**生成物のディレクトリ（`src/generated`）は走査しない** — gitignore 対象で人が直せないので、依存を上げたときに生成物のコメントへ印が入ると「直す手段が無い指摘」でゲートが赤くなる（理由付きの表 `KNOWN_BUG_MARKER_EXCLUDED_DIRS` の 1 件だけ。gitignore 対象であることはテストが照合する）。**印は語の境界を要求する**（前後が英数字・下線なら印ではない）— 伏字やプレースホルダを「未解決の欠陥」と報告すると、直す手段が「コメントを書き換える」か「検出網を緩める」だけになる（実測で伏字を書いたコメントが 1 件として報告された）。**片側だけでは足りない**: 同じ印が連続する伏字では、右だけ見ると末尾の 1 つが、左だけ見ると先頭の 1 つが通る。**`TODO` は印に含めない** — 宿題を ADR とコメントに書く流儀なので、含めると実行不能な要求になり検出網が緩められる側に倒れる。**印を探すのはコメントの中だけ**で、これにより**印の一覧そのものやそのテストを理由付きで除外する表を 1 つも作らずに済む**（代償として、説明の文章に印の綴りを書けない。だからこのファイルも「印」と呼んでいる）。

## `scripts/bench-*.ts`

受け入れ基準のうち時間を測るもの（プロキシの追加遅延・1 万件の日次集計）。**しきい値は `scripts/lib/step2-criteria.mjs` が唯一の定義**で、`tests/docs-gate.test.ts` が `docs/roadmap.md` の Step2 行の散文と突き合わせる。プロキシのベンチは**逐次（1 接続）で測る** — 全力で流すと待ち行列が伸び、測れるのは追加遅延ではなく 1 プロセスの処理能力になる（実測: 全力 72ms / 毎秒 50 件に制限しても autocannon 自身のペース配分が混ざって 166ms / 逐次 10ms）。測る percentile は p97.5（autocannon は p95 を出さないので、より厳しい側で見る）。**判定の前に捨て玉（既定 200 件）を流す** — 起動直後の十数件だけが桁違いに遅い初回コスト（ルート読み込み・Prisma の接続確立・TLS 確立）は「中継 1 件あたりの増分」ではないため。混ぜると遅い機械ほど窓に入る件数が減って上位 percentile が押し上がり、同じコミットが機械によって合否で割れる（実測: 開発機 1358 件で p97.5 12ms・合格／CI ランナー 606 件で p97.5 155ms・不合格）。**上限も percentile も追加遅延の定義も変えていない**。捨てた側の分布も結果の JSON に出す。理由の正本はスクリプト冒頭のコメント。**ベンチ本体は計測して結果 (payload) を返すだけにし、判定・出力・終了コードは `scripts/lib/bench-criteria.mjs` の `runBench(ラベル, 計測)` が持つ** — false` を出したまま exit 0 になり、ゲートは終了コードしか見ないので緑）。結線は `tests/gate-scripts.test.ts` が**トップレベルで実行するのは `requireContractDatabase` → `runBench` の 2 つだけ**（順番込み）・トップレベルに条件や `try` を置かない・`process.exit` / として読めるか、あるいは**代入の左辺**（`globalThis[MARKER] = true` の印。値がそこから外へ出ない唯一の形）のときだけ免除し、それ以外は `'globalThis'` という使い方として数えて許可リストで落とす。**免除を「さらに辿る・呼ぶ形でなければ」にしてはいけない** — 値は変数宣言・括弧・実引数などあらゆる式の文脈から外へ出られるので、`const R = globalThis.globalThis;` と 1 ホップ挟むだけで塞いだはずの 2 系統が戻った（実測）。**「土台なら免除」にしてはいけない** — 追えるのは 1 ホップだけなので、2 ホップ以上や読めない添字がまるごと視界から消える。同じ理由で、**`process.exit` を呼ばずに取り出した形**（`.call` / `.apply` / `.bind(…)()` / `Reflect.apply` / 別名束縛）は実引数を非 0 に縛る検査が読めないので別の使い方として数え、**`eval` / `new Function`** も「そこで追えなくなる組み込み」として同じ枠で落とす。**許可の範囲は走査済みの集合から導く** — import の許可が `scripts/lib/` の前方一致だった頃は、走査が直下 1 段だったときの `scripts/lib/sub/`、拡張子 `.mjs` で絞っていたときの `scripts/lib/preflight.js`（`type` 宣言が無いので CJS）がどちらも「許可されるのに一度も見られない」状態で、そこへ `process.exit(0)` を置いて取り込むだけで素通りした（実測）。ベンチがアプリ本体から取り込む先も同様で、「`src/` の下なら許す」では偽の合格 payload を出すモジュールを新設するだけでベンチを走らせずに基準を通せたため、結線ごとの許可リスト（実在チェック付き）にしてある。**それでも名前を並べる側は原理的に閉じない。** `[].constructor.constructor('process.exit(0)')()` は `Function` も `eval` も `globalThis` も `process` も綴らずに同じことをする（`.constructor` は不透明なホップとして数えるようにしたが、これも 1 つの綴りでしかない）。**そこで綴りを見ない層に置き換える**: 各ゲートを、`npm` をシムに差し替えた子プロセスで実際に走らせる **negative control の行列**。他はすべて成功させ（テストには満点のレポート、ベンチには合格の JSON を書かせる）、**流すと書いてある検証を 1 つだけ失敗させて**、ゲートが非 0 で終わることを 1 つずつ見る。あわせて **何も壊さなければ 0 で終わる**ことも見る（positive control。これが検査自身の射程を固定する — 射程が縮めば「壊していないのに落ちる」か「壊したのに落ちない」のどちらかで必ず赤くなる）。**検査対象を「実際に呼ばれた `npm`」から導いてはいけない** — 途中で黙って終わる変異は呼び出しの一覧ごと縮むので、検査も一緒に縮んで素通りする（実測で、判定の直後に反射的な終了を置く変異も、`audit` の判定を `if (false && …)` にする変異も全件緑で通った）。**ソース（流すと書いてある `npm` の引数）と `STEP0_STEPS` から別に導き、実際に流したものと突き合わせる**。これで、綴りを追っていた頃の 8 巡ぶんの変異（`globalThis` 経由・間接 exit・`eval`/`Function`・`.constructor`・反射的アクセス）と、静的には見えない形（ベンチの結果を偽装するヘルパー・ベンチの失敗だけ握り潰す判定）が**同じ 1 つの理由**で落ちる。同じ考え方は共有モジュール（`importsWithoutExiting`）とベンチ（`runBenchInCleanChild`）が既に使っている。**シムの PATH は先頭に足すのではなく置き換える** — 足すだけだと、シムを起動できない環境で探索が本物の `npm` へ落ち、入れ子の検証が走って上限まで止まる。**行列は両向きに突き合わせる** — 「書いてあるものを流しているか」だけでなく「流しているものが導出に入っているか」も見る（導出が黙って縮むと、実際に流している検証が negative control の対象から外れて「壊しても落ちない」窓が開く）。**検証コマンドの成否だけでは見えない緩め方もある**ので、レポートの中身を 1 件欠かす negative control を別に持つ（料金表の一部しか見ない変異はどの `npm` も失敗させない）。**欠かす位置は末尾 1 か所ではなく全添字を 1 本ずつ**回す — 末尾だけだと「末尾を含んだまま縮める」形（`slice(1)`・偶数添字だけ）が実測で全件緑を通った。料金表は小さいので全添字でも数秒で、これで「部分集合にする」族がまとめて閉じる。**この probe が実際に本物の fail-open を掘り当てた**: 基準のテスト名の照合が素の `includes` だったため、`料金: openai gpt-5` のテストが 1 件も無くても `gpt-5-mini` の名前が代わりに当たり、ゲートは緑のまま「誤差 0」を一度も確かめずに通っていた（`gpt-4.1` と `gpt-4.1-mini` も同じ）。いまは needle の直後が識別子を続けられない文字であることまで求める。**残る境界**: 許可リストが見るのは直接の import 先だけで推移的な依存は追わない。**ゲートのステップを丸ごと削除する形は検出網では捉えられない**（「流すと書いてあるもの」から導く以上、書くのをやめれば要求も消える）ので、`npm audit` と本番ビルド・lint・format:check・typecheck は CI に別ステップとしても置いて二重化してある（検出網を増やすより安い）。 **`npm audit` の範囲は本番依存だけ**（`--audit-level=high --omit=dev`。理由は ADR-0004 — 修正版が存在しない開発依存の勧告でゲートが止まると「直す手段が無いのに全 PR が赤」になり、待つかゲートを無効化するかの二択になる。しきい値は変えていない）。**二重化の一覧は手書きせず、行列と同じ手掛かり（`STEP0_STEPS` ＋ ゲートのソースの npm 引数）から導き、二重化しないものだけを理由付きの表に登録する**（理由は型で分け、「ゲート自身が別の呼び出しで流す」型はその別経路の実在まで機械で確かめる。「所要時間が倍になる」型はレビューでしか見られないので、**エントリが増える差分は理由の妥当性をレビューで必ず確認する** — 実測で、もっともらしい理由を 1 行足すだけで CI のステップを消しても全件緑になった） — 手書きだと新しい検証を足した人が「二重化するか」を一度も問われない。**突き合わせは `&&` で割った素のコマンドとの完全一致**にする（部分一致だと `npm run lint || true`＝削除と等価も、`npm audit --audit-level=critical`＝受け入れ基準そのものの緩和も、実測で全件緑のまま通った）。**同じ理由で、この行列そのものを消す差分も検出網には映らない**（テストを消したことを別のテストで落とす一般解は無く、痕跡はテスト件数の減少だけ）— これはこのリポジトリに限らずテスト全般の境界で、レビューで見る。ベンチ本体の計測式（何を測って `slowestMs` に入れたか）には静的・動的どちらの検出網も無く、レビューで見る。`typeof globalThis` のような正当な特徴検出も現在は落ちる（そう書いているファイルは無い）。**import 時に `process.env.DATABASE_URL` を書き換える形は静的には閉じきれない**ので、規約とレビューで守る（理由は `scripts/lib/contract-database.mjs` の docstring）。

## `scripts/gate-stepN.mjs`

Step ごとの受け入れ基準の検査（ADR-0004）。**受け入れ基準の値はゲート本体に書かず `scripts/lib/stepN-criteria.mjs` に置く**（後の Step のゲートが同じ定義を読む。ゲート本体に数値を書けると新しい Step で静かに緩められるので、`tests/docs-gate.test.ts` が「ゲート本体は基準の数値を宣言しない」ことも見張る）。**判定そのものは `scripts/lib/gate-report.mjs` の純粋関数に置き、`tests/gate-scripts.test.ts` が挙動を固定する** — スクリプトに書き下すと、件数の下限を小さくしても判定を `if (false && …)` にしてもゲートは緑のまま通った（実測）。しきい値そのものは `tests/docs-gate.test.ts` が `docs/roadmap.md` の**その Step の行**と突き合わせる（表全体を対象にすると、別の行の「ADR 3 件以上」に当たって下限 3 が素通りする）。**判定結果から終了コードへの写像は `scripts/lib/run-npm-steps.mjs` の `exitIfFailures` に集約する** — スクリプト本体に `process.exit(1)` を書くと、その 1 行を消すだけで「失敗の理由を表示したうえで `gate:step1 緑` と出て exit 0」になった（実測）。`runSteps` ともども子プロセス経由で挙動を固定している。
