## 運用（この文書の使い方）

- **バグを見つけたら、直すまでこの表に 1 行足す。** その間ゲートは赤になる＝「既知バグ 0」ではない、
  という状態が機械的に見える（これが基準④の「Issue 管理」のこのリポジトリでの解釈。
  ゲート運用ルール 4 に従い `docs/roadmap.md` と ADR-0013 にも書いてある）。
- **GitHub の Issue はゲートから読めない**（ネットワークに出られない・権限が要る）ので、
  未解決のバグの正本はこの表に置く。GitHub 側にも Issue を立てるのは自由だが、
  **ゲートが見るのはこの表**。
- **文書だけを手がかりにしない。** ゲートは**ソースのコメントに残った「未解決の欠陥」の印**も
  同時に探し、1 件でもあれば落とす（印の一覧の正本は `scripts/lib/step7-criteria.mjs`）。
  文書だけだと編集 1 行で黙らせられ、印だけだと文書に書いたバグが素通りする（どちらも fail-open）。
- **「後の Step でやる設計上の宿題」は印に含めない。** このリポジトリは宿題を ADR とコメントに
  書く流儀で、それらは欠陥ではない（含めると実行不能な要求になり、検出網が緩められる側に倒れる）。
  宿題は下の節と各 ADR の「宿題」欄に書く。

## 既知の制限（バグではない。設計上そうしてある／後の課題）

実装済みの範囲で**意図的に閉じていない**ことの一覧。いずれも ADR に理由と申し送りがある。

| 項目 | 内容 | 出典 |
| ---- | ---- | ---- |
| 保守の定期実行はスケジューラを同梱しない | ガードレールの定期掃きとレート制限の記録の回収は `POST /maintenance/run`（＋`npm run maintenance:tick`）で行うが、**それを定期的に起こす仕組みは配備側の責務**（host の cron・systemd timer・GitHub Actions の `schedule` 等。繋ぎ方は `docs/deploy.md`）。繋がないと、使われなくなったエージェントのエラー率・品質のルールが発火せず、二度と来ないキーの記録も残る。**Vercel Cron からは直接呼べない**（GET しか発行せず、この経路は副作用があるので POST にしてある） | ADR-0016 |
| ロックの待ちの打ち切りが混雑と区別されない | レート制限の判定は 1 トランザクションの中で「`lock_timeout` の設定 → キーごとの助言ロック → 判定の CTE → COMMIT」を行い、待ちを `RATE_LIMIT_LOCK_TIMEOUT_MS` で打ち切ったら数えずに 429 を返す（`rate_limit.contended`）。**ここには 3 つの残課題がある。** (a) 打ち切りは**トランザクション全体**に効くので、同じトランザクションの中の per-key の掃き出しが行ロックで待たされた場合も同じ経路に落ち、ログは「同じ枠の判定が混み合っている」と言う（運用者は上限を調べて空振りする）。**定期掃きの `FOR UPDATE SKIP LOCKED` が守るのは「掃きが待たない」側だけで、逆向き（`consume` が掃きの行ロックを待つ）は塞げていない** — あちらはキー指定の `DELETE` で `SKIP LOCKED` を書ける形ではない。(b) ロックは COMMIT まで握るので、**遠隔 DB（RTT 5〜10ms）では同時に来た数本が待ちの打ち切りを超えうる** — 上限に遠く及ばない同時バーストでも 429 になる。(c) `lock_timeout` の設定が毎要求 1 往復ぶん増えている（接続単位で設定すれば消える）。**値と形は実測で決め直す必要がある**が、同時アクセス下のレート制限を測るベンチが無いのも同じ課題（既存の同時実行ベンチは枠の無い経路を叩く） | ADR-0015 |
| 保守の掃きは通知の同時発射を絞らない | 定期掃きは 1 要求で予算ぶん（既定 50・最大 200）のエージェントを判定し、**通知の完了を待たない**（待つと `NOTIFY_TIMEOUT_MS` × 件数が 1 要求に乗って予算が長さを縛れない）。そのため**発火がまとまった回には予算ぶんの POST が同時に飛ぶ** — いちばん起きやすいのは「窓から古い行が抜けて越える」エージェントがまとめて初回発火する、**繋いだ直後のティック**。受け手が細いときは `MAINTENANCE_AGENT_BUDGET` を小さくして最初の数回を流す。同時数を絞るには判定側が通知の待ちを呼び出し側へ返す形が要る | ADR-0016 / ADR-0010 |
| 保守の一巡はティックの中だけで続く | ティックは続きのカーソルを**プロセスの中にしか持たない**ので、回数の上限（1,000 要求）に達すると一巡を終えられず、**次の起動はまた先頭のテナントから**になる。つまり 1 回のティックで届く範囲（既定の予算 50 なら約 5 万エージェント／空のテナントが多い配備なら約 20 万テナント）を超えると、**後ろの方は毎回同じように取り残される**（遅いのではなく届かない）。超える規模では `MAINTENANCE_AGENT_BUDGET` を上限（200）まで上げるか、**続きの位置をサーバー側に持つ**必要がある（下の「カーソルが中身を持つ」と同じ前提） | ADR-0016 |
| 続きのカーソルはテナントを名乗らない | `nextAgentCursor` は「あるテナントの中の位置」だが、どのテナントのものかは応答に現れない。一巡の途中で**そのテナントが DB から消える**と（解約の `Cascade`。API 経路は無いので DB へ直接当てた場合）、続きの要求は次のテナントを読んでそこへ同じカーソルを当てるので、**そのテナントの古い側のエージェントがこの一巡では判定されない**（`failed` も増えず応答にも出ない）。次のティックが先頭から拾うので自己修復するが、閉じるにはカーソルにテナントを持たせる（＝上の 2 項目と同じ「一巡の位置をサーバー側に持つ」） | ADR-0016 |
| 続きのカーソルが中身を持つ | `nextAgentCursor` は一覧と同じ符号化（`base64url("<作成時刻>:<エージェント ID>")`）なので、**復号すればエージェントの ID と作成時刻が読める**。`agentBudget: 1` で呼び続ければプラットフォーム管理者がテナント横断で列挙できる — あの資格情報はテナント内の資源に 403 を返す建前なので、その境界をメタデータのぶんだけ緩めている（ID 自体は他の経路では使えない）。不透明な継続トークンにするには**一巡の位置をサーバー側に持つ**必要があり、上の項目と同じ仕組みで一緒に閉じる | ADR-0016 / ADR-0005 |
| 保守の定期実行の死活は見えない | ティックが 1 度も走らなくなっても、アプリ側に「呼ばれていない」ことを知る術が無い（最後に掃いた時刻を持っていない）。いまはスケジューラ側で `maintenance:tick` の終了コードを見張る前提 | ADR-0016 |
| 前段のリバースプロキシ | 本文サイズ・タイムアウト・未対応メソッド（`TRACE` 等）・未認証経路の絞り込みはアプリ手前の責務 | ADR-0005 / ADR-0007 |
| 課金イベントの配信順 | 同じ契約の中で価格だけが前後する入れ替わりは閉じていない（`event.created` の高水位が要る） | ADR-0012 |
| 監査ログと反映の原子性 | プランの反映は確定したが監査ログの書き込みだけが落ちた場合、記録の無い変更が残る | ADR-0012 |
| 評価の支出 | judge とエージェント呼び出しは `UsageEvent` に入れないので、テナントの予算には積まれない | ADR-0009 |
| Checkout セッションの作成 | 課金は受信と参照だけ。事業者へ外向きに出す経路は入れていない | ADR-0012 |
| 幅方向のリクエスト費用 | 本文の深さには上限があるが、幅（短いキーを詰めた本文）の解釈費用は縛っていない | ADR-0007 |
