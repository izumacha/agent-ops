# 負荷試験レポート（Step7）

Step7 の成果物。**受け入れ基準②「同時 100 リクエストでエラー率 < 1%」と
①「クリーン環境で `docker compose up` → 5 分以内にデモ動作」の実測**を記録する。

> **数値の正本はベンチの出力**で、この文書はその読み物版。しきい値は
> `scripts/lib/step7-criteria.mjs` が持ち、`docs/roadmap.md` の散文との一致は
> `tests/docs-gate.test.ts` が突き合わせる（ここに写しは置かない）。
> **判定はゲートが毎回やり直す**ので、この表は「そのとき何が出たか」の記録として読む。

## 測り方

| ベンチ | コマンド | 何を測るか |
| ------ | -------- | ---------- |
| 同時実行 | `npm run bench:concurrency` | 本番ビルドを起こし、デモの筋で用意したテナントに対して `GET /api/v1/agents` を同時 100 接続で 10 秒叩く |
| 配備からデモ動作 | `npm run bench:demo-ready` | 本番ビルドを起こしてから、デモの筋（6 段）が通るまでの実時間 |

どちらも**専用 DB（名前が `_contract` で終わるもの）**を要求し、計測の前に全テーブルを
`TRUNCATE` して「何も無い配備」を作る。**上流 LLM は呼ばない**（実キーも課金も不要）。

### `GET /api/v1/agents` を選んだ理由

認証（トークンのハッシュ照合 ＋ DB の引き当て）とテナント境界つきの一覧クエリを通る
「ふつうの読み取り」で、**レート制限が掛かっていない**経路。レート制限のあるルート
（中継・評価の実行・ガードレールの明示実行・連鎖の検証）を選ぶと、同時 100 で 429 が返るのが
**正しい挙動**なので「エラー率 < 1%」を測れない。枠を環境変数で広げると、今度は本番と違う
設定を測ることになる。上流 LLM を呼ぶ経路も選ばない（実キーと課金が要る）。

### 失敗の数え方

**2xx 以外 ＋ 接続エラー ＋ タイムアウト**の合計。autocannon は接続エラーとタイムアウトを
`errors` / `timeouts` に別で数えるので、`non2xx` だけを見ると「接続を切られた分」が
無かったことになる。エラー率は小数第 4 位まで残す（1 万件規模で 1 件の失敗を 0% に丸めない）。

**計測が成立したかの門番も基準と同じ重みで掛ける**（判定は `scripts/lib/bench-criteria.mjs`）:

- 同時接続が受け入れ基準どおりか（1 接続に下げるとエラー率は 0% になる）
- 流れた要求が接続数の 10 倍以上か（分母が小さいほど割合は緩くなる）
- デモの段が宣言どおりの数あり、全部通ったか（段を削って速くした計測を通さない）
- 登録したエージェントが一覧に出たか（201 だけでは「動いた」と言えない）

## 実測（2026-10-07）

計測機: 4 vCPU / 16 GB RAM / Node 22（`.nvmrc`）/ PostgreSQL 16（同一ホスト）。
**この条件での記録**なので、CI ランナーや本番とは絶対値が変わる（基準との比較はゲートが毎回行う）。

### 受け入れ基準② 同時 100 リクエスト

| 回 | 同時接続 | 時間 | 総リクエスト | 失敗 | エラー率 | p97.5 | 最大 |
| -- | -------- | ---- | ------------ | ---- | -------- | ----- | ---- |
| 1 | 100 | 10 秒 | 2,939 | 0 | 0% | 593 ms | 803 ms |
| 2 | 100 | 10 秒 | 3,100 | 0 | 0% | 551 ms | 771 ms |

**合格**（上限は 1% 未満）。失敗は 2 回とも 0 件で、2xx 以外・接続エラー・タイムアウトの
いずれも発生しなかった。

**遅延は判定に使っていない。** 同時 100 では待ち行列が伸びるので、ここで出る数百ミリ秒は
「1 件あたりの処理時間」ではなく**飽和した状態の待ち時間**。1 件あたりの増分は Step2 の
受け入れ基準（プロキシ経由の追加遅延 ≦ 50ms）が、逐次 1 接続で別に測っている
（混ぜると測れないことの実測は `scripts/bench-proxy.ts` の冒頭コメント）。

スループットは約 300 req/s（4 vCPU、アプリと DB が同じホスト、1 リクエストあたり DB 2 往復）。

### 受け入れ基準① 配備からデモ動作まで

| 回 | 所要 | 通った段 | 一覧に出たエージェント |
| -- | ---- | -------- | ---------------------- |
| 1 | 1,061 ms | 6 / 6 | 1 |
| 2 | 1,045 ms | 6 / 6 | 1 |

**合格**（上限 5 分 = 300,000 ms に対して約 1 秒）。これは**部分集合**の計測で、
本番ビルドの起動からデモの筋が通るまで。**基準そのもの（`docker compose up` から数える）は
CI の `docker-smoke` ジョブ**がイメージのビルドとマイグレーション適用を含めて測る
（解釈は `docs/roadmap.md` の「Step7 の受け入れ基準の解釈」と ADR-0013）。

デモの筋（`scripts/lib/demo-flow.mjs` の `DEMO_STEPS` が正本）:
健康確認 → テナント作成 → エージェント登録 → 一覧 → 契約プランの参照 → 監査ログの参照。

## 分かったこと・分かっていないこと

**分かったこと**

- 同時 100 の読み取りで**取りこぼしは出ない**。接続は飽和するが、待ち行列に並ぶだけで
  エラーにはならなかった（Prisma の接続プールが待たせ、タイムアウトまでは届かない）。
- 配備からデモまでの時間は**ほぼアプリの起動時間**で、5 分の予算に対して 2 桁の余裕がある。
  予算を使うのはイメージのビルド（CI 側）なので、基準に近づくとしたらそこ。

**測っていないこと（意図的に残している境界）**

- **書き込みの同時実行**は測っていない。基準の文は「同時 100 リクエスト」で、
  読み取りの経路を選んだ理由は上記のとおり。書き込みは行ロックで直列化する箇所
  （テナント行の `FOR NO KEY UPDATE`）があるので、同じ条件ならスループットは下がる
  —— **ロックが存在することは契約テストが決定的に固定している**ので、
  「速さ」ではなく「正しさ」の側で担保している。
- **複数インスタンス**は測っていない。レート制限がインプロセスの `Map` なので、
  台数を増やすと枠が台数分だけ緩くなる（ADR-0010 の宿題。`docs/known-issues.md` にも記載）。
- **上流 LLM を含む経路の負荷**は測っていない（実キーと課金が要る）。中継 1 件あたりの
  追加遅延は Step2 のベンチがスタブ上流に対して測っている。
- **長時間の安定性**（メモリの増え方・接続の滞留）は測っていない。10 秒の窓で見ているので、
  リークがあっても現れない。
