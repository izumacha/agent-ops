# ロードマップと受け入れ基準

合計約 14 週・8 Step。**各 Step の基準は `npm run gate:stepN` として自動化し、赤なら次 Step のブランチを切らない。** Step の順序を入れ替えず、後 Step の機能を前 Step に混ぜない。

| 0 設計・骨組み           | 1 週 | `docs/spec.md`（ユースケース 10 件・ER 図・API 一覧）、リポジトリ雛形、Docker Compose、CI               | `typecheck/lint/test` が CI で緑／OpenAPI 定義が存在し `npm run gen` で型生成が通る／ADR 3 件以上                                           | 実装済み（`gate:step0`） |

## ゲートの運用ルール

1. `scripts/gate-stepN.mjs` が基準を順に検査し、1 つでも赤なら非 0 で終了する。
2. CI（`.github/workflows/ci.yml`）は実装済みの最新 Step のゲートを必ず実行する。
3. Step N+1 のブランチは、`main` で `gate:stepN` が緑になってから切る。
4. 基準を緩める変更は、このファイルと該当 ADR を同じ PR で更新する（テスト側だけを書き換えない）。

## Step6 のカバレッジの計測対象（基準④の解釈）

**「全体」をロジック層に限る。** 定義の正本は `scripts/lib/step6-criteria.mjs`（`vitest.config.mts` とゲートが同じ定義を読む）。対象は `src/domain` / `src/lib` / `src/data` / `src/app/api` の 4 つで、判定は **statements / branches / functions / lines の 4 指標すべて**が 80% 以上（1 つだけ見る形にすると、通る指標を選んで基準を満たしたように見せられる）。計測できなければ落とす（「測れていないから緑」に倒さない）。

外すものとその理由（ゲート運用ルール 4 に従い、基準の解釈はここと ADR-0012 に書く）:

- **画面の `.tsx`** — 主要 5 画面の E2E と Lighthouse が担保している（Step5 の基準）。入れると画面の行数で総計が決まり、ロジックのカバレッジが下がっても％が動かない。
- **生成物（`src/generated`）・型だけのファイル（`src/types`）・Port の契約（`src/data/ports`）** — 実行されるコードが無い（Port の実装は adapters 側で測る）。
- **prisma の結線と本番アダプタ（`src/lib/prisma.ts` / `src/lib/prisma-client.ts` / `src/data/adapters/prisma`）** — この計測は DB 不要の `npm run test` で走るので原理的に 0% になる。**正しさは基準③（契約テストが別 DB で CI で緑）が担保する**ので、同じ対象を 2 つの指標で数えない。

**この除外表に増える差分は理由の妥当性をレビューで必ず確認する**（除外表はこのリポジトリが繰り返し「静かに緩む口」として見てきた形）。

## 前提

- Next.js 16 + Prisma 7 + PostgreSQL 16（Docker）。
- 検証はすべてローカル＋CI で完結する（人手の営業・ヒアリングは含めない）。
