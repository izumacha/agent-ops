# ロードマップと受け入れ基準

合計約 14 週・8 Step。**各 Step の基準は `npm run gate:stepN` として自動化し、赤なら次 Step のブランチを切らない。** Step の順序を入れ替えず、後 Step の機能を前 Step に混ぜない。

| ------------------------ | ---- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| 0 設計・骨組み           | 1 週 | `docs/spec.md`（ユースケース 10 件・ER 図・API 一覧）、リポジトリ雛形、Docker Compose、CI               | `typecheck/lint/test` が CI で緑／OpenAPI 定義が存在し `npm run gen` で型生成が通る／ADR 3 件以上                                           | 実装済み（`gate:step0`） |
| 1 エージェント台帳・権限 | 2 週 | Agent/Tenant/Role の CRUD、API キー発行、RBAC（閲覧/実行/停止）                                         | ユニット＋API テスト 60 件以上 pass／権限違反テスト全パターン（役割 3 × 操作 3）で 403／`npm audit`（本番依存）high 0                                  | 実装済み（`gate:step1`） |
| 2 コスト計測プロキシ     | 2 週 | LLM 呼び出しを中継するプロキシ（Anthropic/OpenAI 互換）、トークン・料金を `UsageEvent` に記録、日次集計 | 料金計算の単体テストがベンダー公表単価と誤差 0／プロキシ経由の追加遅延 p95 ≦ 50ms（autocannon）／1 万件投入で集計 SQL ≦ 1 秒                | 実装済み（`gate:step2`） |

## ゲートの運用ルール

1. `scripts/gate-stepN.mjs` が基準を順に検査し、1 つでも赤なら非 0 で終了する。
2. CI（`.github/workflows/ci.yml`）は実装済みの最新 Step のゲートを必ず実行する。
3. Step N+1 のブランチは、`main` で `gate:stepN` が緑になってから切る。
4. 基準を緩める変更は、このファイルと該当 ADR を同じ PR で更新する（テスト側だけを書き換えない）。

## Step6 のカバレッジの計測対象（基準④の解釈）

**「全体」をロジック層に限る。** 定義の正本は `scripts/lib/step6-criteria.mjs`（`vitest.config.mts` とゲートが同じ定義を読む）。対象は `src/domain` / `src/lib` / `src/data` / `src/app/api` の 4 つで、判定は **statements / branches / functions / lines の 4 指標すべて**が 80% 以上（1 つだけ見る形にすると、通る指標を選んで基準を満たしたように見せられる）。計測できなければ落とす（「測れていないから緑」に倒さない）。

外すものとその理由（ゲート運用ルール 4 に従い、基準の解釈はここと ADR-0012 に書く）:

- **画面の `.tsx`** — 主要 5 画面の E2E と Lighthouse が担保している（Step5 の基準）。入れると画面の行数で総計が決まり、ロジックのカバレッジが下がっても％が動かない。
- **生成物（`src/generated`）・型だけのファイル（`src/types`）・Port の契約（`src/data/ports`）** — 実行されるコードが無い（Port の実装は adapters 側で測る）。
- **prisma の結線と本番アダプタ（`src/lib/prisma.ts` / `src/lib/prisma-client.ts` / `src/data/adapters/prisma`）** — この計測は DB 不要の `npm run test` で走るので原理的に 0% になる。**正しさは基準③（契約テストが別 DB で CI で緑）が担保する**ので、同じ対象を 2 つの指標で数えない。

**この除外表に増える差分は理由の妥当性をレビューで必ず確認する**（除外表はこのリポジトリが繰り返し「静かに緩む口」として見てきた形）。

## Step7 の受け入れ基準の解釈（ゲート運用ルール 4）

値の正本は `scripts/lib/step7-criteria.mjs`（ゲートとベンチが同じ定義を読む）。4 つの基準のうち 2 つは
「何をもって満たしたと言うか」を決めてあるので、ここに書いておく。

### ① クリーン環境で `docker compose up` → 5 分以内にデモ動作

**2 つの経路が同じ上限（5 分）を見る。**

- **CI の `docker-smoke` ジョブ** — `docker compose up -d --build` の開始時刻から数えて、
  イメージのビルド・コンテナ起動時のマイグレーション適用（`Dockerfile` の `CMD` が
  `prisma migrate deploy` を流す）・デモの筋が通るまで。**こちらが基準そのもの**。
  **シードは投入しない** — デモの筋は `POST /tenants` で自分のテナントを作るので、
  シードデータに依存しない（デモシードの確認は `migrate-and-build` ジョブが別に行う）。
- **`npm run bench:demo-ready`** — 本番ビルド（`.next/standalone`）を起こしてからデモの筋が
  通るまで。**ゲートが毎回確かめるのはこちら**で、Docker デーモンが無い機械でも回せる**部分集合**。

部分集合のほうが必ず速いので「ゲートが緑でも CI が赤」はありうる（逆は無い）。
**「デモ動作」の中身**は `scripts/lib/demo-flow.mjs` の `DEMO_STEPS` が正本で、
健康確認 → テナント作成 → エージェント登録 → 一覧 → 契約プランの参照 → **停止** →
監査ログの参照 の 7 段。**段数も判定する**（段を削って速くした計測は「デモが動いた」の
証拠にならない）。**停止を入れているのは監査ログの段を意味のあるものにするため** —
記録を残す操作を 1 つもしないまま `GET /audit-logs` を叩くと、空の一覧に 200 が返るだけで
「運用の記録が残る配備であること」を何も示さない（記録の書き込みが壊れていても通る）。

### ② 同時 100 リクエストでエラー率 < 1%

`npm run bench:concurrency` が、デモの筋で用意したテナントに対して `GET /api/v1/agents` を
同時 100 接続で叩く。**レート制限の無い読み取りの経路を選ぶ**（中継や明示実行を選ぶと、
同時 100 で 429 が返るのが正しい挙動なので基準を測れない）。失敗として数えるのは
**2xx 以外 ＋ 応答が返らなかった要求**（autocannon の `errors`。これは**タイムアウトを含む**ので
`timeouts` を足し合わせない —— 足すと二重に数えて、基準を満たしている計測を赤にする）。
分母が小さいほど割合が緩くなるので最小件数（接続数の 10 倍）を門番に置く。
**境界は等号を含めない**（「< 1%」）。

### ④ 既知バグ 0（Issue 管理）

GitHub の Issue はゲートから読めない（ネットワークに出られない）ので、**未解決のバグの正本は
`docs/known-issues.md` の「未解決のバグ」の表**に置き、ゲートは「表が空であること」を見る。
**文書だけを手がかりにしない** — 編集 1 行で黙らせられるので、**ソースのコメントに残った
「未解決の欠陥」の印**（一覧の正本は `scripts/lib/step7-criteria.mjs`）も同時に探し、
1 件でもあれば落とす。走査が 1 ファイルも読めていない場合も落とす（「印ゼロ＝緑」にしない）。

**「後の Step でやる設計上の宿題」は印に含めない**（このリポジトリは宿題を ADR とコメントに書く
流儀で、それらは欠陥ではない。含めると実行不能な要求になり、検出網が緩められる側に倒れる）。
宿題は `docs/known-issues.md` の「既知の制限」の節と各 ADR に書く。

## 前提

- Next.js 16 + Prisma 7 + PostgreSQL 16（Docker）。
- 検証はすべてローカル＋CI で完結する（人手の営業・ヒアリングは含めない）。
